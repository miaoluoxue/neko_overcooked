# 开发约定（硬规则，不要跳过）

> 这些规则不是建议，是**踩过坑之后用时间换来的**。违反它们会直接浪费实机测试机会，
> 而每次实机测试都要用户手动开一局（150 秒一局）。

---

## 规则 1（最重要）：动手前先读反编译，不要猜

**任何要改游戏交互/数值/机制的地方，先在 `overcooked_decomp/` 里把相关代码读出来，
把「文件名:行号」写进提交说明，然后再写代码。**

为什么是硬规则：这个项目里**每一次"猜"都错了**，而且都伪装成别的问题，代价很大。

真实案例（全部记录在案）：

| 我猜的 | 实际（读代码后） | 代价 |
|---|---|---|
| 厨师 id 就是玩家编号 | `cid` 只是 `FindObjectsOfType` 枚举序号，与 `Player.One/Two` 无关 | 键全发给错的人，人一动不动 |
| 交互半径 1.8 够用 | `FindNearbyObjects` 用 `GetCollidersInArc(1f, PI, ...)` —— **半径 1.0，量到碰撞体表面** | 走过去却拿不到东西 |
| 交互只看距离 | `IsColliderInArc` 还要 `Dot(forward, 目标) >= 0` —— **只认前 180°** | 背对着按交互键完全无效 |
| 移动有加速/惯性 | `ClientPlayerControlsImpl_Default` 每帧**直接赋值**水平速度 —— 无惯性，`RunSpeed=4` | 按键时长一直靠猜，来回震 |
| 网格就是关卡范围 | `GridManager.GetGridHalfSize()` 只覆盖厨房那一块；关卡远大于它 | 厨师被判成"被困住"，一步走不了 |
| 原生 `GridNavSpace` 是权威寻路 | 它只在 `Start` 建一次、**永不刷新**，且全工程只被老鼠 NPC 消费 | 直接穿水面淹死 |
| 水面是障碍 | 水是 `RespawnCollider` 触发器，**不占格子** | 同上 |
| 台面角色看组件类型 | 游戏靠 **tag**（`CookingStation`/`PlateStation`/`PlateReturn`/`ChoppingStation`…）+ 组件混合判断 | 台面分类全错 |
| 传送带只有一种 | `Travelator` 推**厨师**；`ConveyorStation` 推**物品**，速度单位是**格/秒** | 判定"这关没有传送带" |
| 手持物读哪个 carrier 都行 | `Server*` 拾取时立即写；`Client*` 靠同步，**晚一帧** | 刚拿到读成空 → 重试再按一次把东西放下 |
| 锅是"能倒空自己"的容器 | 锅身上**只有** `ServerCookableContainer`（实测组件清单：无 `PreparationContainer`）—— 锅永远不消失、不被消耗 | —— |
| 煮的是食材，取法是"用手拿" | 锅在灶上时 `CookingHandler` 长在**锅**身上（`cooking.name` = 锅名、`ing` 为空）；**空手对灶台按键 = 把锅端走**（`ServerAttachStation.CanHandlePickup` → 转交锅的 `IHandlePickup`） | 锅被搬走 → 每次都得多跑一趟把锅端回来 |
| 手拿盘子对锅交互是把菜倒进锅 | 反向分支：`ServerPlacementContainer.HandlePlacement` → 锅的 `ServerCookableContainer.CanTransferToContainer(盘子)` → `AssembledNodeTransfer.CanTransferFromContainer`（要求**全熟**）→ `TransferToContainer(null, 盘子, _dontRemove:false)` → **锅的容器被清空，锅留下** | 一直以为取菜必须拿锅 |
| `dir_sign` 防抖写在算方向之前没问题 | 它在第一次循环就读了还没赋值的局部变量 → `UnboundLocalError`，被 `execute` 的 `catch(Exception)` 吞成"这一步走不到" | 上一次提交让**每一次导航都崩**，还伪装成"卡住" |
| 空手对着盘子堆按键能拿到盘子 | 手上已经有东西时，同一个键是"放下" —— 材料会被丢在盘子堆上 | 材料凭空消失，后面拼不出菜 |
| 放东西的目标是"手里的东西" | `PlaceHeldItem_Server(_control, _target)` 拿 `_target` 去 `GetControllingPlacementHandler_Server(_target)`（`PlayerControlsHelper.cs:126-147`）—— **`_target` 必须是承载"放置句柄"的物体**（柜台/锅/上菜台），客户端发的也是 `m_iHandlePlacement` 本身（`ClientPlayerControlsImpl_Default.cs:156`），不是被拿的东西 | 放下时找不到句柄 → 走 `carrier.TakeItem()` 分支，东西**丢在脚下** |
| 按一下"使用"键 = 一条消息 | 是**两条**：`Update_Interact`（`:265-283`）在目标变化时发 `Interact`（开始互动，把 `Interactable` 的 InteractorCount 顶起来），按键瞬间再补 `TriggerInteract`（真正干一下） | 只发一条 → 切菜/和面"按了没反应" |
| 拾取键只做拾取 | 三个分支（`:238-263`）：手上有东西 → 放置；空手且 `m_iHandlePickup` 可取 → 拾取；否则若 `m_interactable.UsePlacementButton` → **当触发键用** | 上菜铃/工作台类交互完全按不动 |
| 按键没生效就是输入层的问题 | 六轮实测把输入侧全部排除（`pickupIsDownCalls=16111` 说明游戏每帧在读我们的键、`clientOurs/serverOurs=True`、`rebinds=0`、`paused` 全 false），卡的是**客户端消息链**（`Update_Carry` → `ChefEventMessage` → 服务端路由） | 在输入层反复试，浪费六轮 |

**正确流程**：
1. `grep` 出相关类 → 读实现（带行号）
2. 把结论写成注释放在改动旁边（写清"依据: 文件名.cs:行号"）
3. 再写代码
4. 能离线验证的**先离线验证**（见规则 3）

## 规则 2：拿不准就问游戏，不要自己算几何

游戏里凡是"判定"类的东西，它自己**早就把答案算好了**，直接读出来就行：

| 想知道 | 不要自己算 | 去读 |
|---|---|---|
| 按交互键会作用到谁 | 算距离/朝向 | `PlayerControls.CurrentInteractionObjects`（`PlayerControls.cs:394`）→ `m_TheOriginalHandlePickup` / `m_interactable` |
| 手上拿着什么 | 找子物体 | `ICarrier.InspectCarriedItem()`（`ICarrierPlacement.cs:5`），优先 `ServerPlayerAttachmentCarrier`（`:100`） |
| 厨师能不能动 | 猜 | `m_bRespawning` / `IsSuppressed()` / `MovementScale`（`PlayerControls.cs:304,494,390`） |
| 该用哪套键 | 试 | `PlayerIDProvider.GetID()`，配 `PCPadInputProvider.GetDefaultSplitKeyboardBindings()`（`:55-85`） |
| 哪些格子能走 | 猜障碍 | `GridManager.GetGridOccupant`（公开 API）+ 地面射线（`Ground\|SlopedGround` 层） |
| 怎么让厨师真的动手做一次交互 | 模拟按键、等游戏的消息链 | **直接调服务端入口**：`ServerPlayerControlsImpl_Default.ReceivePickUpEvent/ReceivePlaceEvent/ReceiveInteractEvent/ReceiveTriggerInteractEvent/ReceiveThrowEvent`（`:152-239`，全是 public 且无门），目标用游戏算好的 `CurrentInteractionObjects`。见 `Overcooked2AI/Game/InteractDirect.cs`、`tools/direct_probe.py` |

**尤其记住**：台面是**有体积**的，`IsColliderInArc` 量的是**到碰撞体表面的距离**，
厨师永远走不到台面正中间 —— 拿"格子中心"算距离是没有意义的。

## 规则 3：能在离线验证的，绝不留到实机

实机代价极高：要用户开一局、150 秒、还要抢焦点。

已有的离线手段：

```bat
python -u tools\dump_level_objects.py <关卡名> --summary   :: 离线看这一关有什么
python -u tools\floor_map.py <关卡名> --box ...           :: 离线看真实可站区域
python -u tools\reachcheck.py                              :: 逐台面检查够不够得着
python -u tools\check_names.py                             :: 未定义名字/BOM(能抓漏 import)
python -u tests\test_fetch.py                              :: 取料决策离线跑通
python -u tests\test_flow_sim.py                           :: **整条流程**在模拟器里跑完整闭环
```

`tests/test_flow_sim.py` 是"假游戏": 它按反编译出来的规则模拟切/煮/摆盘/送餐，让引擎
**不带游戏**跑完整张订单。它的移动也是真实运动学（`RunSpeed=4`、无惯性），
所以"来回跑一趟要几秒、饭会不会焦"在离线就能看出来。

> 模拟器本身的坑：`FakeGame` 的台面必须**深拷贝**（`dict(s)` 是浅拷贝，`on` 那个 list
> 会被两轮用例共用 → 单独跑通过、连跑两个用例失败）；`FakeKB` 必须带 `b` 键位表
> （引擎的 `_key()` 要走它）。这两处都是"测试失效却不是代码错"的典型。

**测试必须验证"能抓到回归"**：写完测试后，**故意把 bug 改回去**，确认测试报错，
再改回来。（`tests/test_fetch.py` 就是这么验证过的。）

## 规则 4：拿/放是同一个键 —— 误判＝毁掉战果

`PickupAndDrop` 是一个开关。所以：
- **确认"拿到了"必须轮询**（≤1.6 秒），不能只看一眼
- **重试前先重新读一次手持状态**，已拿到就别再按
- 读值优先服务端（权威），客户端值仅作对照

## 规则 5：别烧整局

一局 150 秒。任何"同一步反复失败"都要**立刻停下报错**，并指出卡在哪一步
（已在 `Engine.run()` 里实现：同一步连续失败 3 次就停）。
日志里必须打印**足够定位的数字**（坐标、距离、游戏给的判定值），不要只写"卡住了"。
