## 三分钟版

**平时什么都不用设。** 需要改的只有三样，而且它们都该写进 `runtime/watch.local`：

| 你要干的事 | 配什么 |
|---|---|
| 两个脚本自己打 | `NEKO_WATCH_CHILD=run_team.py --input keys,virtual` |
| 一个键盘一个手柄 ⇒ **必须保持前台** | `NEKO_WATCH_KEEP_FOCUS=1` |

配好之后：`python -u run_watch.py`。

## 参数本地化：`runtime/watch.local`

每开一次终端都要 `set` 一串环境变量，忘一个就跑成另一个配置 —— 而**跑错配置的代价是一整局**。
所以参数可以从一个本机文件读（`runtime/` 是 gitignore 的，不进仓库）：

```ini
# 每行 KEY=VALUE; # 开头是注释; 值里的 = 和空格都原样保留
NEKO_WATCH_CHILD=run_team.py --input keys,virtual
NEKO_WATCH_KEEP_FOCUS=1
```

- ☠ **显式设的环境变量优先于这个文件**（走 `setdefault`）——
  临时改一格 `set NEKO_CHORES=0` 仍然管用，不用去动文件。
- ☠ **这个文件能放下面这张表的全部 52 个，不只是看护那 11 个。**
  看护起子进程时 `Popen` **不带 `env=`** ⇒ 整个环境变量原样传给子脚本
  （实测：文件里的 `NEKO_CHORES` / `NEKO_STEP_COOLDOWN` 子进程都收得到）。
  ⇒ **一个文件配完所有东西**。
- 换路径：`NEKO_WATCH_LOCAL=<别的文件>`；**关掉它**：`NEKO_WATCH_LOCAL=0`。
- 它由 `run_watch.py` 读取（`parse_local_config`，纯函数，`runtime/_watch_probe.py` 有断言）。

## 行为层（执行器 / 兜底 / 失败处置）

| 变量 | 默认 | 干什么 |
|---|---|---|
| `NEKO_PLAN` | **`on`** | **默认开**（2026-09-17 起）／`shadow` = 算计划+打日志、**不改行为**／`0` = **一键回退**（与加它之前逐字相同） |
| `NEKO_PLAN_TTL` | `20.0` | 一份计划能用多久（秒）。过期就当没有 —— 这是"动态地图"那条的落地。☠ 判的是**计划自己的算出时刻**，不是"我读到的时刻" |
| `NEKO_PLAN_INTERVAL` | `6.0` | 多久重算一次（秒）。⚠ 某步**真失败**时会跳过节流立刻重算 |
| `NEKO_PLAN_BONUS` | `8.0` | "这一步是计划排给我的"奖励分。只加不减 |
| `NEKO_PLAN_COST` | `sec` | 规划器的**代价尺子**：`sec` = 秒（走路秒数 + 动作服务时间，见下）／`cell` = 逐字退回老尺子（走过的格数） |
| `NEKO_PLAN_MAKESPAN` | `1` | 派活时**看不看并行**：`1` = 目标改成**两个厨师各自总时间取最大**（makespan）／`0` = 逐字退回老口径（只看「这一步对谁最便宜」） |
| `NEKO_CHOP_SEC` | `1.5` | 一次切菜的**服务时间**（秒）。☠ **还没标定** —— 见「换尺子」那一节 |
| `NEKO_COOK_SEC` | `12.0` | 一次煮/烤的**兜底**秒数（拿得到游戏报的 `need` 时，执行期用它） |

`on` 走的是**软闸门 + 奖励分**（不是另写一个调度器）：
`_plan_next` 只放行计划排给我的那一步、`_plan_bonus` 给那一步 +8；
**这一步这一轮做不到就退回整池** —— 那正是"绝不停机"。

收窄的三条边界（2026-09-17 定）：
- **只收"计划覆盖的那几张单"的步** —— 归属按**槽位键**对（`_plan_flow` 返回一组槽位键，
  取自 `Plan.slots`），不靠菜名。同名多单里长得一样的步骤不会被一起收进来。
- **杂活留着** —— 计划管的是"菜谱那几步的顺序"，不是"别的活都别干"。
  （救锅另有硬上限兜底；但洗盘子/开火/到点取菜不该因为计划命中就停。）
- **可达性逐条判** —— 收窄前把此刻够不着的那几条**剔掉**，剩下的照常收窄；
  一条不剩才退回整池。老的"全部可达才收窄"在计划横跨几张单时会让整份计划
  被静默忽略（一张单那一步不可达 ⇒ 三张单的计划全不生效）。

★ **计划覆盖整个订单池**（`planner.plan(flows, …)`，2026-09-17）：`_plan_tick` 自己
建池（最多 `NEKO_COOP_ORDERS` 张单），所以 `NEKO_COOP_ORDERS` **同时**是
"候选池几张单"和"计划覆盖几张单"的上限。

形状是用户定的：**只覆盖到池，不在规划期排人** —— "谁做哪一步"仍旧交给
**执行层的评分 + 步级占位**去错开两个人。合并计划 = **无交并**：每张单各走一遍
它的链，拼起来、`deps` 整体偏移、每步盖上槽位键（`Step.slot`）；跨单**不建**依赖边。
某张单推不出解 ⇒ **跳过它**（打一行 notes），不把别的单的计划一起扔掉。

### 「这一步没有货源」不再拿满分（`NEKO_NOSRC_PENALTY`，2026-09-17）

用户原话：**"菜单的制作链有问题"**。实机 `s_balloon_5_2` 的订单卡：

```
1. fetch Bun  (⚠ 找不到货源(箱子/生料/成品都没匹配上))
```
引擎自己也认了：`⚠ BeefBurgerMax: **重拉知识表后还是找不到货源** —— 这关可能真的没有这种料`。

☠☠ **可这个信号全仓只有 `_derive_with_retry` 一处读它** —— 评分、候选池、`⊕备料`、
执行层**一处都不看** ⇒ 一个**已判定不可行**的步骤照样拿 `fetch` 的**满分 20** 并被反复选中：

### 站位格只认游戏的「那 4 个正方向」（`NEKO_STAND_ORTHO`，2026-09-17）

「锅的定位 ①」的**根**（换边只是补救）。症状：厨师**站到了**煎锅旁边、也转身了，
游戏却说放置目标是**隔壁那张台面**：

```
[P2] ⚠ 站位不对: 游戏说会放到 'workstation_plate_return',
                而不是 'workstation_cooker_01 (4)' / 锅 'utensil_frying_pan_01 (1)'
```

**依据（反编译定案，规则 1）** —— 台面**只有一条路**能变成放置目标：

| 环节 | 出处 |
|---|---|
| `m_iHandlePlacement` 的来源：`ScanForObject` 从碰撞体数组里挑**一个**物体 | `PlayerControls.cs:763-768` |
| 台面是 **grid-owned**，会被弧线过滤**剔掉**，只能靠 `GetFacingGridOccupant` **塞回**数组 | `InteractWithItemHelper.cs:177-200` |
| 它的候选集就是**那 4 个正方向**（从**厨师所在格**数起） | `InteractWithItemHelper.cs:20-26` |
| 打分 = `dot(forward, 偏移)` 最大者胜（>135° 丢弃） | `InteractWithItemHelper.cs:85-96` |

⇒ 两条推论：
- 厨师站在**斜角**上时，目标台面落在偏移 `(±1,±1)` —— **那张表里没有**，
  游戏只能指向某个**正方向**上的邻居 ⇒ 就是日志里的 `workstation_plate_return`；
- `_stand_cell_of` 的候选里**包含厨师脚下那一格**（它只跳**目标**那格）⇒
  离厨师 0 格、距离一比较**必然夺冠** ⇒ "站过去"变成"原地别动"，
  而原地方向是斜的 ⇒ **必然判给隔壁**。

所以"换边能救回一些"（`_align_try_other_cells` 走 `max_di=1` 且**跳过脚下那格**），
而**第一次**的选择从来没走对过。

现在 `_stand_cell`（"站过去动手"的唯一入口）先按**那 4 个正方向**扫一遍，
扫到了就用它；**一格都扫不到**才退回老口径（±2 格 + 斜角）—— 是"先收紧、收不紧再退回"，
不是"一律收紧"，免得把"旁边站得下"变成"没有站位格"。

⚠ **只管"站过去动手"那一类**。`_stand_cell_of` 的直接调用方问的是另一件事
（"我走得到它旁边吗"），口径**本来就不一样**：传球是**抛掷**，射程比交互半径大，
所以 `pass` 的 Δ≤2 **是刻意留的**（`_splitkitchen_probe.py` §2/§3b 钉着这条）。
别把默认翻过来 —— 那会让传球线凭空变远一格。

**反面断言**：
```
[步骤] ↻ 换到 (7.2,7.2) 再问: 游戏仍说 … ✗   ← 换到了**斜角**上 ⇒ 说明这一档没生效
```
（正常应当是"换到的那几格，相对目标都在正方向上"。）

### 两个厨师别去挤同一格（`NEKO_CELL_RESERVE`，2026-09-17）

用户点名的 ②：**"看到两个厨师会去一个地方挤来挤去的"**。
实机证据（`s_balloon_2_3`）—— 两人 x 相同、z 只差一格，挤在同一张台面上。

⚠ **这是"物理上互相挡路"，不是"选了同一步"**（判据见 `_chef_in_cell` 那段：实机 P1
送餐必经的走廊上站着空转的 P2，推了 8 下没过）。所以修法不在评分层。

根因是**两条，都是"机制在、没人用"**：

- **`World.reserve()` 在全仓零调用者**。它和 `reserved_by_others` / `occupied_by_others`
  是一对现成 API（docstring 原话："用于**我要站这里，你别来**"），却从来没人说过那句话
  ⇒ `occupied_by_others` 只答得了"队友**现在**在哪"，答不了"他**要去**哪"。
  两个厨师**同时**从远处出发去同一张台面时，各自算出的站位格**是同一格**
  （选格口径只看"离我最近"）⇒ 顶在一起。
- **`_stand_cell` / `_stand_cell_of` 压根没有 `avoid` 参数**，而 `_stand_cells` 有。
  `_approach`（取/放）那条路守着避让纪律，而 **`navigate_smart` 的"目标格是障碍 ⇒
  挑个站位格"那一支没守** —— 那才是**去任何台面的主干道**（22 个调用点）。

现在：选定站位格时 `_reserve_cell()` **先说一声**再走过去；三处避让
（`_approach` / `_align_try_other_cells` / `navigate_smart`）**收成同一个口径**
`_avoid_cells`（= 队友站的格 + **他马上要去的格**）。

⚠ **只"优先避开"，不是禁行**：全被占了照常返回一个（同 `_stand_cells` 的纪律 ——
宁可挤一下，也别站着什么都不做）。
⚠☠ **绝不并进 `_dynamic_blocks`**（A* 的禁行集）：两个人在窄走廊上时那会把路
**彻底封死**（本仓被"多禁一格就无解"害过）。软避让 + 已有的
`_note_blocked`/`MATE_STUCK_MAX` 补救够了。

日志（**这就是验收指纹** —— 只有队友**真的改变了我的选择**时才打一行）：
```
[避让] 队友占着 (7.2,6.0) ⇒ 我改站 (6.0,7.2)
```

### 规划器也要知道「去哪拿一只盘子」（`NEKO_PLAN_PLATE`，2026-09-17）

`derive()` 的链里**压根没有「拿盘子」这一步** —— 执行层是在 `op_assemble` /
`_get_plate_for_pot` 里**顺手**解决的，来源有**三条**：

1. **摆盘位上已经有一只**（材料放上去直接进盘，最省事）；
2. `_empty_plate_source` —— 对得上订单容器类型的**盘子堆** / 台面上的**空盘**；
3. 手上那只（`_grab_parked_plate` 取回走开前放好的）。

规划器**一条都不知道**，后果两层：

- 计划说不出「摆盘位在哪」⇒ `assemble` 那几步**恒被标成**
  `探测期判不可行(还没挑摆盘位)` —— 那是一句**假理由**（不是"不可能"，是"没去问"）；
- **「盘子从哪来」这条约束根本没进计划** ⇒ 在「全场一只空盘都没有」的世界里，
  这份计划看起来照样成立，到执行期才一个接一个失败。

**根因**是 `_PlanView` 里那条自己写着的老注释：

> 「**不去调 `pick_assemble_spot`** —— 那个会写 `_board.pick_spot`，影子模式就不该碰
>  共享黑板。要让规划期也能判 `assemble`，**等真正接管时再说**。」

那个「等」到了（`NEKO_PLAN` 已默认 `on`），而担心的副作用**早就有只读档**：
`pick_assemble_spot(claim=False)` 是**评分层替队友算**用的，它不写 `_assemble_sid`、
不碰黑板（`_empty_plate_source` 也补了同一个 `claim` 参数）。

现在规划期把这三条**只读地**解析一遍，结果写进 `Plan.assumptions`，于是
`[规划]`（shadow 模式）里看得见：

```
⚠ 假设: 摆盘位 counter4 (规划期只读挑的)
⚠ 假设: 那只空盘**已经在** counter4 上(材料放上去直接进盘)
⚠ 假设: 空盘从 plates0 取(盘子堆)
⚠ 假设: ⚠ 全场**没有可用的空盘**(盘子堆 / 台面上的空盘都没有) —— 摆盘那一步要现找, 很可能做不成
```

☠ **「不知道」≠「没有」**：`WorldView.plate_known` 区分这两件事。老调用方
（手写 `WorldView` 的离线桩）拿到的是 `False` ⇒ **一句盘子的话都不说** —— 否则每份计划
都会多一条假的 `⚠`。这和 `Item.cook_steps` 那条「空列表 = 拿不到这件信息 ⇒ 退回老行为」
是同一个形状。

☠ **它只影响「计划怎么说」，不影响「计划怎么收窄」**：收窄闸门（`_plan_next_all`）匹配的是
`(槽位, action, target)` 三元组，**从不看坐标** ⇒ 把 `assemble` 那几步的目标坐标从"没有"
变成"有"，不会改任何候选的放行。

**反面断言**（看到就是坏了）：
```
⚠ 假设: ⚠ 全场**没有可用的空盘** …     ← 而台面上明明有盘子 ⇒ 说明解析走空了
```

### 计划的「假设」真的被校验了（`NEKO_PLAN_CHECK`，2026-09-17）

`Plan.assumptions` 的 docstring 从加字段那天起就写着：

> 「地图/世界更新时**只校验这些**（破了就局部修补），而不是整体重规划。」

**从来没有实现。** `assumptions` 只是一串**人话**（"货源 counter1 仍然存在且够得着"），
而一句散文没法校验。后果：世界变了（队友把背包摘了 / 那件东西被人捡走了 / 台面没了）
**没有任何人管** —— 计划照用 `PLAN_TTL`(20 秒)，而**冷板凳也是 20 秒**，最坏就是
"拿一份已经知道不行的计划试满 20 秒"，一局 150 秒里这是**七分之一**。
唯一的作废路径是"某一步**真的失败**"，那已经晚了。

现在：`planner.Assumption` 是**一个 `str` 子类** —— 它**就是**那行日志文本，另外挂着
`kind` / `key` / `slot` 三个标签。所以打印/排序/去重**逐字不变**（这才是"加法"），
而每轮能拿标签去**现场核**：

| `kind` | 核什么 |
|---|---|
| `src` / `wear` | 那件东西还在场上吗（台面 / 地上的料 / **背包单独一遍**） |
| `back` | 那个厨师还背着那个背包吗（`"厨师\|背包名"`） |
| `cooking` | 那口锅还在台账里吗 |
| `plate_spot` / `plate_src` | 那张台面还在吗 |
| `no_plate` | **永远算成立** —— 它说的是"一件坏事为真"，空盘出现了是**好消息** |

**局部修补**：`_plan_dirty(why, slots=…)` —— 破了的那几张单的步剔掉，**其余照常服务**。
☠ 但**空 `slot`（= 全局事实：摆盘位 / 正在煮的锅 / 全场有没有空盘）破了就整份作废** ——
那些事实不属于任何一张单，猜一张去剔是**错的**；全中（没有健康单剩下）也走老路。

日志：
```
[规划] ↻ 计划作废(这些假设不成立了: 货源 counter0 仍然存在且够得着) —— **只剔掉 1 张单(留 2 张)** —— 下一轮立刻重算, 这段时间走评分那条路
```

☠ **三条纪律**（探针都钉着）：
- **每轮都要跑** ⇒ 它放在 `_plan_tick` 的**节流之前**（十几次比较，不建视图、不跑 BFS）；
- **认不出就放行** —— 认不出的 `kind`、老调用方塞进来的纯 `str`、读不到的字段，一律**当它成立**；
- **校验器抛异常 ⇒ 当它成立** —— 一个坏判据不该把计划打成作废；
- **不改原对象** —— 黑板上那份是**两个厨师共用**的，就地改 `steps` 会连队友那份一起改，
  所以是 `dataclasses.replace` 造一份新的。

**反面断言**（看到就是坏了）：
```
[规划] ↻ 计划作废(这些假设不成立了: …) —— **整份**      ← 而破的那几条明明都带槽位键
```
（那是"局部"没生效；先看那几条假设的 `slot` 是不是真填了 —— 见 `Assumption` 的注释：
**漏填标签的后果是静默的**，那条假设只是永不报警。）

### 转身那条守卫的「信游戏」退路（`NEKO_FACE_TRUST_GAME`，2026-09-17）

```

所以它敢放在 `face` 这种高频调用的地方。

[P2] [接近] (2.7,-8.3) 距 1.98 格, 游戏说可作用: 抓取='DLC13_dispenser_crate_camping_new (5)' ✓
[P2] [步骤] 拿到的是 'Seaweed', 不是 'DLC13_Orange' → 放回去
```
三次重试**同一个位置同一个错** ⇒ `✗ 放弃` 整单。那一关 **7 个分发箱同名只差 `(N)`**，
而且**排成一列、间距正好一格**。

根因是 `_aim_ok` 的**两档判据自己没分信用等级**：

| 档 | 怎么对上的 | 可信吗 |
|---|---|---|
| ① 精确 | `nm == want`，**连实例号都一样** | ✅ 身份确定 |
| ② 宽松 | 走 `_name_is` 的兜底（子串/归一化） | ⚠️ **只该用于"名字认不准"** |

而"同一族台面排一排"时，② **会把隔壁那只也判成"就是它"** —— 厨师停在离目标
**1.98 格**（曼哈顿格距 2）的地方就报 ✓，按下去从隔壁掏出另一份料。

现在 ② 之后**再问两句话**，判据**来自游戏自己的交互几何**，不是我们编的阈值：

> `InteractWithItemHelper.IsColliderInArc`：到**碰撞体表面** < 1.0 格。
> 格子步长 1.2 ⇒ 站格心时**正交相邻**那格表面 ≈ 0.6（够得着）；
> 正交两格 = 2.4、斜角一格 = 1.7 ⇒ 表面 ≥ 1.1（**够不着**）。
> ⇒ "够得着" ⟺ **曼哈顿格距 ≤ 1**。

- **②-a 游戏报的那个物体**挨着我吗（名字在图上能认出同名台面时，取最近那只）；
- **②-b 我要去的那个台面**挨着我吗 —— 这一问是关键，实机那次就是"**我根本没走到它旁边**"。

两问都要，因为盲区不同：只问 ②-a 时，同族台面排一排里"报的那个"往往**确实**就在手边
（它就是隔壁），拦不住；只问 ②-b 时，名字没建模就无从问起。

```
[瞄准] ⚠ 游戏报的是 'DLC13_dispenser_crate_camping_new (2)' —— 名字**宽松档**对得上
       'DLC13_dispenser_crate_camping_new', 但它/我离要去的 (7.2,13.2) 够不着
       (多半是同族台面排一排) ⇒ 不算, 换个站位格再问
```

**换一个站位格**这件事**不用另写**：`_approach` 本来就是"候选站格逐个试"的循环，
② 判否 ⇒ 它自然去试下一个格（试不出来还有"就地微调"朝目标挪那一段兜底）。

⚠ **两处刻意不动**：
- **① 逐字相同的一律照认**（哪怕几何上讲不通）—— 那条路是实机跑熟的，
  精确到实例号时身份本来就是确定的。此时只**多打一行证词**（见下），不拦。
- **`km`/`tm` 不给 ⇒ ② 整段放行** ⇒ 老调用点一个都不用改，逐字退回老行为。

**要定案的另一半**（`handle_target`）：`pick` = `m_TheOriginalHandlePickup`（那个**物体**），
而 `Update_Carry` 用的是 `m_iHandlePickup`（那个**接口实例**）—— 两者**分开赋值**，
同族箱子排一列时可能落在**不同的那一只**上。插件一直有报这个字段（`pickh`），
但 Python 侧**从没读过**。现在 `_aim_ok` **两个名字都试**，并在 `[接近]` 那行里单独打出
`抓取处理=`（只在它和 `抓取` 不同时才出现）。指纹：

```
[接近] (2.7,-8.3) 距 1.98 格, 游戏说可作用: 抓取='…(5)'  抓取处理='…(3)' ✓(要的是 '…(1)')
[瞄准] ⚠ 游戏报的 '…(1)' **逐字就是它**, 可它不在我够得着的地方 —— 游戏自己的半径(表面<1.0)解释不了, 这条要留证据
```
上面的 `不是 ±` 那行就是**定案证据**：若它出现，说明"游戏说会作用到 X"与游戏自己的
几何自相矛盾 ⇒ 病在 `pick`/`pickh` 这一层，不在站位。

**反面断言**：`拿到的是 'X', 不是 'Y' → 放回去` **连着 3 次同一个位置** ⇒ 这道闸没生效
（查 `NEKO_AIM_AT` 是不是被设成 0 了，或者那一步 `want` 是空的 —— 短路在闸门之前）。

**反面断言**：`不转身` 与 `挪了 8 次` 成对出现、而且**没有** `信游戏, 这次照转`
⇒ 脚下那格地图说安全（即地图没在乱报）⇒ 那是**真的**水，去看别处。

## 两个容易踩的注意事项

**① `python -u` 不是可选的。**
`run_watch.py` 起子进程走的是**管道**，而 Python 对管道默认 8KB 块缓冲 ⇒ 日志会**攒着分批吐**，
看不到实时次序；更糟的是收尾走 `CTRL_BREAK_EVENT`，缓冲区里没吐出来的那部分**直接丢**。
`-u`（= `PYTHONUNBUFFERED=1`）关掉它。`run_watch.py` 拼子进程命令时**固定带 `-u`**。

**② "跑起来就不用管焦点了"只在两只都用手柄时成立。**
`runInBackground` 被打开的是**游戏**，而**键盘注入走 `SendInput`，只发给当前前台窗口**。
所以 `--input keys,virtual` 那种配置下，进对局之后**仍然必须保持前台** ——
否则走键盘的那只当场不动。⇒ 开 `NEKO_WATCH_KEEP_FOCUS=1`，或者跑的时候别切出去。

### 方向沿步数表走（`NEKO_NAV`，2026-09-17）

☠☠ **规划器用两把尺子，控制器只用一把** —— 这就是这一刀的全部理由：

| 谁 | 判"过不过得去"用 |
|---|---|
| 规划（`find_path` / `distances_from` / `_stand_cell*`） | `walkable`(**格子字符**) + `step_ok`(**相邻格高差 ≤ 0.65**) |
| `navigate()` 选方向 | 只有 `dir_for_step(dx,dz)` —— **朝目标的直线** |

而 `LevelInfo.cs:774` 自己写着："平台降下时格子仍是 `.`(能站)，**只有高度差出跨步上限(0.65)
才判不可走**" ⇒ 于是图表上"有地板但迈不过去"的那种格子，**规划器知道过不去、控制器不知道**
⇒ 一路硬顶 ⇒ `stuck` ⇒ 一格记一条禁行、每条 25 秒 ⇒ 整局钉在原地。

实测两关，两个不同的主因、**同一个洞**：

- `MovingPlatform4`：`可走160 / 平台35`，两个厨师的可达格都是 **59/160**；规划器早算出
  西北那半过不去（`fetch Bun 不可达(够不着)`），而 P1 整局钉在 `x=12.2`、P2 钉在 `x=14.2`，
  刷 `地图说能走, 人撞住了`。
- `s_moonfestival_1_2`：地形 A* 失败 ⇒ 掉到**对地形一无所知**的第三兜底 `plan_path`
  （拿台子列表当障碍）⇒ 它给的路点**穿过危险格**（`路径点 (12.0,1.2) 是危险格, 跳过`
  **连四行** —— 只有它给得出这种东西：`find_path` 只回可走格心、`_native_path_safe`
  有一个危险点就整条作废）⇒ 前向守卫把**整趟**判死 ⇒ 路点在整条走廊上挨个陪葬、厨师一步没动。

现在：**直线走得通就走直线（今天"精确到位"那套一个字不改），走不通才问步数表。**

```
[导航] ↪ 直线不通(挡墙/水/高差), **走步数表** (0.99,0.17) 还差 1.26 格 —— 每一步都是规划器认可的
[导航] ⚠ 直布不通, 而**步数表里没有我这一格**(被推到不可走区/目标在另一个连通块) —— 退回直线硬推
[导航] ⇄ 对照: 直线朝 (…), 步数表朝 (…)      ← 只有 `compare` 会打
```

- **步数表** = `distances_from(目标)`（`tm.ver` 变了自然重算，按 `(版本, 目标格)` 缓存）。
  它和规划器**同源**：危险格/空洞/物理阻挡(`x`)**天然不在表里**、高差超限的边**天然不在表里**
  ⇒ **表中每一步都是规划器认可的**。取步：8 邻格里挑 `step_ok` 通过、可走、非危险、步数更小
  的那格；斜向还要求**两条肩格可走**（不切墙角）。
- ⚠ **返回 `None` 就逐字退回老行为**，最常见的是**目标在另一个连通块**（`MovingPlatform4`
  实测 `我的可达格 59/160`）—— 那时本来就到不了，该由上层判"够不着"换目标，不是让控制器继续顶。
- ☠☠ **前向危险守卫照查，只是改查"转向方向"**。第一版把它整段跳过了，理由是"步数表给的步
  天然不踩危险格" —— **那个理由是错的**：步数表给的只是**下一格**，而厨师是**连续**移动
  （模拟量 + 风 + 击退 + 推挤），越过那一格之后就没人拦，表现就是用户报的
  **"一直寻路到空洞格导致死亡"**。

⚠ 本条**不解决**"目标在另一个连通块"（那要开桥，见下），也**不解决**"地图漏了会动的挡路物"
（那要靠 `placeh`/`step_ok` 之外的判据）。它只保证一件事：**控制器与规划器用同一套边模型。**

### 桥的触发条件：从「没有路点」改成「目标够不着」

`pilot_bridge`（`bridge_cells 算桥位 → 走到控制台进会话 → 开平台到桥位 → 退出 → 重取地形 →
重算可达`）本来就有了，但**只在"三条规划路全失败"(`if not pts:`)时才试**。

而**遥感关**里地图**根本看不见那台平台**（它不占格子）⇒ 地图**永远以为对岸连通** ⇒ `pts` 非空
⇒ **桥那条路一次都不会被敲**。实测 `MovingPlate4`：两个厨师的可达格都是 `59/160`、
每个货源都判 `够不着`、`[规划] 推不出解`，而日志里**没有** `地形 A* 无解` 那行、
也**没有**任何 `[搭桥]`/`[遥感]`。

现在改成问**"我到得了目标旁边吗"**：够不着 + 这关**有遥感控制台**（`_has_pilot_console`：
工位报 `pilots`/`session`）+ 不在开桥中 + 不在会话里 ⇒ **先开桥**。
`bridge_cells` 返回空（单格当桥救不了）时 `pilot_bridge` 立刻返回、只多一行日志 —— 所以
**对非遥感关几乎不要钱**。

```
[导航] ⚠ 目标 (…) **够不着**, 而这一关有遥感控制台 —— 先试**用平台搭桥**
[搭桥] 桥位候选 N 个(按离厨师近排序), 试前 3 个: …
[搭桥] `bridge_cells` 说单格当桥救不了 (目标 …)      ← 出现它 ⇒ 要挪**两格以上**, 是 `bridge_cells` 的口径问题
```

## 规划器的「接地分类」（`NEKO_PLAN_GROUND`，2026-09-17）

目标（用户原话）：**"完整语义的可行性规划"** —— 加新机制时 `planner.py` 一行不改，只把基元语义写对。

### 缺口

求解器**每一个分支**都过同一道闸门（`planner.py:_solve_have_inner`）：

```python
ok, why, _d = _ok(ctx, op, chef)      # `_ok` 就是注入的 `check`
if ok: return [...]
```

而 `check` 的 `ok` 原来是 `_cell is not None`（`engine.py` 的 `_plan_ctx`），
于是**两种完全不同的"不行"长得一模一样**：

| | 原来 | 该不该剪 |
|---|---|---|
| **动作本身不可能**（`_op_actionable` 说不） | 剪 | **该剪** |
| **规划期接不上地**（此刻解析不出货源/站位格） | 剪 | **不该剪**（接地是执行期每轮重解析的） |

后者被当成"这条支不存在" ⇒ **完备求解器不完备** ⇒ `[规划] … 推不出解`。

### ☠ 试错记录（别再走一遍）

第一版想用**两个布尔**（`action` / `grounded`）分档 —— `runtime\_planctx_probe.py` 第 ⑭ 节
**当场打回**：

```
✗ ★ 反面: **背包的主人自己取不了**(改前/改后都必须是 False —— 这条判据不能被修松)
```

根因：**跨人约束不是由 `_op_actionable` 执行的** —— "自己的背包自己取不了"是
`_fetch_source_live` 的 `exclude_back` 在**接地那一层**把货源排除掉，
⇒ 它**以"接不上地"的形式出现**，和"真的没有"长得一样。

### 现在：四类，只有一类剪

`_op_target_for_score` 的 11 个失败出口各自打标（`Engine._no_target`）：

| 类 | 出处（例） | 剪? |
|---|---|---|
| `no_source` **真的没有** | `无货源坐标(现场也没找到能出它的箱子/台面)`／`没有送餐口`／`这关没有搅拌台(放不进碗)`／`空操作`／`没有搅拌台` | **剪** ☠ 跨人约束从这儿进 |
| `far` **有货源但够不着** | `够不着: 计划货源@x,z, 也没有别的够得着的货源` | 不剪 |
| `busy` **工位都被占着** | `没有能用的切菜板(都被占着?)`／`没有能用的灶台` | 不剪 |
| `pending` **还没挑/还没解析出坐标** | `还没挑摆盘位`／`传球: 没解析到队友位置`／`{a}: 没解析到目标` | 不剪 |

收下的那三类给一个**悲观代价 `999.0`**：有真解得出来时**永远输给真解**，只有**全都**接不上地
时才轮到它 —— 既恢复完备性，又不扭曲偏好（代价只在"同一个目标的不同拿法"之间比）。

☠ **判不了归 `no_source`（剪）** —— 分类只用来**放宽**，归错只会退回老行为，不会把判据修松。
分类走**实例属性**（`_ground_kind`），**不改 `_op_target_for_score` 的返回形状** ——
它有 4 个调用点，而且 `runtime\_splitkitchen_probe.py` 里的桩**覆写**了它。

指纹（`planner` 那边`推不出解`时会逐条打 `[规划]   ⛔ …`）：
```
[规划]   ⛔ P1 取不到 X(无货源坐标(现场也没找到能出它的箱子/台面)): …   ← 真的没有(剪了)
[规划]   ⛔ P1 取不到 Y(crate3): 够不着: 计划货源@12.0,-6.0 …            ← 这一条现在会被收下
```

**验收**：`runtime\_planctx_probe.py` 第 ⑯ 节 13 条断言（正三 / 反二 / 动作闸门 / 回退档 / `cell` 非空那条老路）。
⚠ **实机未验**；离线 50/50 全过。

## 规划器的代价尺子：格 → 秒（`NEKO_PLAN_COST`，2026-09-17）

用户原话：**"先换尺子"** —— 目标是 **"相同时间最高分的路线"**
（上一句：*"两个厨师各做贪心未必是最优解"*）。

### 为什么必须换

`Step.cost` 原来是**走过的格数**（`_feasible` 报回的 `reach.get(cell)`）⇒
**切 7 刀、搅 10 秒、煮 12 秒全都不进代价**（它们的 cost 也只是"走到那个台面的格数"）
⇒ 规划器在"先做哪步 / 派给谁"上**根本看不见时间**。
而"两个厨师各做贪心未必最优"要解的**正是时间**。

### 尺子长什么样（`Engine._op_seconds`）

```
代价(秒) = 格数 × CELL_M(1.2) / RUN_SPEED(4.0)      ← 走路的秒数(两个都是**游戏事实**)
         + 这一步动作本身的服务时间
             chop → CHOP_SEC    mix → MIX_TIME    cook → COOK_SEC
```

⚠ **判据只有这一份**：`planner.py` **不 import 引擎**（它文件头写着的纪律），
它拿的就是注入的 `check` 报回来的**第三个值** —— 所以尺子天然落在引擎那一侧。

☠ **`CHOP_SEC` 还没标定**（默认 1.5）—— 日志里只给"需切 N 刀"，**没给节奏**，
所以不假装知道。标定口子 `NEKO_CHOP_SEC`；指纹：`[步骤] 需切 N 刀` 到下一行
`切好了` 之间的时间差（日志有时间戳）。

☠ **不含"等待"**：煮的 12 秒里人是走开去干别的（引擎本来就这么做，`KIND_DEFER`）——
把等待算进代价会**高估**一步的成本。真正该算的是"**占用这个厨师多久**"，
那是**第 2 刀（makespan）**的事。

### 影响面（很小）

`cost` 只进两个地方：`Plan.cost`（日志）和 `_plan_one` 挑 owner 的那一个 `min()`。
⇒ **行为变化 = 分工可能换人**。所以验收看**同一局的总分**（`status.json`/游戏星数），
不看"日志看起来聪明了"。

一键回退：`NEKO_PLAN_COST=cell`。

**离线**：`runtime\_planctx_probe.py` 第 ⑰ 节 9 条断言（走路算式 / 三种动作各加一份服务时间 /
走得越远越贵 / 老尺子看不见服务时间 / 回退档 / 不抛）。**回归 51/51**。**实机未验。**

### 派活看「并行」（`NEKO_PLAN_MAKESPAN`，2026-09-17）

用户原话：**"两个厨师各做贪心未必是最优解"**（上一刀已把尺子换成秒）。

`_plan_one` 挑 owner 的老口径是 `min(总代价)` —— 那是**串行求和**，**完全不管那个人手上
已经排了多少活** ⇒ 只要同一个人每一步都稍便宜一点，**整单就排给他，另一个闲着**。
实测症状（仓库里记过两次）：`★ 我(P2)下一步应为: (没有分给我的步)`。

新口径：派给谁之后，**两个厨师各自的总时间取最大**，取最小的那个 ——
就是调度里的 makespan（列表调度）。`_load` 是**实际已派**的（按 `steps` 里的 `Step.chef` 累加），
不是估的；`CHAIN_DEAD_PENALTY` 仍然有效（它加进那一步 ⇒ 那个人的 makespan 爆掉 ⇒ 落选）。

```
[规划]   Fish: 选 P1(并行后最长 0.3)      ← 默认
[规划]   Fish: 选 P1(该步代价 0.3)        ← NEKO_PLAN_MAKESPAN=0（老口径）
```

⚠ **判据仍然是注入的** —— makespan 只是**调度策略**，所以它敢待在 `planner.py` 里
（模块文件头那条"判据一律不在这儿"说的是可行性判据）。

⚠ **待补**：`runtime\_planctx_probe.py` 第 ⑱ 节现在钉的是**开关接线 + 日志措辞**，
**还没钉"真的把活分匀了"** —— 那要造一个"前两步先把某个人的 load 垫高"的两厨师世界
（≥3 个目标），现有脚手架里没有。
