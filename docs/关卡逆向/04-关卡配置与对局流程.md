## 1. 机制概览

这题有三层，混用必踩坑。**脚本要"进关卡 → 打局 → 开下一把"，必须同时理解这三层**：

### 1.1 三个平面

| 平面 | 载体 | 谁拥有它 | 关键入口 |
|---|---|---|---|
| **配置平面** | `LevelConfigBase`（`ScriptableObject` 资产，挂在 `SceneDirectoryData → SceneEntry → PerPlayerCountDirectoryEntry` 上） | 静态数据，关卡场景无关 | `GameUtils.GetLevelConfig()`（`GameUtils.cs:204-221`） |
| **场景平面** | Unity 关卡场景（tag = `GameController` 的根物体 + 其子 Manager 树 + 台面/厨师/网格） | 每个关卡一个场景 | `GameUtils.GetGameEnvironment()`（`GameUtils.cs:38-41`） |
| **流程平面** | `GameState` 枚举 + 双端 `FlowController` 状态机 | 主机（Server）权威，客户端镜像 | `GameUtils.GetFlowController()`（`GameUtils.cs:116-119`） |

`GameSession`（tag = `GameSession`，`GameUtils.cs:48-56`）是贯穿三层的"当前会话背包"：它持有 `Progress`（存档进度）、`LevelSettings.SceneDirectoryVarientEntry`（**当前关卡配置的唯一真相源**，`GameSession.cs:25-28`）、`TypeSettings`（`WorldMapScene` 名字，`GameSession.cs:16-22`）。

### 1.2 一局的生命周期（一句话版）

```
WorldMap 场景：货车 Avatar 站到关卡 Portal 上 → 按确认键
   → ServerWorldMapFlowController.OnSelectLevelPortal → LoadLevel()            (ServerWorldMapFlowController.cs:68-121)
   → ServerMessenger.LoadLevel(index, playerCount, LoadKitchen, RunKitchen)     (ServerWorldMapFlowController.cs:141)
   → 加载 "Loading" 场景（LoadingScreenFlow.LoadScene 的过渡）                   (LoadingScreenFlow.cs:83-107)
   → 关卡场景：ServerKitchenLoader 六连状态机 → GameState.RunKitchen
   → ServerFlowControllerBase.StartFlow() → RunLevelIntro                       (ServerFlowControllerBase.cs:49-52)
      · 客户端跑 LevelIntroFlowroutine（暂停游戏、Ready UI、GO UI）              (LevelIntroFlowroutine.cs:40-92)
      · 服务端 RunRound()：每帧 OnUpdateInRound，直到 HasFinished()             (ServerFlowControllerBase.cs:104-120)
      · HasFinished = 回合计时器到期（或 SkipToEnd）                            (ServerKitchenFlowControllerBase.cs:104-107)
   → GameState.RunLevelOutro → 客户端 ScoreScreenOutroFlowroutine（星级结算）    (ClientFlowControllerBase.cs:86-91)
   → 按键/超时 → 客户端上报 RanLevelOutro → 服务端 GetNextScene()                (ClientFlowControllerBase.cs:94-107)
   → 回 WorldMap（CampaignMap + RunMapUnfoldRoutine）或重玩本关
```

### 1.3 权威分工（关键）

- **服务端**决定：回合何时结束（计时器）、分数、连击、订单随机、下一场景（`GetNextScene`，`ServerCampaignFlowController.cs:155-186`）。
- **客户端**决定：结算画面什么时候结束（因为**按键在客户端**，`ScoreScreenOutroFlowroutine.cs:93-112`），然后通过 `ClientMessenger.GameState(GameState.RanLevelOutro)` 通知服务端推进（`ClientFlowControllerBase.cs:94-107`）。

> **这意味着**：单机（`!ConnectionStatus.IsInSession()`）时客户端和服务端在同一个进程里，按键照样走"客户端 → 消息 → 服务端"这条路。**不存在"服务端自己在 20 秒后自动开下一把"**——服务端必须收到 `RanLevelOutro` 才会换场景。

#### 2.1.8 出单算法（精确）

`RoundData.GetNextRecipe`（`RoundData.cs:26-40`）：
1. `RecipeCount++`
2. 用 `GetWeight(data, i)` 加权随机抽一个 `RecipeList.Entry`
3. `CumulativeFrequencies[抽中的下标]++`

权重（`RoundData.cs:35-40`）：
```
total   = Σ CumulativeFrequencies          // 历史已出次数总和
avg     = (total + 2) / recipeCount        // "平均每个菜应该出了几次"，+2 是平滑项
weight  = max(avg - CumulativeFrequencies[i], 0)
```
**语义**：出的越少的菜权重越高；一旦某菜出得超过平均值，权重归零 → **不会连续重复出同一个菜**。当所有菜都被"出平"时 sum(weight) 可能为 0，此时 `GetWeightedRandomElement` 的 `Random.Range(0f, 0f)` 返回 0，第一次循环 `num4 += 0`，`0 <= 0` 成立 → 返回下标 0（`ArrayUtils.cs:296-315`）。**这是个可预测的边界行为**（推断：等价于"权重全零时固定出第 0 个菜"）。

`BossRoundData` 覆写为**顺序出单**：`phase.Recipes.m_recipes[RecipeCount++]`（`BossRoundData.cs:33`）；该阶段出完返回空数组（`BossRoundData.cs:29-32`），调用方 `AddNewOrder` 循环 0 次 → 不刷单（`ServerOrderControllerBase.cs:120-127`）。

### 2.2 场景结构（专题要求 2）

#### 2.2.1 `GameUtils.GetGameEnvironment()` 到底是什么

```csharp
public static GameObject GetGameEnvironment()      // GameUtils.cs:38-41
{
    return GameObject.FindGameObjectWithTag("GameController");
}
public static GameObject GetGameMetaEnvironment()  // GameUtils.cs:43-46
{
    return GameObject.FindGameObjectWithTag("GameMetaEnvironment");
}
public static GameSession GetGameSession()         // GameUtils.cs:48-56
{
    GameObject go = GameObject.FindGameObjectWithTag("GameSession");
    return go != null ? go.RequireComponent<GameSession>() : null;
}
```

**结论**：`GetGameEnvironment()` = **tag 为 `GameController` 的那个根物体**。它是"关卡场景的 Manager 宿主"：
- 它（或其子物体）上挂 `ManagerDirectory`，`RequireManager<T>()` 就是在这棵树里按类型找 `Manager`（`ManagerDirectory.cs:23-38,45-58`）。
- `GameUtils.RequireManager<T>()` 会**先找 GameController，再找 GameMetaEnvironment**（`GameUtils.cs:137-161`）——所以持久 Manager（存档、音频、成就）在高层的 Meta 环境里，关卡 Manager 在 GameController 里。

#### 2.4.2 生成规则


**精确语义**：
1. **订单计时和刷单计时共用同一个 `num`** —— 只要**回合计时器被压制**（`IsSuppressed`）**或** `m_enableOrderExpiration == false`，`num == 0`，那么**订单永不超时、也永不刷新单**。
   回合计时器被压制的唯一来源就是 `m_recipesBeforeTimerStarts`（`ServerCampaignMode.cs:52-58` 添加 `Suppressor`，`ServerCampaignMode.cs:60-71` 交够单后 `Release()`）。
2. **保底 2 单**：`m_activeOrders.Count < 2` 时无视 `m_timerUntilOrder` 立刻再刷一单 → 开局瞬间会连出 2 单。
3. 满了（5 单）就停。

#### 2.4.4 交付匹配规则（"上错菜不扣分"的机制来源）

- 匹配失败 → `OnFoodDelivered` 走 `else` 分支 → **`OnFailedDelivery`**，只清 `TotalMultiplier/TotalCombo/ComboMaintained`（`ServerKitchenFlowControllerBase.cs:173-180`），**不扣分**。✅ 与用户已知一致。
- 多个匹配时按 **`Remaining` 最小**（最紧急）挑（`ArrayUtils.cs:240-258`，用严格小于 `<`，**并列时取列表里更靠前的**）。

```csharp
// ServerOrderControllerBase.cs:173-191
public bool IsComboOrder(OrderID _orderID, bool _restart)
{
    if (_restart)
    {
        var d = m_activeOrders.Find(o => o.ID == _orderID);
        if (d != null) { m_comboIndex = m_activeOrders.IndexOf(d);   // 记住这次交付在列表里的**下标**
                         return m_comboIndex == 0; }                  // 是第 0 个（最左边）才算连击
        return false;
    }
    if (m_comboIndex >= 0 && m_comboIndex < m_activeOrders.Count)

    return false;
}
```
**规则**：
1. 连击为 0 时，**只有交付订单栏最左边（下标 0）那一单**才开始连击，并把 `comboIndex` 记成 0。
2. 之后每交付一单，因为 `RemoveOrder` 会把那一项从 `m_activeOrders` 移除、后面整体前移，而 `comboIndex` **不变**，所以：**只要每次都交最左边那一单，连击就一直续下去**（下标 0 永远有货）。
3. 一旦某次交的不是 `m_activeOrders[comboIndex]`，`o_wasCombo = false` → `TotalCombo = 0`、`TotalMultiplier = 0`、`ComboMaintained = false`（`ServerKitchenFlowControllerBase.cs:164-169`）。下一次交付因为 `TotalCombo == 0`，会重新 `restart`（只能从下标 0 重新起链）。

**订单栏"左起顺序"= `m_activeOrders` 的下标顺序**：
- 服务端 `AddNewOrder` 是 `List.Add`（追加到尾）（`ServerOrderControllerBase.cs:112-118`）。
- 客户端 `ClientOrderControllerBase.AddNewOrder` 也是追加（`ClientOrderControllerBase.cs:65-73`）。
- UI 布局按 `RecipeWidgetData.m_order`（一个自增计数器）从左往右排（`RecipeFlowGUI.cs:69-79,228-244`），而 `m_order` 就是加入顺序。
→ **"最左边的订单" == `m_activeOrders[0]` == 最早刷出来的那一单**。✅ 与用户已知一致。

#### 2.5.5 成功 vs 失败，流程有什么不同

| | 成功（≥1 星） | 失败（0 星） |
|---|---|---|

## 5. 对自动化的含义

### 5.1 【最重要】对局结束后按什么键能进入下一局

**按 `SPACE`。**

- 结算界面的"继续"按钮 = `LogicalButtonID.UISelect`（`ScoreScreenOutroFlowroutine.cs:41,99`），键盘上硬编码 `KeyCode.Space`（`PlayerInputLookup.cs:469-481`）。
- 但有两个前置门槛（`ScoreScreenOutroFlowroutine.cs:88-99`）：
  1. `m_starRatingController.HasAnimationSettled()` 必须为 true（星级动画播完，`StarRatingUIController.cs:42-47`）；
  2. `m_starRatingController.AllowedToSkip()` 必须为 true —— 这要求**当前没有任何 uGUI 焦点物体**（`CoopStarRatingUIController.cs:241-252`）。所以**如果脚本之前点过 UI，需要先按 `Escape` 清焦点**。
- **兜底：什么都别按，20 秒后也会自动回地图**（`m_fTimeout = 20f`，`ScoreScreenFlowroutineData.cs:23` + `CoroutineUtils.cs:25-31`）。
- 回地图后，货车停在本关节点上（`ServerMapAvatarControls.cs:71-95`）。**要开下一关，必须在地图上把车开到下一个节点再按 SPACE**——新关卡要按**两次**（第一次只"购买/解锁"，`ServerLevelPortalMapNode.cs:21-39`）。
- 想完全绕过地图：调 `ServerWorldMapFlowController.OnSelectLevelPortal(avatarControls, levelNode)`（`ServerWorldMapFlowController.cs:68-83`），或打开 `DebugManager` 的 `"Auto Load Levels"` 选项（`ServerMapAvatarControls.cs:137-140`）。

### 5.4 连击保命的脚本策略

要让 `TotalMultiplier` 冲到 4（小费 ×4）：
1. **永远只交付订单栏最左（`m_activeOrders[0]`）的那一单**（`ServerOrderControllerBase.cs:185-189`）。
2. 但交付时系统是**按"最紧急"挑单**的（`ServerOrderControllerBase.cs:163`）。→ **千万不要让多张订单同时匹配同一种菜**。控制手段：
   - 只做"当前最左订单"要的菜；
   - 或者，一旦发现最左订单不是最紧急的那单，**先故意让它超时**（超时只扣 10 分 + 清连击——不划算）；
   - 或者，在插件侧直接调 `ServerCampaignFlowController.SetOrdersAutoProgress(false)`（`ServerCampaignFlowController.cs:188-191`）**暂停刷单**，用手动 `AddNextOrder()` 控节奏 —— 但这会同时冻结"超时计时"（因为 `m_autoProgress` 只控制刷单，超时另算；**注意**：`Update()` 里超时扣减走的是 `num`，与 `m_autoProgress` 无关，所以关掉自动刷单不会停止超时）。
   - **最稳的做法**：把"交付时的匹配不确定性"降到 0 —— 保证任何时候只有一种可交付品能匹配到多于一单的概率极低。
3. 超时 / 交错误菜 / 任何一次非连击交付都会 `TotalCombo = 0, TotalMultiplier = 0`（`ServerKitchenFlowControllerBase.cs:120-123,164-169`）。失败代价仅仅是倍率清零，**丢分只有超时那 10 分/次**。
