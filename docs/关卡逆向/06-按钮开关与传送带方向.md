## 1. 机制概览

### 1.1 三套完全不同的"传送带"

项目里有**两套**名字里带 convey/travel 的运动机制，脚本千万不要混为一谈：

| 名称 | 组件 | 搬什么 | 是否占格 | 方向字段 |
|---|---|---|---|---|
| `ConveyorStation`（桌面传送带） | `ConveyorStation.cs:6`（要求 `TabletopConveyenceReceiver` + `StaticGridLocation` + `AttachStation`） | **物品**（一格一格传，物品站在台面上） | 是（`StaticGridLocation`，`StaticGridLocation.cs:24`） | `m_conveyanceDirectionXZ`（**public**，`ConveyorStation.cs:18`） |
| `Travelator`（扶梯/自动步道） | `Travelator.cs:3`，实现 `IMovingSurface` | **厨师**（改变踩在上面的人的移动速度） | 是（tag `"Travelator"`，`InteractWithItemHelper.cs:46`） | `m_directionXZ`（**private**，`Travelator.cs:15`） |

两者都由"方向枚举 + 朝向"共同决定方向，但语义相反（见 §2.3、§2.4）。**"按钮改变传送带方向"最可能说的是 `ConveyorStation`**（因为方向切换 = 物品流往哪边），但两者都要能读，脚本才能兜底。

另外 `SwitchMapNode` / `WorldMapSwitch` 是世界地图（Campaign 大地图）上的东西，与厨房内的 `SwitchStation` **没有任何关系**（见 §2.7）。

### 1.2 按钮/开关"是什么"：全部是 marker + 预制体连线

代码里**不存在** `Switch` / `ToggleSwitch` / `PressureSwitch` 这三个 MonoBehaviour 类。实际存在的只有：

- `SwitchStation.cs:4`：`[RequireComponent(typeof(Interactable), typeof(AttachStation))] public class SwitchStation : MonoBehaviour {}` —— **空类，只有两个 RequireComponent**，本身零逻辑。
- `SwitchCosmeticDecisions.cs:4` / `ToggleSwitchCosmeticDecisions.cs:4` / `PressureSwitchCosmeticDecisions.cs:4` —— 三个**纯视觉**组件（材质/Animator 参数/按钮下沉位移），也不含任何逻辑。

**所以"开关做什么"完全由 prefab 上的如下三类组件决定：**

1. `Interactable`（触发字符串，`Interactable.cs:6-19`）
2. `TriggerZone`（压力板的占据检测，`TriggerZone.cs:6-13`）
3. 转发类（`TriggerOnObject` / `TriggerToggleOnAnimator` / `TriggerAnimatorSetVariable` …）

### 1.3 `SwitchStation` 是台面吗？

**是，但玩家不能往上放东西。**
- 它强制要求 `AttachStation`（`SwitchStation.cs:3`，`AttachStation.cs:6`），所以从数据模型上它是一个**可以承载物品的台面**：传送带可以把物品送到它上面（`ServerConveyorStation` 的目标就是 `IConveyenceReceiver`，`ServerConveyorStation.cs:226-235`）。
- 但 `ServerSwitchStation.AllowItemPlacement` 明确返回 `_context.m_source != PlacementContext.Source.Player`（`ServerSwitchStation.cs:39-42`，客户端同 `ClientSwitchStation.cs:39-42`），配合 `PlacementContext.Source` 只有 `Game` / `Player` 两个值（`PlacementContext.cs:3-12`）→ **玩家手动放置被拒绝，只有"Game"来源（传送带/机械）能放。**
- **一旦台面上有东西，`Interactable` 被强制禁用**：`ServerSwitchStation.cs:23-29`（`OnItemAdded` → `m_interactable.enabled = false`）与 `ServerSwitchStation.cs:31-37`（`OnItemRemoved` → `enabled = true`），客户端镜像同逻辑（`ClientSwitchStation.cs:23-37`）。

> 这条对自动化是**致命细节**：传送带把物品送到开关台上 → 按钮变灰按不动 → 直到物品被拿走。见 §5.3。

### 1.4 三种开关各自"怎么被激活"

| 类型 | 激活方式 | 键盘能按吗 | 依据 |
|---|---|---|---|
| `SwitchStation` + `SwitchCosmeticDecisions`（"普通开关"） | **玩家按交互键**（瞬时按下 → 触发 `m_onInteractImpulseTrigger`）；也支持按住/松开（`m_onInteractStartedTrigger` / `m_onInteractEndedTrigger`） | ✅ 能（默认左 Ctrl） | `ServerInteractable.cs:84-111`、`ClientPlayerControlsImpl_Default.cs:279-282` |
| `ToggleSwitch`（`ToggleSwitchCosmeticDecisions`，`ToggleSwitchCosmeticDecisions.cs:3`）+ `Interactable` + `TriggerToggleOnAnimator` | 同样是**按交互键**，但效果是**翻转一个 Animator bool**（状态持久、服务器权威、有同步消息） | ✅ 能 | `ServerTriggerToggleOnAnimator.cs:22-29`、`ClientTriggerToggleOnAnimator.cs:38-51`、`TriggerToggleOnAnimatorMessage.cs:6` |
| `PressureSwitch`（`PressureSwitchCosmeticDecisions.cs:3`，要求 `TriggerZone`） | **有 Collider 进入/离开触发区**：厨师踩上去或物品被放上去 → `m_onOccupationTrigger`；离开 → `m_onDeoccupationTrigger`。**不需要按键** | ❌ 不需要按（走过去/放东西即可） | `ServerTriggerZone.cs:51-67`、`TriggerZone.cs:6-13` |

注意 `SwitchCosmeticDecisions` 的"亮/灭"其实就是 `Interactable.enabled` 的镜像（`ClientSwitchCosmeticDecisions.cs:21-48`，还附带 `SwitchOn`/`SwitchOff` 音效），所以它是**瞬时/可用性**状态；而 `ToggleSwitch` 是**持久 toggle** 状态（`ClientToggleSwitchCosmeticDecisions.cs:30-50` 读 `ClientTriggerToggleOnAnimator.CurrentState` → `Animator.GetBool(m_targetParameterHash)`，参数名默认 `"On"`，`ToggleSwitchCosmeticDecisions.cs:12`）——这两者的"开关状态怎么读"完全不同。

### 2.7 `SwitchMapNode` / `WorldMapSwitch`（一句话）

**是世界地图（Campaign 大地图）上的"关卡开关/翻转节点"，与厨房内的 `SwitchStation` 毫无关系**：`SwitchMapNode.cs:3` 继承 `MapNode`，`SwitchMapNode.cs:21-25` 用 `GameProgress.GetSwitchState(...)` 判断"是否已被按下"，`SwitchMapNode.cs:45-48` `CanProcessSwitch` = 还没被按下；`WorldMapSwitch.cs:4` 要求 `WorldMapFlipperBase`，`WorldMapSwitch.cs:31-39` 查询 `CanBePressed()` / `IsSwitchActivated()`。二者都是世界地图场景实体（`MultiplayerController.cs:520-521` 注册同步器）。**不展开。**

## 5. 对自动化的含义（重点）

### 5.1 按钮"能不能用键盘按"——**能**，但有三条硬约束

**结论：能用键盘按，默认键是左 Ctrl（LeftCtrl）；但必须满足"空手 + 站对位置 + 开关台面是空的"三条。**

1. **按键就能按**：`WorkstationInteract` 走的是普通键盘按键枚举（`PlayerInputLookup.cs:16,385-396` → `AmbiControlsMappingData.cs:43-48` → `ControlPadInput.Button.X` → 默认 `Key.LeftControl`，`PCPadInputProvider.cs:92`）。每次是 **JustPressed 边沿**（`PlayerControls.cs:107-110`、`ClientPlayerControlsImpl_Default.cs:279-282`）→ 脚本必须"按下再松开"，长按只会触发一次。
   - 项目担心"只能用移动键 + 一个交互键"：**交互键和抓取键是两个不同的键**（Ctrl vs Space），如果脚本只有一个可发送的键，请把它绑到 **Ctrl**（交互），因为开关走的是 `WorkstationInteract`。
   - 【未验证】若某关卡的开关把 `m_usePlacementButton` 设成了 true（`Interactable.cs:18-19`），则要用抓取键（Space）。稳妥做法：**两个键都轻敲一次**。
2. **必须空手**：`PlayerControls.cs:746-758` —— 手上有物品时 `m_interactable` 会被手持物的 `ClientUsableItem` 覆盖，否则直接被置为 `null`。**拿着东西按交互键，按不到开关。** 所以脚本流程必须先确认手上为空（可以先放到任意台面或用抓取键放下）。
3. **开关台面上不能有东西**：台面被占 → `Interactable.enabled = false`（`ServerSwitchStation.cs:23-29`），而扫描要求 `val.enabled`（`InteractWithItemHelper.cs:257`）→ 选不中、按键无效。**如果这个开关正好是传送带的收货台，就会陷入"传送带把货送来 → 按钮锁死"的循环。**
4. 额外门槛：`CanButtonBePressed()` 要求游戏窗口有焦点（`PlayerControls.cs:455-458`）→ Python 用 SendInput 时必须保证游戏窗口在前台，且没有打开菜单/对话框（`PlayerControls.cs:463-466`）。

**站哪、朝哪**：半径 1.0、朝向前方 180° 半圆（`PlayerControls.cs:745`）。实践上就是"站在开关的那一格或紧邻格，用移动方向把自己转向开关"。脚本可以在按键前先读 `PlayerControls.CurrentInteractionObjects.m_interactable`（`PlayerControls.cs:394`、`:157` public 字段）自检：**只有它非空且组件属于目标开关时再按**，否则先微调走位——这比盲按可靠得多。

### 5.3 按键是否有效、按几次、有没有冷却

- **按几次**：**不知道，且不应该假设。** 取决于 prefab 挂的是哪一类转发：
  - 若挂 `TriggerAnimatorSetVariable`（"设值"语义，`TriggerAnimatorSetVariable.cs:17-32`）：每次按下 = 播放一次换向动画 → **按 1 次换 1 次**。
  - 若挂 `TriggerToggleOnAnimator`（"翻转"语义，`ServerTriggerToggleOnAnimator.cs:22-29`）：每次按下 = 翻转一次 bool → **按 1 次翻 1 次**，但状态是持久 toggle。
  - 也可能一次按下触发整条传送带链一起换向（一个 `TriggerOnObject` 指向多个 `m_targetObjects`，`ServerTriggerOnObject.cs:24-30`）。
  → **正确做法：按下 1 次后轮询**（方案 A 的 `GetNextGridIndex()`），方向变了就停；没变再按 1 次。设置一个最多 2~3 次的上限，避免死循环。**千万不要用"按 N 次到达某方向"的开环逻辑。**

- **冷却/一次性**：
  - 代码层**没有冷却机制**：`ServerInteractable.TriggerInteract` 无任何限流（`ServerInteractable.cs:84-91`）。有 `TriggerWithCooldown` 这个组件（`MultiplayerController.cs:555` 注册），但**没有任何证据它挂在开关上【未验证】**。
  - **真正的节流点**是传送带动画：`TriggerAnimationOnConveyor.m_stopWhileAnimating = true`（`TriggerAnimationOnConveyor.cs:25-26`）→ 动画期间禁止搬运（`ServerTriggerAnimationOnConveyor.cs:48-51`），并且 `Pending → Animating` 要等"当前没有物品在传/在收"（`ServerTriggerAnimationOnConveyor.cs:73`）。
    ⇒ **如果传送带上正有物品在移动，按下的换向请求会排队，等物品送到才播动画。** 脚本按键后应"等待 + 轮询方向"，而不是立刻读一次判定失败。
  - **一次性陷阱**：`SwitchStation` 台面被物品占用时按钮直接失效（§5.1 第 3 条）。如果该开关是传送带的收货台，必须先把货拿走。

### 5.4 如果键盘按不动，替代策略

按可靠性从高到低：

1. **【推荐，最稳】绕开按钮**：把传送带当"固定方向的加速带"用。先在关卡开始时读一次方向（§5.2 方案 A），然后在路径规划里**顺着**这个方向用它；方向不合用就走地面绕行。传送带占格（`StaticGridLocation.cs:24`），而 `GridNavSpace` 的可行走图是 `GetGridOccupant(...) == null`（`GridNavSpace.cs:44-56`，且**只在 Start 时算一次快照**，`GridNavSpace.cs:53`）→ **传送带格对 A\* 是"不可通行"**，所以"绕开"在寻路层是天然生效的。
2. **等它自己转回来**：若关卡用 `TriggerTimer`（`TriggerTimer.cs:7` 有 `m_startTrigger`，`ServerTriggerTimer.cs:60`）或 `TriggerCounter` / `MultiPlayerController.cs:461-463` 之类做周期性触发，方向会定时自动翻转。脚本只需**读方向 + 等待**，不按任何键。**【未验证】具体关卡是否用了这种定时器。**
3. **改走压力板**：如果现场有 `PressureSwitchCosmeticDecisions`（`PressureSwitchCosmeticDecisions.cs:3` 要求 `TriggerZone`），那**根本不需要按键**——走过去踩一下或把物品放上去即可换向（`ServerTriggerZone.cs:51-67`）。**这是最适合纯键盘自动化的开关类型，代价最小。** 脚本应优先寻找压力板而不是按钮。
4. **【越过键盘，直接走 C# 路径】**（属于"改游戏状态"，非只读分析，仅作为策略记录，风险自负）：
   - 触发同一条换向链路：对传送带 GameObject 调 `SendTrigger(triggerAnimationOnConveyor.m_startTrigger)`（`GameObjectUtils.cs:423`、`TriggerAnimationOnConveyor.cs:56-59`），等价于按钮按下后的转发结果；
   - 或直接 `animator.SetTrigger("Animate")`（客户端侧就是这么做的，`ClientTriggerAnimationOnConveyor.cs:31`）；
   - 或直接改 `ConveyorStation.m_conveyanceDirectionXZ`（public）+ 调 `ServerConveyorStation.UpdateAdjacentReceiver()`（public，`ServerConveyorStation.cs:142-148`）让邻居立刻重算，并补发一次 `SendTrigger("AnimationFinished")` 让 `TriggerAnimationOnConveyor` 状态回到 `Idle`（否则它会一直以为自己还在动画、持续禁止搬运，`ServerTriggerAnimationOnConveyor.cs:48-51`）。
   - **风险**：这样绕过 Animator，视觉朝向可能与逻辑方向不一致（`GetNextGridIndex` 同时用 `transform.right` 和枚举，`ServerConveyorStation.cs:237-247`），也可能与联机对手不同步。

2. **【未验证】"改变方向"的具体实现形式**：是
   (a) 动画 clip 旋转 `transform` 180°？还是
   (b) 动画 clip 直接 key `ConveyorStation.m_conveyanceDirectionXZ`（Unity 可以动画 public 序列化字段）？还是
   (c) 两者都有、或配合 `TriggerAnimatorSetVariable` 改 Animator 状态？
   证据倾向 (a) 或 (b) 都可行且 (a) 足以单独完成反转（因为 `GetNextGridIndex` 里 `transform.right` 与枚举是相乘关系，`ServerConveyorStation.cs:237-247`）。**注意：不管是 (a) 还是 (b)，§5.2 的方案 A/B 都能正确读到新方向**，所以脚本不受此未知项影响。
   → 另一个佐证：全仓库**没有任何 C# 代码写过 `m_conveyanceDirectionXZ`**（仅 `ConveyorStation.cs:18` 声明、`ServerConveyorStation.cs:241` 读取），说明它的运行时变化只能来自动画/脚本外部。

3. **【未验证】`ClientTriggerZone.m_occupied` 从未被赋值**（`ClientTriggerZone.cs:8` 声明，全文件无写入；也没有重写 `ApplyServerEvent` 去消费 `TriggerZoneMessage`，而消息类型确实已注册于 `MultiplayerController.cs:114`）。
   若这不是反编译缺口而是真实行为，则 `ClientPressureSwitchCosmeticDecisions` 的材质/下沉表现（`ClientPressureSwitchCosmeticDecisions.cs:24-33`）会在客户端恒为"未占用"。
   → **对脚本的建议：一律读服务端的 `ServerTriggerZone.IsOccupied()`**（`ServerTriggerZone.cs:46-49`），不要信客户端那份。

4. **【未验证】具体关卡里开关是否把 `m_usePlacementButton` 设为 true**（决定要按 Ctrl 还是 Space，`Interactable.cs:18-19` + `ClientPlayerControlsImpl_Default.cs:259-262`）。建议脚本两个键都轻敲。

5. **【未验证】开关的转发是否经过冷却/一次性组件**（`TriggerWithCooldown` 等，`MultiplayerController.cs:555`），以及是否存在"按下后按钮永久失效"的关卡设计。

6. **【未验证】`Travelator` 的方向是否也会被开关/按钮改变。** `Travelator` 没有任何 Server/Client 同步器注册（`grep Travelator` 只有 `Travelator.cs` / `TravelatorCosmeticDecisions.cs` 两处命中，`MultiplayerController.cs` 里也没有登记），说明它的方向**是纯 prefab 静态配置**——这反过来支持"用户说的按钮换向指的是 `ConveyorStation`，不是 `Travelator`"这一判断。若确实需要运行时改变扶梯行为，只能改 `m_directionXZ`（反射）或直接 `enabled = false`（`Travelator.cs:136` 会让速度为 0）。

7. **【未验证】压力板/开关是否可能同时连接多条传送带**（`TriggerOnObject.m_targetObjects[]`，`ServerTriggerOnObject.cs:24-30`）——这会导致"按一次，多条一起换向"，脚本的方向轮询必须**针对每一条传送带分别判断**，不能用"某一条变了"代表全部就绪。
