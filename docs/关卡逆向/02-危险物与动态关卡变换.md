## 1. 机制概览

Overcooked! 2 的"危险物"和"地图运动"是**两套完全独立**的系统，但对自动化脚本来说它们有一个共同后果：**网格占用（grid occupancy）会在运行中改变，而原生寻路图 `GridNavSpace.m_nodeMap` 永远不会重建**。

- **危险物体系**：`HazardBase` 是一个空基类（`HazardBase.cs:3-5`），真正干活的是 `ServerHazardBase`，它**多实现了一个接口 `IHandleGridTransfer`**（`ServerHazardBase.cs:4`）。这就是"危险物是占用格"的机制来源：危险物自己占一格（靠 prefab 上的 `IGridLocation`，`ServerHazardBase.cs:16-17`），并且当别的东西要来占这一格时，`GridManager.OccupyGrid` 会回调 `HandleTransfer`，危险物借此把"被踩/被放东西"变成一次状态转移（`GridManager.cs:64-80`）。
- **火灾**：整个火灾系统有一个总开关——`LevelConfigBase.m_hazardInfo`（`LevelConfigBase.cs:9`）里的 `FireConfigData`（`HazardInfo.cs:7`、`FireConfigData.cs:3-13`）。没有它，`ServerFlammable.CanCatchFire()` 恒为 false（`ServerFlammable.cs:236-239`），`ServerCookingStation` 也永远不会点燃台面（`ServerCookingStation.cs:195`）。也就是说：**同一个"锅烧糊"逻辑，在配了 FireConfigData 的关卡会引燃台面，在没配的关卡什么都不会发生。**
- **动态变换**：`DynamicFlowController.m_transitions[]`（`DynamicFlowController.cs:5-6`）是一组 GameObject，服务端按"阶段（phase）"推进时给客户端发 `DynamicLevelMessage`（`ServerDynamicFlowController.cs:22-26`、`:46-52`），客户端把第 `phase-1` 个 transition 对象 `SetActive(true)` 然后跑它的协程（`ClientDynamicFlowController.cs:58-72`）。变换的核心后果是：**台面（计数器/木筏/潮水淹没区）的 Transform 会动、里面的物品会被销毁或重生、部分网格占用会失效**，而玩家基本**不会被强制传送**（唯一例外见 §3.5）。
- **对脚本最致命的一条**：`GridNavSpace.Start()` 只在场景开始时把占用状况烘焙进 `m_nodeMap`（`GridNavSpace.cs:44-56`），之后**从不刷新**。变换之后原生 `FindPath` 用的还是旧地图。这既是坑，也是我们必须自己维护 `LevelInfo` 那张网格图的根本理由。

### 2.2 可燃物体系（Flammable）

`Flammable`（`Flammable.cs:3-26`）字段：

| 字段 | 行 | 默认/含义 |
|---|---|---|
| `m_fireEffectPrefab` | `:7` | 火焰特效 |
| `m_progressUIPrefab` | `:10` | 火焰进度条 |
| `m_fireSpreadRadius` | `:13` | **1.5**（世界单位，用于扩散判定） |
| `m_overrideTargetFlammability` / `m_overrideTargetFlammabilityTime` | `:16,19` | 强制覆盖被点燃者的点燃耗时 |

`Flammable` 上有 `[ExecutionDependency(typeof(IFlowController))]`（`Flammable.cs:3`）——意味着它依赖关卡流程控制器先启动。

`ServerFlammable`（`ServerFlammable.cs:6-477`）核心状态：

- `m_immolatedComponents`（`:39`，在 `Awake` `:189-194` 组装）= 同 GameObject 上的 `Interactable` / `PickupItemSpawner` / `Workstation` 三个组件。**着火时这三个被 `enabled = false`**（`:214-224`），熄灭时恢复。→ 这是"着火的台面不能操作"的实现方式（同时对玩家和脚本成立，见 §5）。
- `m_fireStrength`（`:41`，`Mathf.Clamp01`，`:329-332`）。`1.0` 就是"烧起来"的阈值（`:344-347`）。
- `m_fireEncouragedBy`（`:43`）+ `m_prevProximateFlammables` / `m_currProximateFlammables`（`:45-47`，**长度固定 8**），对应"3×3 去中心"的邻域。
- `m_encourageSupressedTimer` / `m_cooldownSupressedTimer`（`:49-51`）。
- `m_canCatchFire`（`:53`，`SetCanCatchFire` `:226-229`）。
- `s_objectsOnFire` 静态表（`:35`，`GetAllOnFire()` `:172-175`）——**这是脚本最容易挂上去的钩子**：全场景着火物的列表。
- `OnObjectsOnFireChanged` 静态事件（`:65-75`）。

`ServerFlammable.UpdateSynchronising()`（`:351-430`）逐段：

1. `m_startOnFire` 处理（`:353-360`）：出生即燃，然后清零该标志。
2. 若"没有任何着火物"且无待同步更新则直接返回（`:361-364`）——**性能捷径**。
3. 扩散（`:372-403`）：交换 prev/curr 邻域数组，调 `GetProximateFlammables`；对每个邻域可燃物：
   - 新旧不同 → 新进入者 `StartEncourageFire(this)`，离开者 `StopEncourageFire(this)`（`:382-392`）
   - 相同且非空 → `EncourageFire(this)`（`:393-396`）刷新一次
4. 自身未满 1 时按 `Recover` 速度回涨（`:398-402`）。
5. 若**不在烧**且 strength>0 → 按 `1/CooldownTime` 衰减（`:404-407`）。
6. 计时器递减（`:408-415`）。⚠️ `:414` 写的是 `m_cooldownSupressedTimer = m_encourageSupressedTimer - deltaTime;`（疑似原版 bug：把 cooldown 计时器赋成 encourage 计时器减 dt）。照抄不影响我们，但说明"冷却可能在特定序列下不按预期衰减"。
7. 速度总量变化 → 同步给客户端（`:416-425`），随后把 Encourage/Fight/Recover 三个速度槽清零（`:426-428`）。

**点火 / 加火 / 灭火三个入口**：

- `Ignite()`（`:241-258`）：`CanCatchFire() && !OnFire()` → `SetClampedFireStrength(1)`、禁用 immolated 组件、加入 `s_objectsOnFire`、回调 `m_ignitionCallbacks(true)`、`m_onFire = true`。
- `FightFire(timeToExtinguish, deltaTime, player=false)`（`:280-293`）：每帧 `fireStrength -= (1/timeToExtinguish) * deltaTime`；`strength == 0` 时 `_Extinguish(false, player)`。**同时把 `m_encourageSupressedTimer` 顶成 `EncouragementSupressedTime`**（`:287`）——即"正在被灭火时，火势涨不回来"。
- `Extinguish()` / `_Extinguish(shutdown, player)`（`:295-327`）：恢复 immolated 组件、移出 `s_objectsOnFire`、回调 `m_ignitionCallbacks(false)`、断开与所有邻域可燃物的 encourage 关系、清三个速度槽。
- `CalculateFlammabilityTime`（`:432-442`）：若任一"煽火者"设了 `m_overrideTargetFlammability`，用它的 `m_overrideTargetFlammabilityTime`；否则用**被点燃者自己的** `FireConfigData.FlammabilityTime`。
- `GetProximateFlammables`（`:444-476`）：取自身格为中心 3×3 扫描，判定 `(自身位置 - 邻格中心).sqrMagnitude < m_fireSpreadRadius²`，再取该格占用物上的 `ServerFlammable`。
  **数值推演**：格距 1.2，默认半径 1.5 → 半径平方 2.25；正交通道 1.2² = 1.44 < 2.25 ✅；对角 √(1.2²+1.2²)=1.697，平方 2.88 > 2.25 ❌。
  → **默认参数下火只沿正交通道（上下左右）扩散，不走对角**。若某 prefab 把 `m_fireSpreadRadius` 调到 ≥1.697 就会连对角一起烧。
  另注意 `:470-473`：占用物是**自己**时那一格保持原值（不置 null，也不设成自己）——数组复用上的小瑕疵。

`ClientFlammable`（`ClientFlammable.cs:6-217`）：纯表现层。`ApplyServerEvent`（`:54-70`）按 `m_onFire` 起/灭火焰特效；`IsBurning` 的判定在客户端是 `m_fireEffect != null`（`:125-128`）。`Extinguish(..., playerExtinguished=true)` 且全场火灭时会记一次成就（`:185-192`）。

### 2.3 火灾的载体、生成器与触发器

**`FireHazard`**（`FireHazard.cs:3-12`）：`HazardBase` 子类，带 `[RequireComponent(typeof(Flammable))]` + `[RequireComponent(typeof(CapsuleCollider))]`（`:3-4`）。字段：`m_lifetime`（`:8`）、`m_destroyTime`（`:11`）。

**`ServerFireHazard`**（`ServerFireHazard.cs:3-65`）：

- `StartSynchronising`（`:11-17`）：拿同一 GameObject 上的 `FireHazard` 和 `ServerFlammable`，注册点火回调。
- `UpdateSynchronising`（`:19-37`）：**若 `m_lifetime > 0`，每帧对自己调 `FightFire(m_lifetime, dt)`**（`:25-28`）→ 火自己会按 `1/m_lifetime` 的速度烧尽（默认行为：一个火格自己烧 `m_lifetime` 秒后自动熄灭）。
  然后倒计时 `m_destroyTimer`，归零时 `NetworkUtils.DestroyObject`（`:29-36`）。
- `Conflagrate()`（`:39-43`）：`Ignite()` + 清空销毁计时器。**这是"让某个火格重新烧起来"的唯一入口。**
- `Shutdown()`（`:45-48`）：点火状态变 false 时（`:58-64`）设 `m_destroyTimer = m_destroyTime` → 火灭后 `m_destroyTime` 秒这个危险物对象被销毁。
- `HandleTransfer(index, object)`（`:50-56`）：**若来抢格子的是别人（不是 FireHazard），就 `Extinguish()`**。
  → **语义：往正在燃烧的格子里放/挪进另一个物体 = 把火扑灭**（这是脚本可用的灭火手段之一，前提是该格的火是一个独立的 `FireHazard` 对象；见 §3.3 路径 D）。

**`ClientFireHazard`**（`ClientFireHazard.cs:3-37`）：`Awake` 里把碰撞体关掉（`:19-23`），随点火状态开关碰撞体（`:25-31`）——纯客户端表现/碰撞。

**`FireHazardSpawner`**（`FireHazardSpawner.cs:3-13`）：`m_hazardPrefab`、`m_spawnTrigger`（字符串）、`m_alignToGrid = true`。

**`ServerFireHazardSpawner`**（`ServerFireHazardSpawner.cs:4-85`，`ITriggerReceiver`，`EntityType.FireHazardSpawner` `:16-19`）：

- `StartSynchronising`（`:21-28`）：取 GridManager、向上找 `Rigidbody`、把 prefab 注册为可同步生成物。
- `Burn()`（`:30-71`）逻辑：
  1. 用 Rigidbody 位置求格；取该格占用物（`:32-34`）。
  2. **如果占用物本身就是 `FireHazard`** → 对它 `Conflagrate()`（`:35-39，让已存在的火重新烧`）。
  3. **否则**：只有"该格为空 **或** 该格占用物是 `HazardBase`"才继续（`:42-45`）——即**不会往普通台面上叠一个火格**。
  4. 若设了 `m_targetTransform` → 通过 `IParentable.GetAttachPoint` 挂到目标上并同步（`:46-61`）；否则 `NetworkUtils.ServerSpawnPrefab`，并按 `m_alignToGrid` 对齐格心（`:63-69`）。
- `OnTrigger(string)`（`:78-84`）：`m_spawnTrigger == _message` 时 `Burn()`。

**`TriggerCreateHazard`**（`TriggerCreateHazard.cs:3-38`）：`CreateHazard` 只在"该格为空 **或** 该格占用物是 `HazardBase`"时实例化 hazard prefab 并对齐格心（`:14-29`）。`OnTrigger(string)` 在 `:31-37`。

> ⚠️ **接口缺口（重要）**：`TriggerCreateHazard : MonoBehaviour`（`:3`）**没有实现 `ITriggerReceiver`**，同样地 `TriggerIgniteArea : MonoBehaviour`（`TriggerIgniteArea.cs:4`）和 `TriggerCreateObject : MonoBehaviour`（`TriggerCreateObject.cs:5`）也没有。
> 而 `GameObjectUtils.SendTrigger`（`GameObjectUtils.cs:423-433`）用的是 `RequestInterfaces<ITriggerReceiver>()`——**只调用实现了接口的组件**。
> 所以这三个组件的 `private void OnTrigger(string)` 只能通过**另一条路径**被调用：`SendMessage("OnTrigger", ...)`。工程里确实存在这条路径：`SendTriggerToObject.cs:62`、`ForwardTriggerToTarget.cs:18`、`GameObjectUtils.cs:357/363`（发 `"destroyed"`）、`ServerSessionInteractable.cs:171/183`。

**`TriggerIgniteArea`**（`TriggerIgniteArea.cs:4-73`）：按半径 BFS 扫格，对每个格占用物上的 `ServerFlammable` 调 `Ignite()`（`:20-30`），半径判定用格子中心到自身位置的 sqrMagnitude（`:56-64`）。`OnTrigger` 在 `:12-18`。

**`EntityType`**（`Team17.Online.Multiplayer.Messaging\EntityType.cs`）里与本文相关：`SprayingUtensil`(`:7`)、`RespawnBehaviour`(`:9`)、`Flammable`(`:10`)、`PlayerSlip`(`:33`)、`RespawnCollider`(`:57`)、`FireHazardSpawner`(`:69`)、`TriggerMoveSpawn`(`:30`)、`TriggerZone`(`:27`)。
注意 **没有 `Hazard` 这个 EntityType**。`ServerFireHazard` 也没有覆写 `GetEntityType()`，所以它拿到的是基类默认值 `EntityType.Unknown`（`ServerSynchroniserBase.cs:19-22`）。换言之：**火本身不靠独立实体同步，火焰状态全靠 `EntityType.Flammable`（`ServerFlammable`）承载**——这也是 `ClientFireHazard` 只监听自己身上 `ClientFlammable` 的点火回调（`ClientFireHazard.cs:11-17,33-36`）的原因。

### 2.4 灭火体系

数据组件：

- `SprayingUtensil`（`SprayingUtensil.cs:3-30`）：`m_startSprayTrigger` / `m_stopSprayTrigger`（字符串）、`m_sprayAngleInDegrees = 15`（`:18`）、`m_sprayDistance = 4`（`:21`）、`m_CollisionLayerMask = -1`（`:27`）、**`public const float c_itemRadius = 0.6f`（`:29`）**。
- `FireExtinguishSpray : SprayingUtensil`（`FireExtinguishSpray.cs:3-7`）：`m_exinguishTime = 0.5f`。
- `WaterGunSpray : FireExtinguishSpray`（`WaterGunSpray.cs:3-10`）：`m_washSpeed`、`m_knockbackForce`。
- `ExtinguishCollider`（`ExtinguishCollider.cs:3-5`）/ `ClientExtinguishCollider`（`ClientExtinguishCollider.cs:3-5`）都是空标记组件。

服务端：

- `ServerSprayingUtensil`（`ServerSprayingUtensil.cs:5-145`，`ICarryNotified, ITriggerReceiver`）：
  - `StartSpray/StopSpray` 发 `SprayingUtensilMessage`（`:67-89`）；`OnTrigger` 匹配 `m_startSprayTrigger` / `m_stopSprayTrigger`（`:91-101`）。
  - `UpdateSprayDistance`（`:103-115`）：从 `m_effectAttachPoint` 朝前打 raycast，命中就**把射程缩短到命中距离**（即喷雾被墙挡住）。
  - **`IsInSpray(Transform)`（`:117-139`）：判定"目标是否在锥形喷雾里"**——以 **carrier（厨师）** 为原点、用 `carrier.transform.forward` 做朝向；距离平方 < `(sprayDistance + 0.6)²`（`:123`）；且 `dot(lhs, forward) ∈ (0, sprayDistance+0.6)`（`:126-127`）；再算半角 `sin(angle/2)` 得到一个横向半径 `num3`，判定 `(num3+0.6)² > |pos - 轴上投影点|²`（`:129-132`）。两处 `+0.6` 就是 `c_itemRadius` 的物化。
    → **默认 15° 半锥角 + 4 单位射程 + 0.6 物品半径**：一个站在厨师正前方 1~2 格（1.2~2.4 单位）的目标，只要横向偏移在约 0.6~0.9 单位内就会被浇到。地面上相邻格的横向偏移是 0 或 1.2 → **正前方的格子必然命中，斜前方的格子基本不会**。
  - `OnCarryEnded` 会把厨师的 `MovementScale` 复位为 1（`:58-65`）。
- `ServerFireExtinguishSpray : ServerSprayingUtensil`（`ServerFireExtinguishSpray.cs:4-58`）：
  - `OnCarryBegun`（`:14-22`）：**拿起灭火器的人自己 `SetCanCatchFire(false)`**（!），`OnCarryEnded` 恢复（`:24-35`）。→ **拿着灭火器的厨师不会着火。**
  - `UpdateSynchronising`（`:37-57`）：每帧遍历 `ServerFlammable.GetAllOnFire()`，凡 `IsInSpray` 的调 `FightFire(m_exinguishTime, dt, player: true)`。
- `ServerWaterGunSpray : ServerFireExtinguishSpray, IWindSource`（`ServerWaterGunSpray.cs:4-96`）：在父类灭火之外，还遍历 `ServerWashable.GetAllWashable()` 做清洗（`:72-80`），并遍历 `WindAccumulator.GetAllWindReceivers()` 做击退（`:82-90`）；`GetVelocity()` 返回 `transform.forward * m_knockbackForce`（`:92-95`）。
- `ServerExtinguishCollider`（`ServerExtinguishCollider.cs:3-43`）：进入碰撞/触发区 → `Extinguish()` + `SetCanCatchFire(false)`（`:5-13`）；离开 → 恢复可燃（`:15-22`）。**这是一个"区域型永久灭火器"**（例如喷淋区）。
- `ClientSprayingUtensil`（`ClientSprayingUtensil.cs:5-131`）：**`StartSpray` 里 `playerControls.SetMovementScale(0f)`（`:104`），`StopSpray` 复位为 1（`:126`）**。→ **喷的时候厨师原地定住不能移动**（但可以转向）。同时 `UpdateSynchronising` 在 `TimeManager.IsPaused` 时强制停喷（`:79-85`）。

### 2.5 滑倒体系（Splat）

- `SplatHazard : HazardBase`（`SplatHazard.cs:1-3`）——空标记，即"一摊东西"。
- `Splattable`（`Splattable.cs:3-17`）：`m_splatPrefab[]`、`m_alignToGrid = true`、`m_prefabIndex`。**`Awake()` 里 `Object.Destroy(this)`（`:13-16`）**——这个数据组件"用完即删"，所以运行时**不能再靠 `FindObjectsOfType<Splattable>()` 找它**。
- `ServerSplattable`（`ServerSplattable.cs:4-53`）：`Awake`（`:14-23`）里随机 `m_prefabIndex = Random.Range(0, len-1)`（`:21`，注意上界是 `len-1`，**最后一个 prefab 实际取不到**），并注册"可抛掷物落地"回调。
  - `OnThrowableLanded`（`:46-52`）：落地点层的 layer 在 `"Ground"` 掩码里（`m_landscapeMask = 1 << LayerMask.NameToLayer("Ground")`，`:18`）才 `Splat()`。
  - `Splat()`（`:29-44`）：目标格为空**或**占用物是 `HazardBase` 时，在（可选对齐格心的）位置生成 splat prefab，并**给自己加一个 `StaticGridLocation`**（`:37`）——**关键：溅出的 splat 会变成该格的占用物**。最后销毁自己。
    → **结论：扔出的东西砸到地面 → 生成一个 `SplatHazard` 并占据那一格。这对脚本意味着"地面上的杂物 = 网格障碍 + 滑倒陷阱"。**
- `SlipCollider`（`SlipCollider.cs:3-11`）：`m_slipFilter = -1`、**`m_deleteOnSlip = true`**。
- `ServerSlipCollider`（`ServerSlipCollider.cs:5-66`）：碰撞/触发进入且 layer 通过掩码且未记录过 → `Slip(obj)`（`:30-37`）；`Slip` 里对有 `ServerPlayerSlipBehaviour` 的对象调 `Slip(this)`（`:17-28`）；`m_deleteOnSlip` 时**销毁自己（splat 消失）**（`:24-27`）。
- `PlayerSlipBehaviour`（`PlayerSlipBehaviour.cs:5-36`）：`m_fallTime = 0.38`、`m_standTime = 0.42`、`m_downTime`（无默认值，prefab 决定）、`m_impactTrigger = "FallImpact"`。
- `ServerPlayerSlipBehaviour`（`ServerPlayerSlipBehaviour.cs:5-75`）：`Slip()` → 协程依次 "滑倒(Slip)" → 等 `m_fallTime` → 等 `m_downTime` → "站起(Stand)" → 等 `m_standTime` → "结束(Finished)"（`:30-55`）。期间 `DisablePlayer`：**Rigidbody 速度清零并设 kinematic、Collider 关掉、`PlayerControls.enabled = false`**（`:57-65`），结束后恢复（`:67-74`）。
  → **踩到 splat 的厨师会有 `0.38 + m_downTime + 0.42` 秒完全无法操作**（`m_downTime` 未知，未验证）。这对双猫自动化是必须检测的状态。

### 2.6 危险物对"厨师 / 物品"分别做什么

- **`ITriggerReceiver` / `SendTrigger` 路由**（`GameObjectUtils.cs:423-433`）：触发字符串是整个关卡动态的"事件总线"。可被 `SendTrigger` 命中的危险/变换相关接收者：

  → **未验证但风险明确**：被"动画带走"的台面若靠 active 状态切换，可能留下幽灵占用格。

## 3. 运行时流程（时序）

### 3.1 "锅烧糊 → 台面起火"完整时序

前置条件（**两个硬开关**）：
1. `LevelConfigBase.m_hazardInfo != null` 且 `.FireConfigData != null`（`ServerCookingStation.cs:195`）
2. 该烹饪台自身 GameObject 上有 `ServerFlammable`（`ServerCookingStation.cs:61`，null 时 `:198` 会跳过 Ignite，且 `CanCook` 的 `:143` 也跳过）

时序：

```
N-frames: 锅放在灶上, m_itemPot != null, CanCook()==true → SetCookerOn(true) (ServerCookingStation.cs:141-188)
          UpdateSynchronising: m_isTurnedOn && m_itemPot → m_itemPot.Cook(speed*dt)   (:192-194)
          Cook() 仅在 !IsBurning() 时才推进进度 (ServerCookingHandler.cs:107-115)
frame K:  进度 p 满足 p < 2T, p + dt > 2T
          Cook() 返回 true(本帧仍推进), 随后 IsBurning() 立刻变 true (进度>2T)
          → 条件 (m_isCooking && ... && m_itemPot.IsBurning()) 成立
          → SetCookerOn(false) + m_flammable.Ignite()                    (:195-202)
          ★ 注意 m_isCooking 是"上一帧"的状态, 正好在这一帧为 true, 所以点火是确定发生的, 不是竞态
Ignite(): 站点自身 fireStrength = 1
          同 GameObject 的 Interactable / PickupItemSpawner / Workstation 全部 enabled=false
          (ServerFlammable.cs:241-258, 189-194, 214-224)
          → 该台面在脚本看来"交互组件消失了"
之后每帧: ServerFlammable.UpdateSynchronising (:351-430)
          → GetProximateFlammables() 取上下左右 4 格 (默认半径 1.5 < 对角 1.697)
          → 对每个邻居 ServerFlammable: StartEncourageFire/EncourageFire
          → 邻居每秒 +1/FlammabilityTime(默认5) 的火势, 累到 1.0 时 Ignite() (OnFireIncrease :334-349)
```

**自动化的直接后果**：从锅开始烧糊起，**约 5 秒后相邻的正交台面也会着火**，再 5 秒后扩散到下一圈——**火会沿台面链式蔓延**。所以脚本检测到 `burning == true` 时，必须**立刻把锅拿走/丢弃**，而不是"再等一会儿"。

### 3.2 火势扩散的判定细节

- 扩散不是"按格"，而是**按格中心距离 + 该格占用物是否有 `ServerFlammable`**（`ServerFlammable.cs:444-476`）。
- 只有"占用物"能被烧：**空格不会烧，水/岩浆（`RespawnCollider`，非占用物）永远烧不起来**（呼应已知事实）。
- 火势在没人煽的时候会自己衰减（`CooldownTime`，`:404-407`）；被水浇时 `FightFire` 会把 `m_encourageSupressedTimer` 顶满（`:287`），**灭火期间火势涨不回来**。
- 一个 `FireHazard` 对象着火了，它自己每帧 `FightFire(m_lifetime, dt)`（`ServerFireHazard.cs:25-28`），所以**独立火格会自己烧完**。

### 3.3 灭火的四条代码路径

| # | 路径 | 代码 | 适用 |
|---|---|---|---|
| A | **灭火器 / 水枪喷洒** | 拿 `FireExtinguishSpray`/`WaterGunSpray` → `OnTrigger("start")` → `IsSpraying` → 每帧对 `IsInSpray` 的着火物 `FightFire(m_exinguishTime=0.5, dt, player:true)`（`ServerFireExtinguishSpray.cs:37-57`、`ServerSprayingUtensil.cs:117-139`） | 唯一"手动可控"的路径。**喷的时候厨师 MovementScale=0 不能动**（`ClientSprayingUtensil.cs:104`） |
| B | **灭火区域（`ExtinguishCollider`）** | 物体进入触发器 → `Extinguish()` + `SetCanCatchFire(false)`（`ServerExtinguishCollider.cs:5-13`） | 关卡自带的喷淋/水池区。**离开才恢复可燃**（`:15-22`） |
| C | **把灭火器拿在手里** | `OnCarryBegun` → 持有者的 `SetCanCatchFire(false)`（`ServerFireExtinguishSpray.cs:14-22`） | 只能保护自己，不能灭火 |
| D | **让别的东西占用火格** | `GridManager.OccupyGrid` → 旧占用物 `HandleTransfer` → `if (新占用物不是 FireHazard) Extinguish()`（`ServerFireHazard.cs:50-56`、`GridManager.cs:64-80`） | **需要该格的火是一个独立的 `FireHazard` 对象**。对"锅烧糊导致的台面 `ServerFlammable` 自燃"这条路径，台面本身并不是 `FireHazard`，所以**这条路径不适用**（未验证台面 prefab 上是否也挂了 `FireHazard`） |
| E | **让火烧完** | `ServerFireHazard.UpdateSynchronising` 自减（`:25-28`）；或 `ServerFlammable` 无煽火者时按 `CooldownTime` 衰减 | 时间成本高，不推荐 |

**灭火后能否恢复**：能。`_Extinguish` 会 `SetImmolatedComponentsEnabled(true)`（`ServerFlammable.cs:306`），台面的 `Interactable`/`Workstation`/`PickupItemSpawner` 重新可用。若是独立 `FireHazard` 对象，点火状态变 false 会 `Shutdown()` → `m_destroyTimer = m_destroyTime` → 之后该对象被销毁（`ServerFireHazard.cs:45-48,58-64`）。

### 3.4 动态变换时序（通用骨架）

```
服务端: ServerDynamicFlowController.BuildRunLevelRoutine (ServerDynamicFlowController.cs:36-60)
  ├ phase 计时 (Duration 来自 DynamicRoundData.Phases[i].Duration)
  ├ SendPhaseMessage(phaseNumber)  → ServerMessenger.DynamicLevelMessage 广播 (:22-26, ServerMessenger.cs:413-417)
  └ MoveToNextPhase()

客户端: ClientDynamicFlowController.OnDynamicLevelMessage (ClientDynamicFlowController.cs:31-36)
  → BuildTransitionToPhaseRoutine(phase) (:58-72)
     ├ obj = m_transitions[phase-1]
     ├ obj.SetActive(true)              ← 变换对象此刻才被激活
     ├ Setup(空回调)  ── 服务端在这里挂真正干活的回调(仅 IsHost)
     └ Run() 逐帧推进, 直到结束
  在 OnUpdateInRound 里被逐帧驱动 (:45-56)
```

**关键时序语义**：`Setup()` 是"注册动作"，`Run()` 是"播放动画 + 在正确的时间点执行动作"。**动作执行点在动画的关键帧之间**，所以"变换进行中"是一个真实存在的、持续若干秒的状态（例如 Beach 从 `TideInScene=true` 到潮水退出）。对自动化来说：**这段时间内不能假设网格与台面位置不变。**

### 3.5 变换对玩家的影响（`ServerPlayerRespawnManager.KillOrRespawn`）

`KillOrRespawn(obj, collider)`（`ServerPlayerRespawnManager.cs:22-36`）：
- 找 `RequestInterfaceRecursive<IRespawnBehaviour>()`；**有** → `StartCoroutine(behaviour.RespawnCoroutine(collider))`；**没有** → `NetworkUtils.DestroyObject(obj)`。

工程里 `IRespawnBehaviour` 的实现**只有三个**（`IRespawnBehaviour.cs:3-6` 定义）：
- `ServerPlayerRespawnBehaviour`（`ServerPlayerRespawnBehaviour.cs:5`）→ 玩家
- `ServerUtensilRespawnBehaviour`（`ServerUtensilRespawnBehaviour.cs:5`）→ 餐具/锅/盘子
- `ServerBackpackRespawnBehaviour`（`ServerBackpackRespawnBehaviour.cs:5`）→ 背包

**⭐ 关于 `collider == null` 的坑（重要且可验证）**：

- `ServerUtensilRespawnBehaviour.RespawnCoroutine`（`:27-77`）**不 deref `_collider`**，硬编码 `m_ServerData.m_RespawnType = RespawnCollider.RespawnType.FallDeath`（`:40`）→ **传 null 安全**。
- `ServerBackpackRespawnBehaviour` 也显式做了 null 保护：`(!(_collider != null)) ? RespawnType.FallDeath : _collider.Type`（`ServerBackpackRespawnBehaviour.cs:40`）→ **传 null 安全**。
- **`ServerPlayerRespawnBehaviour.RespawnCoroutine`（`:21-28`）没有保护**：
  ```
  :23  DropOrDestroyHeldItems(_collider);       // 若玩家手持物品 → :37 直接 _collider.Type → NRE
  :24  m_ServerData.m_RespawnType = _collider.Type;  // 无条件 deref → 必然 NRE
  ```
  → **只要以 `collider == null` 调用玩家，这个协程在第一次 `MoveNext` 时就抛 NRE**（Unity 会记异常并终止该协程）。也就是说：**`KillOrRespawn(player, null)` 不会真的把玩家传送到出生点。**
  这一条同时反证了"传 null 的做法在工程里是已知的"——`ServerBackpackRespawnBehaviour` 加了保护、`ServerPlayerRespawnBehaviour` 没加。
  （**未验证**：运行时是否真的每次都抛、是否有其它 `IRespawnBehaviour` 挂在玩家身上先被命中。但从 `IRespawnBehaviour` 的完整实现列表看，玩家身上只有 `ServerPlayerRespawnBehaviour`。）

**逐个变换对玩家的实际效果**：

| 变换 | 玩家会被传送吗 | 依据 |
|---|---|---|
| `BeachAnimatedDynamicTransition` | ❌ 不会。它遍历的是 **`IAttachment`**（物品），玩家不是 `IAttachment`（`:46-58`） | `BeachAnimatedDynamicTransition.cs:46-58` |
| `CampsiteAnimatedDynamicTransition` | ✅ **会**。遍历 **`IRespawnBehaviour`**（玩家也算），且传的是**非 null** 的 `m_respawnCollider`（`:77`、`:95`） | `CampsiteAnimatedDynamicTransition.cs:53-99`；重生流程见 `ClientPlayerRespawnBehaviour.cs:96-175` |
| `GraveyardAnimatedDynamicTransition` | ❌ 不处理玩家；但**散落物品被 `DestroyObject`（真销毁）** | `GraveyardAnimatedDynamicTransition.cs:31-46` |
| `GraveyardCountersDynamicTransition` | ❌ 不直接处理玩家；但若玩家身上挂着 `IRespawnBehaviour` 且位置落在 `"Counters"` 根下……不，它只对 `m_countersGoingOut[]` 的子树递归取 `IRespawnBehaviour`（`:139-154`），玩家不在其中 | `GraveyardCountersDynamicTransition.cs:130-167` |
| `DynamicReparentAnimatedDynamicTransition` | ⚠️ 不传送，但会 **`PlayerControls.transform.SetParent(null)`**（`:25-29`）——把厨师从会动的父级上摘下来 | `DynamicReparentAnimatedDynamicTransition.cs:25-29` |

**变换期间能不能操作？**
- 变换代码本身**没有任何** `PlayerControls.Suppress(...)` 调用。全工程 `Suppress` 的调用点只有：`CutsceneController`（`ClientCutsceneController.cs:168`）、表情轮盘（`ClientEmoteWheel.cs:235`）、重生（`ClientPlayerRespawnBehaviour.cs:425`）、对话框（`ClientTriggerDialogue.cs:71`）。
  → **结论：动态变换期间厨师可以照常移动和交互**（唯一例外是正在被重生的那段时间）。
- 唯一的"冻结"是 `GraveyardAnimatedDynamicTransition` 对**回合倒计时**的 suppressor（`GraveyardAnimatedDynamicTransition.cs:16-28,53-54` + `ServerRoundTimer.cs:30-42`）→ **那段时间内时间不流逝，订单不会超时**。
- 但台面的 `Interactable` 在动画期间可能被 `SetActive`/`SetParent` 影响（**未验证**），而且位置在动——**脚本按旧坐标走过去会走空。**

### 3.6 `TriggerMoveSpawnPoints` 的配合

- `TriggerMoveSpawnPoints`（`TriggerMoveSpawnPoints.cs:3-13`）：`m_trigger`、**`m_movePlayersImmediately`**、`m_spawnPoints[]`。
- `ServerTriggerMoveSpawnPoints`（`ServerTriggerMoveSpawnPoints.cs:5-77`，`ITriggerReceiver`，`EntityType.TriggerMoveSpawn`）：
  - `OnTrigger` 匹配 `m_trigger` → `Move()`（`:22-28`）。
  - `Move()`（`:30-39`）：`FindGameObjectsWithTag("Player")` → `CalculateBestSpawns` → 发 `MoveSpawnMessage`。
  - `CalculateBestSpawns`（`:41-57`）：把"每个玩家 × 每个 spawn point"展开成列表，按 `SortSpawnsByDistance` 排序后贪心配对（每轮取最近的一对并移除该玩家和该点）。
  - `SortSpawnsByDistance`（`:59-70`）：**优先挑没被占用的 spawn point**（`IsSpawnPointOccupied` → 未占用者排前），同优先级再比距离。
  - `IsSpawnPointOccupied`（`:72-76`）：用 `GridManager.GetGridOccupant(该点所在格) != null` 判定。
- `ClientTriggerMoveSpawnPoints`（`ClientTriggerMoveSpawnPoints.cs:6-112`）：
  - `ApplyServerEvent`（`:23-39`）：对每个配对调 `ApplySpawnChange` → `ClientPlayerRespawnBehaviour.MoveRespawnPoint(spawn.localPosition, spawn.parent)`（`:55-59`、`ClientPlayerRespawnBehaviour.cs:192-201`）——**改的是"以后重生到哪"，不是现在把人搬走**。
  - **只有 `m_movePlayersImmediately == true`** 才会 `MovePlayer`（`:31-38`）：关 `PlayerControls`、`Motion.SetKinematic(true)`、关 `DynamicLandscapeParenting`、暂停 `ClientWorldObjectSynchroniser`、`SetPositionAndRotation(target)` + `SetParent(target)`，一帧后恢复（`:61-111`）。
    → **这是唯一一处"立即把厨师搬到指定 Transform"的机制**，而且它会**同时把厨师的父级设成目标点**（`:83`），与 `DynamicReparentAnimatedDynamicTransition` 的 `SetParent(null)` 正好相反。

## 5. 对自动化的含义（怎么规避）

### 5.1 火灾：必须"零容忍"，检测到就撤

1. **总开关级检测（进关一次就做）**：读 `LevelConfigBase.m_hazardInfo` 是否为 null、其 `FireConfigData` 是否为 null。
   `GameUtils.GetLevelConfig()`（插件 `StateCollector.cs:254` 已在用）→ 反射取字段 `m_hazardInfo`（`LevelConfigBase.cs:9`）→ 取 `FireConfigData`（`HazardInfo.cs:7`）。
   **为 null 的关卡：永远不会因烧糊起火，脚本可以让锅多烧一会儿换取别的收益；不为 null 的关卡：必须严格控时。**
2. **单点检测（每帧/每 100ms）**：`ServerFlammable.GetAllOnFire()`（`ServerFlammable.cs:172-175`）是最直接的"全场景着火清单"，比 `FindObjectsOfType<FireHazard>()` 更准（因为台面自燃时**不一定**存在 `FireHazard` 对象）。插件 `SceneScanner` 目前只扫 `"FireHazard"` / `"SplatHazard"` 类型名（`SceneScanner.cs:31-32`），**会漏掉"台面 `ServerFlammable` 自燃但没有 FireHazard 组件"的情况——建议补上 `ClientFlammable`/`ServerFlammable` 的扫描，或用 `GetAllOnFire()` 静态方法。**
3. **提前预警（最好是这个）**：不要等火烧起来。每 100ms 读 `ClientCookingHandler.IsBurning()`（插件已在做，`SceneScanner.cs:191-193`；判定 `progress > 2*AccessCookingTime`，`ClientCookingHandler.cs:208-211`）。
   **留出的安全窗口**：锅从 `Cooked`（1×）走到 `Burnt`（2×）正好是一整段烹饪时间 `AccessCookingTime`（`SceneScanner.cs:208-212` 已能读到）。脚本必须在这段时间内把锅取下来。
4. **不要靠"灭火"兜底，要靠"别烧糊"**：灭火路径 A 需要用灭火器，而**喷的时候厨师 `MovementScale=0` 完全不能动**（`ClientSprayingUtensil.cs:104`），在双人协作里代价很高；路径 B（`ExtinguishCollider` 区域）只在特定关卡存在。
   如果真要灭火：**对准目标的正前方 1~2 格**（默认 15° 半锥、4 单位射程、正交格必中、斜前方必不中，见 §2.4 推演），并且**拿着灭火器的人自己不会着火**（`ServerFireExtinguishSpray.cs:14-22`）。
5. **着火台面的可交互性会"消失"**：`Interactable`/`Workstation`/`PickupItemSpawner` 被 `enabled = false`（`ServerFlammable.cs:214-224`）。
   → 脚本的状态机里"台面找不到组件"不能一律当成"关卡换了布局"，要先查是不是着火了。
   → 同理，**拿起灭火器后本厨师的 `ServerFlammable.SetCanCatchFire(false)`，放下才恢复**；如果脚本用"着火=危险"来判断，注意这个例外。

### 5.2 滑倒：把 splat 当"会消失的临时障碍"

- **扔完的东西落地会造出一个占据网格的 `SplatHazard`**（`ServerSplattable.cs:29-44`，`:37` 给 splat 加了 `StaticGridLocation`）。
  → 脚本若在某处"丢弃物品"（例如扔烧焦的菜），**那一格会变成障碍**，后续寻路要重读网格。
  → 而且 **`m_deleteOnSlip = true`**（`SlipCollider.cs:11`）：被踩一次就消失（`ServerSlipCollider.cs:24-27`）。**这是唯一一处"踩一次就自我修复"的障碍**。
- **踩到 splat 的厨师会失控 `0.38 + m_downTime + 0.42` 秒**（`ServerPlayerSlipBehaviour.cs:30-55`，`PlayerSlipBehaviour.cs:24,28`）。
  → 脚本必须能检测这个状态，否则会持续对一个不动的厨师发按键。
  可检测信号：`PlayerControls.enabled == false`（`ServerPlayerSlipBehaviour.cs:64`）或 `Rigidbody.isKinematic == true`（`:61`）。注意重生/喷水也有类似特征，需要交叉判断。
- `Splattable` 的数据组件 `Awake` 就自毁（`Splattable.cs:13-16`），**不要用 `FindObjectsOfType<Splattable>()` 找溅落点**。

### 5.3 动态变换：怎么检测、检测到之后怎么办

**核心问题**：变换期间（a）台面在移动，（b）物品被回收/销毁，（c）网格占用可能被改写，（d）**原生 `GridNavSpace.m_nodeMap` 不会更新**（`GridNavSpace.cs:44-56` 只建一次）。

**检测手段（按可靠性排序）**：

1. **`DynamicFlowController.m_transitions[].activeSelf`** —— 最直接。
   `ClientDynamicFlowController.BuildTransitionToPhaseRoutine` 在跑之前 `obj.SetActive(true)`（`ClientDynamicFlowController.cs:62`）。
   （**未验证** 变换结束后是否会被 `SetActive(false)`——源码里没有反向调用，所以更可能是"激活后一直留着"。因此用 `activeSelf` 做"正在变换"的信号可能只对**第一次**有效。）
2. **`Animator.GetBool` 状态位** —— 最准。这些是动画状态机自己维护的：
   - 通用台面：`"IsTransitioning"`（`AnimatedDynamicTransition.cs:14,34,38`）
   - 海滩潮水：`"TideInScene"` + `"IsTideTransitioning"`（`BeachAnimatedDynamicTransition.cs:24-26`）
   - 露营地木筏：`"RaftsAreChanging"` + `"IsArtInMotion"`（`CampsiteAnimatedDynamicTransition.cs:31-33`）
   - 墓地台面：`"InScene"` + `"IsTransitioning"`（`GraveyardCountersDynamicTransition.cs:51-53`）
   → 脚本可对**场景里所有 `Animator`** 轮询这几个 bool；任一为 true ⇒ 变换进行中。
3. **回合倒计时被 suppress** —— 只在墓地 Boss 变换期间为真（`GraveyardAnimatedDynamicTransition.cs:16-28` → `ServerRoundTimer.cs:33`）。可用作辅助确认。
4. **最稳的自建信号：维护自己的网格图，并周期性重建。**
   插件已经有 `LevelInfo`（`LevelInfo.cs:51-71` 有 5 秒缓存 + `force` 重建参数）。**建议**：在检测到变换时（用信号 1/2）**主动 `force` 重建** `LevelInfo` 网格，并在变换期间**暂停动作**。
   特别注意 `LevelInfo` 自己的两处盲区：
   - `OccupantChar`（`LevelInfo.cs:234-246`）用 tag 区分 `"Hazard"`/`"MovingPlatform"`/`"Travelator"`；**火灾台面自燃时占用物还是那个台面**，`Interactable` 被禁用不会改变网格字符——`LevelInfo` 无法从网格看出"这格在烧"，**必须叠加 §5.1 的 `GetAllOnFire()` 检测**。
   - `CollectHazards`（`LevelInfo.cs:282-339`）只收 `RespawnCollider`。**而 `FireHazard` / `SplatHazard` 是占用格、不是 `RespawnCollider`**；`LevelInfo` 是通过 `OccupantChar` 把它们归成 `'F'`（仅当占用物带 `"Hazard"` tag）。**如果 splat/fire 的 prefab 没打 `"Hazard"` tag，就会被误判成普通 `'#'`**（后果：仍不可走，但脚本无法区分"烧着的格子"和"普通台面"）。**tag 是否配置：未验证**（TagManager 不在 .cs 里）。

**检测到之后应该怎么做**：

- **暂停对该区域的一切寻路与走位**：不要用变换前的坐标走过去。变换期间台面 Transform 在移动，旧坐标会撞墙或踩空。
- **重读 `LevelInfo` + 重读 `SceneScanner.Scan()`**：`SceneScanner` 的布局扫描周期是 1 秒（`StateCollector.cs:135-137`），**足够慢**：变换通常持续数秒，1 秒采样可能正好错过"台面已经动了但缓存还没更新"。建议在变换标志为 true 时**把布局重扫频率提高到每帧或 0.2 秒一次**，或直接复用 `LevelInfo.Snapshot("force")`。
- **不要把物品放在"会沉/会漂走"的台面上**：海滩会把潮水区内的物品、以及 `m_leavingCounterLayoutRoot` 台面上的物品回收（`BeachAnimatedDynamicTransition.cs:40-71`）；露营地同理还会把盘子洗掉（`CampsiteAnimatedDynamicTransition.cs:82-86`）；墓地会**真的销毁**未附着物品（`GraveyardAnimatedDynamicTransition.cs:31-46`）。
  → **规避**：变换临近时把物品拿在手里（`IAttachment.IsAttached()` 为 true 的东西**不会被回收**——三处 `DestroyAndRespawnObjects` 都对 `IsAttached()` 做了豁免，`BeachAnimatedDynamicTransition.cs:49`、`CampsiteAnimatedDynamicTransition.cs:75`、`DynamicReparentAnimatedDynamicTransition.cs:20`）。
  → **手里拿着永远比放在台面上安全。**
- **不要试图站在会漂走的平台上**：露营地是唯一会把厨师重生掉的（`CampsiteAnimatedDynamicTransition.cs:77`，传了有效 collider）；但也别指望海滩/墓地会救你——它们不管玩家，你可能会跟着台面沉下去然后被 `RespawnCollider`/边界处理。
  → **通用规避：变换开始前把两个厨师都撤到"位置固定的地板格"上。**
- **墓地 Boss 变换期间时间冻结**（`ServerRoundTimer.cs:33`）：这段时间订单不会超时，可以放心等它演完。
- 变换期间**没有输入冻结**（§3.5），所以"暂停动作"是脚本自己的纪律，不是游戏强制。

### 5.5 关于"哪些格子会因为动态变换突然变成危险区"

**直接从源码可确定的结论**：

- **没有任何"台面移动后原地变成危险区"的代码。** 危险区的产生只有三条路：
  1. `RespawnCollider` 触发器的 Bounds 覆盖到（`ServerRespawnCollider.cs:28-39`）——这些是**静态**的关卡物体（水/岩浆/熔岩），变换代码不动它们。
  2. 火灾：**火焰会占格**（§2.1/§3.2），且蔓延方向是正交通道。
  3. splat：**扔东西砸地会造出一个占格 + 触发滑倒的 `SplatHazard`**（`ServerSplattable.cs:29-44`）。
- **会"突然出现/消失的区域"反而是：**
  - `BeachAnimatedDynamicTransition` 的潮水退去/涨起——但注意 `DestroyAndRespawnObjects` 只处理**物品**，不产生新的 `RespawnCollider`；潮水的"危险"是那个 `m_tideCollider` 本身在场景里就有的碰撞体（**未验证它是不是也是 `RespawnCollider`**）。
  - **台面消失 → 原本的"格子被占"变成"格子空着"**，如果那格下面是水/坑，脚本就会以为"能走了"从而掉下去。
    → **这是最真实的动态风险：不是格子变危险，而是"障碍格变空格但下面没地板"。**
    `LevelInfo` 已经用 `'V'`（射线打不到地板）标记了这种格（`LevelInfo.cs:248-259`），但**它是在变换前烘焙的**——变换后必须重算，否则 `'#'` 会一直被当成障碍（保守，安全），而**已变成 `'.'` 的格子若下面没地板就危险**（`'V'` 判定是在烘焙时打射线的，变换后地板可能已被移走 ⇒ 需要 `force` 重建）。
