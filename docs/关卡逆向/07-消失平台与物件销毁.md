## 0. 先给结论（荷叶 + 脚本怎么判断这格能不能站）

**Q1：荷叶"踩过就消失"是怎么实现的？**

工程里**没有** `LilyPad` / `Lotus` 类。全 2365 个 `.cs` 里和荷叶有关的唯一直接证据是 5 条音频枚举：

```
DLC_13_LilyPad_Lrg_Plunge,   GameOneShotAudioTag.cs:317
DLC_13_LilyPad_Lrg_Pop,      GameOneShotAudioTag.cs:318
DLC_13_LilyPad_Sml_Plunge,   GameOneShotAudioTag.cs:319
DLC_13_LilyPad_Sml_Pop,      GameOneShotAudioTag.cs:320
DLC_13_LilyPad_Step,         GameOneShotAudioTag.cs:321
```

**结论：荷叶是"纯 prefab 组装"，没有任何专属逻辑类。** 它的行为必须由通用组件拼出来，而这些通用组件本文全部读到了。拼法（代码可证的部分 + 未验证的接线）：

1. **可站立面** —— 荷叶本体是一个带 `Collider` + `Steppable` 的物体。`Steppable` 是全工程**唯一**"可以踩上去的物体"语义组件（`Steppable.cs:3-9`：`[RequireComponent(typeof(Collider))]` + `[AssignChild("PlaneTransform")]` + `ProjectPointOntoStep()`），消费者只有厨师：`ClientPlayerControlsImpl_Default.cs:521-526`（碰撞时尝试踩上去）、`:822-833`（法线夹角 >30° 才尝试）、`:881-893`（投影高度 < `StepHeightMax` 才瞬移上去）。步高上限 **0.65u**（`PlayerControls.cs:50`）。
2. **踩到的检测** —— `TriggerZone`（一格触发体，`m_onOccupationTrigger`）由其服务端孪生 `ServerTriggerZone` 在 `OnTriggerEnter` 时 `SendTrigger(m_onOccupationTrigger)`（`ServerTriggerZone.cs:51-58`）。**它不区分是谁进来了**：`TriggerZone` 没有任何层过滤字段（`TriggerZone.cs:3-13`），任何 collider 都算。
3. **下沉/浮起的表现** —— 走"触发器 → Animator"这条通用链：`TriggerOnAnimator`（`TriggerOnAnimator.cs:5-14`）/ `TriggerAdapter`（`TriggerAdapter.cs:5-9`）/ `TriggerQueue`（`TriggerQueue.cs:57` `m_targetType = Animator`）。这条链的官方用法范式就在 `AnimatedDynamicTransition.cs:30-40`：**SetTrigger/SetBool → 每帧轮询 animator 的 `IsTransitioning` bool，直到它变 false**。荷叶的 collider 是动画层级的一部分，**下沉时 collider 跟着走低**（这就是"消失"的观感）。
4. **延迟** —— "踩上去 N 秒后才沉"或"离开 N 秒后浮起"用 `TriggerTimer`（`ServerTriggerTimer.cs:58-64` + `:85-92`）或 `TriggerQueue`/`TimedQueue`（`ServerTimedQueue.cs:97-130`）或 `TriggerWithCooldown`（`ServerTriggerWithCooldown.cs:23-30`）。
5. **"消失"的物理后果** —— collider 沉到水面以下后，厨师脚下无地面 → `GroundCast` 打不到 → `HasGroundContact()` 变 false（`GroundCast.cs:76-79`、`:180-201`）→ 累计超过 **0.2 秒**判定 falling（`ClientPlayerControlsImpl_Default.cs:468-488` + `PlayerControls.cs:270`）→ 掉进水里被 `RespawnCollider`（`RespawnType.Drowning`）吞掉重生（`RespawnCollider.cs:5-11`、`ServerRespawnCollider.cs:28-39`、`ClientPlayerRespawnBehaviour.cs:129-131`）。

> 音频语义（`Plunge`=下沉 / `Pop`=浮起，`GameOneShotAudioTag.cs:317-321`）表明荷叶**是"沉下去还会浮回来"的循环体，而不是被 `Destroy` 掉的一次性物体**。这一点很关键：它意味着**同一个格子在不同时刻的"可站立性"会反复翻转**，脚本不能靠"开局扫一遍地图"缓存结论。
>
> ⚠️ 上面第 3 步的**具体接线**（荷叶 prefab 上到底挂了 `TriggerZone` 还是 `CollisionTrigger`、trigger 字符串叫什么、是 `TriggerTimer` 还是自带动画事件）**未验证** —— 这些全部是 prefab 序列化数据，`.cs` 里看不到。但**第 1、2、4、5 步的组件级机制是确定的**，脚本的探测方案不依赖第 3 步的具体接线。

**Q2：脚本怎么在运行时知道"这一格现在还能不能站"？**

**唯一可靠答案：问物理，不要问占用格。** 具体见 §5，一句话版：

```csharp
// 复刻游戏自己的判据：ClientChefSynchroniser.cs:490-491
var hits = Physics.SphereCastAll(cellCenter + Vector3.up, 0.1f, Vector3.down, 2f,
                                 LayerMask.GetMask("Ground", "SlopedGround"));
// ① 没命中 → 不能站
// ② 命中了但 hit.point.y 明显低于该关卡的地面基准高度 → 荷叶已下沉，不能站
// ③ 命中体上带 RespawnCollider → 是水面，不能站
// ④ 再用 Physics.OverlapBox(cellCenter, 0.5f³, solidMask, QueryTriggerInteraction.Ignore) 排掉实心阻挡
```

**`GetGridOccupant` 在这里是废的**：荷叶若不注册占用格，`GetGridOccupant` 返回 `null`，与"开阔水面/虚空"**完全无法区分**；若注册了，`GridNavSpace` 就会把这格标成**不可走**（`GridNavSpace.cs:53` 的判据是 `GetGridOccupant(index) == null`），和"能站上去"自相矛盾。详见 §5.2 的失效场景表。

## 1. 机制概览

### 1.1 一句话：游戏里"东西没了"有 **五种物理含义完全不同** 的消失

| # | 消失含义 | 代码路径 | 碰撞体还在吗 | 占用格还在吗 | 物体还能回来吗 |
|---|---|---|---|---|---|
| A | **整个 GameObject 被销毁** | `Object.Destroy` / `GameObjectUtils.Destroy()` | 没了 | **释放**（`StaticGridLocation.OnDestroy` → `DeoccupyGrid`） | 不能（除非另有 `TriggerCreateObject` 重建一个新物体） |
| B | **整个 GameObject 被 `SetActive(false)`** | `NetworkUtils.DestroyObject()`（联机销毁就是这样） | 没了（失活物体不参与物理） | **不释放**（`StaticGridLocation.OnDisable` 是空的） | 可以（`SetActive(true)`） |
| C | **只禁用某个 MonoBehaviour** | `TriggerDisableScript` → `ClientTriggerDisableScript` | 取决于被禁的脚本干了什么 | 不变 | 可以（enableTrigger） |
| D | **collider 被动画/脚本移动到别处**（荷叶下沉） | Animator 驱动 transform；或脚本只动 collider | **还在，只是不在原位** | 不变 | 可以（浮起来） |
| E | **只关渲染，碰撞完全不动** | `TurnToggleMeshsWithinSpecifiedBounds` 只写 `Renderer.enabled` | 在 | 不变 | — |

自动化脚本最容易踩的坑是 **B 和 D**：B 会让"占用表说这格有人"永远为真（因为没人调 `DeoccupyGrid`），D 会让"向下打射线有命中"永远为真（因为 collider 只是变低了）。

### 1.2 触发区 → 动作 的通用链路（3 段式）

```
[触发区]                          [中继/延迟]                    [动作]
TriggerZone            ──┐
  m_onOccupationTrigger │      TriggerTimer           ──┐
  m_onDeoccupationTrigger│     TriggerQueue/TimedQueue  │    TriggerDestroy         (销毁)
  (无层过滤)             │      TriggerWithCooldown     │    TriggerDisableScript   (禁用脚本)
                         │      TriggerAdapter         │    TriggerKillAttachments (清掉上面/周围的物品)
CollisionTrigger       ──┤      TriggerCounter         │    TriggerOnAnimator      (播动画)
  m_collisionFilter (有层)│     TriggerOnObject        │    TriggerCreateObject    (重建，需 SendMessage)
  m_trigger              │      TriggerWithCooldown    │    TriggerCreateHazard / TriggerIgniteArea
                         │                              │    ServerPlayerControlsImpl_Default ("Curse")
RespawnCollider        ──┤
  m_respawnFilter (有层)  │
  m_onRespawnTrigger     │
                         │
SlipCollider           ──┘     （自己就是动作：踩到就 Destroy 自己）
KillCollider                    （自己就是动作：撞到我的东西被 Destroy）
BalloonAnimateOnHit             （自己就是动作：撞到就播动画，动画完 SetActive(false)）
```

**分发机制**（必须理解，否则会误判"某某组件能不能被触发"）：

```csharp
// GameObjectUtils.cs:423-433
public static void SendTrigger(this GameObject _target, string _trigger) {
    if (_trigger == string.Empty) return;
    ITriggerReceiver[] array = _target.RequestInterfaces<ITriggerReceiver>();  // 只找实现了接口的组件
    for (int i = 0; i < array.Length; i++) array[i].OnTrigger(_trigger);
}
```

于是全工程存在**两套互不相通的"触发"投递方式**：

| 投递方式 | API | 命中谁 | 典型调用者 |
|---|---|---|---|
| **接口投递** | `gameObject.SendTrigger(s)` | 只命中实现了 `ITriggerReceiver` 的组件 | `ServerTriggerZone.cs:55,65`、`ServerTriggerTimer.cs:81,90`、`ServerTriggerWithCooldown.cs:27`、`ServerTimedQueue.cs:117`、`ServerTriggerAdapter.cs:18`、`ServerCollisionTrigger.cs:18`、`ServerRespawnCollider.cs:36` |
| **消息投递** | `gameObject.SendMessage("OnTrigger", s, DontRequireReceiver)` | 命中**任何**有 `OnTrigger(string)` 的组件（含 private） | `SendTriggerToObject.cs:58-64`、`SendMessageToObject.cs:11-21`、`ForwardTriggerToTarget.cs:18`、`GameObjectUtils.cs:357,363`、`ClientPilotRotation.cs:41,45`、`ServerSessionInteractable.cs:171,183` |

**这条区分能解释 `TriggerCreateObject` 为什么"平时不触发"**：它只有一个 **private `OnTrigger(string)`**（`TriggerCreateObject.cs:18-30`），**没有实现 `ITriggerReceiver`**（对比 §2.2 的接口清单：全工程所有 `ITriggerReceiver` 声明里都没有它）——所以 `SendTrigger` 链**永远打不到它**，只有动画事件 `SendTriggerToObject` / `SendMessageToObject` 能打到。（这个结论与 `02-危险物与动态关卡变换.md:131` 一致。）

### 1.3 荷叶为什么"脚本必须自己处理"

`GridNavSpace.m_nodeMap` 只在 `Start` 采样一次占用表、**之后永不刷新**（`GridNavSpace.cs:44-56`），而且它**只服务于老鼠 NPC**：

```csharp
// GridNavigator.cs:16-19 → :44-48
m_gridNavSpace = GameUtils.GetGridNavSpace();          // 全工程唯一消费者
Point2 startPoint = m_gridNavSpace.GetNavPoint(transform.position);
path = m_gridNavSpace.FindPath(startPoint, targetPoint);
```

`GameUtils.GetGridNavSpace()` 的调用点全工程只有 `GridNavigator.cs:18`（grep 结果）。所以：

- **游戏自己的 AI（老鼠）也会在荷叶消失后的格子上继续走** —— 它同样会被淹死（NPC 没有 RespawnCollider 免疫，未验证 NPC 是否会死）。
- 厨师**根本不用这张图**：厨师移动是连续的、按速度积分的（`ClientPlayerControlsImpl_Default.cs:393-466`），`RunSpeed = 4 u/s`（`PlayerControls.cs:28`），不按格跳。**格子只用于交互/放置**（`PlayerControls.cs:641` `m_bGridSelection`）。
- 结论：**对厨师而言，"这格能不能站"是纯物理问题，网格系统帮不上忙**。

> ⚠️ **两个重要缺陷（都可直接利用/需要绕开）**
>

> 2. `UpdateSynchronising` 在 `for` 循环里 `Remove` 元素（`ServerTriggerZone.cs:31-37`），删一个后续索引就前移，**会漏检**；只对 `m_fallPad == true` 的触发区生效，实际影响未验证。

#### 2.1.2 `CollisionTrigger` / `ServerCollisionTrigger`

```csharp
// CollisionTrigger.cs:3-10
public class CollisionTrigger : MonoBehaviour {
    public LayerMask m_collisionFilter = -1;   // 默认全层
    public string    m_trigger;
}
```

```csharp
// ServerCollisionTrigger.cs:14-25
private void OnTriggerEnter(Collider other) {
    if ((m_trigger.m_collisionFilter.value & (1 << other.gameObject.layer)) != 0
        && m_trigger.m_trigger != string.Empty)
        base.gameObject.SendTrigger(m_trigger.m_trigger);
}
private void OnCollisionEnter(Collision other) { OnTriggerEnter(other.collider); }
```

与 `TriggerZone` 的三个差异（都很实用）：

1. **有层过滤**，而且**硬编码用 `gameObject.layer`**（不是 `_collisionFilter` 那样比 collider 的层）——所以能精确限定"只有 Player 层会触发"。
2. **每次都发**，没有"只在空→非空跳变时发"的边沿判定 → 一次踩入只发一次（PhysX 语义），但**重复进入会重复发**。
3. `OnCollisionEnter` 也转发（`:22-25`）→ **不需要 isTrigger，实心碰撞也能触发**。

`ClientCollisionTrigger` 是空壳（`ClientCollisionTrigger.cs:3-4`），不参与逻辑。

#### 2.1.4 自己就是动作的碰撞体

| 类型 | 触发条件 | 行为 | 引用 |
|---|---|---|---|
| `KillCollider` | `OnCollisionEnter`（**实心碰撞**，没有 isTrigger 分支） | `Object.Destroy(collision.gameObject)` —— **销毁撞到我的那个东西** | `KillCollider.cs:5-8` |
| `SlipCollider` | `OnCollisionEnter` / `OnTriggerEnter` + 层过滤 `m_slipFilter` | 让玩家滑倒；**`m_deleteOnSlip` 默认 `true` → 自己 `Object.Destroy`** | `SlipCollider.cs:5-11`、`ServerSlipCollider.cs:17-28`（`:24-27` 是自毁）、`:47-65`（进出配对） |
| `BalloonAnimateOnHit` | `OnTriggerEnter`（任意 collider） | 播 animator trigger + 开粒子；等 animator 发 `"animationFinished"` 时 **`SetActive(false)`（含 collider）** | `BalloonAnimateOnHit.cs:3-4, 25-35, 37-48` |

> **`SlipCollider`（`m_deleteOnSlip = true`）是 base game 里最标准的"踩过就消失"**：踩上去滑倒 → 该物体当场 `Destroy` 自己。而 `BalloonAnimateOnHit` 是"踩上去 → 播爆掉动画 → 整物体失活"。这两个都在 **base game**（不是 DLC13），说明"踩过就消失的平台"在 OC2 里是**复用多套通用机制**的，进一步支持"荷叶没有专属类"的判断。

private void StepOntoObject(Steppable _steppable, Vector3 _position, Vector3 _direction, PlayerControls _controls) {
    Vector3 target = _steppable.ProjectPointOntoStep(_position, _direction);      // 投到 Steppable 的平面上
    Vector3 delta  = target - m_Transform.position;
    Vector3 planar = delta.WithY(0f).SafeNormalised(m_Transform.forward);
    if (Vector3.Angle(planar, m_Transform.forward) < 90f
        && Vector3.Project(delta, m_Transform.up).sqrMagnitude < StepHeightMax²)  // 0.65²
        m_Transform.position = target;                 // ← 硬瞬移（不是物理抬升！）
}

### 3.2 "消失"的三种后果，脚本必须分开处理

| 场景 | 占位表 | 向下射线 | 能否恢复 | 自动化对策 |
|---|---|---|---|---|
| **荷叶下沉**（collider 还在，位置变低） | 不变 | **仍命中**（但 `hit.point.y` 变低）→ 只判"命中与否"会**误判为安全** | 能（浮起） | **必须比较命中高度**（§5.3） |
| **荷叶被 `SetActive(false)`**（气球式） | **可能仍显示"被占用"**（`StaticGridLocation.OnDisable` 空） | 命中消失 | 能 | 用 `activeInHierarchy` 辅助判断；射线是主判据 |
| **荷叶被真销毁** | 释放（若走 `OnDestroy`） | 命中消失 | 不能 | 一旦离开这格就再也回不去，路径必须单向规划 |

### 3.3 网络时序的不对称（影响"什么时候能观测到"）

```
主机侧（authoritative）                         客户端侧
─────────────────────────────                  ─────────────────────────────
ServerTriggerZone.OnTriggerEnter               （ClientTriggerZone 什么都没做：
  → SendTrigger → 动作                           SyncOccupied 无调用者，
  → Object.Destroy / SetActive(false)             m_occupied 恒 false）
  → NetworkUtils.DestroyObject                  ← DestroyEntity 消息
     ├─ SetActive(false)（本地立刻）               → ClientSynchronisationReceiver.DestroyObject
     └─ ServerMessenger.DestroyEntity ────────→     → EntitySerialisationRegistry.UnregisterObject
                                                     → Object.Destroy(entity)
```

- `TriggerZone` 的占用状态（`TriggerZoneMessage`）**根本没过网**（`ServerTriggerZone.cs:40-44` 无调用者）。
- `TriggerDisable` / `MultiTriggerDisable` 的启用状态**过了网**（`ServerTriggerDisableScript.cs:21-25` → `TriggerDisableMessage`，`TriggerDisableMessage.cs:6`）但**服务端自己不应用** —— 也就是"服务端只广播状态，客户端才真正 `enabled = ...`"（`ClientTriggerDisableScript.cs:23-30`）。
- 我们的自动化是**同进程 host + 本地客户端**（两个厨师同机）。此时服务端"销毁"= `SetActive(false)`，物体对象还在内存里（`NetworkUtils.cs:112`），`GetComponent` 仍能拿到组件，但 `activeInHierarchy == false` 且**不再参与物理**。**这是脚本最容易误判的一点**：遍历到它、读到它、以为它还在。

## 5. 对自动化的含义

### 5.1 结论速览

| 问题 | 结论 | 依据 |
|---|---|---|
| 能靠 `GetGridOccupant` 判断"荷叶还在不在"吗 | **绝对不能**。荷叶未注册时返回 `null` 与水面/虚空**完全相同**；注册了则被 `GridNavSpace` 标为不可走，与"能站上去"矛盾 | `GridManager.cs:82-87`、`GridNavSpace.cs:53` |
| 能靠 `GetGridOccupant` 判断"这格有没有东西挡"吗 | 部分能，但**必须假定它会陈旧**：`SetActive(false)`（=联机销毁）**不释放格子** | `StaticGridLocation.cs:35-41`、`NetworkUtils.cs:110-114` |
| 能靠 `Physics.Raycast` 判断"这格有地板"吗 | **能，这是唯一正确方向**。但要**同时校验命中高度**，否则荷叶下沉会被判成"安全" | `ClientChefSynchroniser.cs:490-491`、`GroundCast.cs:126-155` |
| 能读 `TriggerZone` 的占用状态吗 | **不能**。`SyncOccupied()` 无调用者 → 客户端 `m_occupied` 恒 false | `ServerTriggerZone.cs:40-44`、`ClientTriggerZone.cs:8` |
| 能靠 `GridNavSpace.FindPath` 规划吗 | **不能**。它只在 `Start` 建一次、永不刷新，而且只服务老鼠 NPC | `GridNavSpace.cs:44-56`、`GridNavigator.cs:18` |
| 荷叶会不会在同一局里反复变 | **会**（Plunge / Pop 是成对的 one-shot 音频） | `GameOneShotAudioTag.cs:317-321` |
| 死了会怎样 | 主 collider 被整个 disable 5 秒 + 搬回出生点；这段时间**发按键无效** | `ClientPlayerRespawnBehaviour.cs:103, 346-359`、`PlayerRespawnBehaviour.cs:42` |
| 该不该"完全绕开荷叶区" | 只在**需要绝对稳定**时可作为降级方案；正常应做**逐格实时探测** | §5.5 |

### 5.3 推荐的探测算法（可直接写代码）

```
── 关卡加载后（只做一次）为每个关卡建立"地形基准" ─────────────────────────
OnLevelLoaded():
    safeY   = 在出生点格做向下 SphereCastAll(Ground|SlopedGround) 的命中 y   // 基准地面高度
    waterCells = { idx | OverlapBox 该格 + 命中体上有 RespawnCollider }        // 水/致命区
    padCells   = { idx | 该格上有 Steppable }                                  // 可踩物体（荷叶候选）
    // 说明：padCells 只是"候选"，荷叶会下沉/浮起，绝不能当成静态白名单

── 每次决定"下一步迈向哪格"之前，逐格实时探测 ─────────────────────────────
bool CanStand(GridIndex idx):
    p = gridManager.GetPosFromGridLocation(idx) + Vector3.up * 0.5f
    // 探针 A：游戏自己的判据（ClientChefSynchroniser.cs:490-491）
    hits = Physics.SphereCastAll(p, 0.1f, Vector3.down, 2f, maskGroundSloped)
    if hits.Length == 0: return false                       // 脚下什么都没有
    h = hits 中 y 最高的那个命中
    if h.point.y < safeY - Y_TOLERANCE: return false         // ★ 荷叶已下沉 / 平台塌了
    if h.collider.GetComponent<RespawnCollider>() != null: return false   // 是水
    // 探针 B：排除实心阻挡（墙/台面）
    if Physics.OverlapBox(h.point + Vector3.up*0.5f, Vector3(0.4,0.5,0.4),
                          Quaternion.identity, maskSolid, QueryTriggerInteraction.Ignore).Length > 0:
        return false
    return true

── 采样策略：只测格心会漏（荷叶可能比格小）──────────────────────────────
    建议 5 点采样：格心 + 四角内缩 0.2 格；5 点里"至少 3 点能站"才算能站
    （0.65 步高 + 0.3 命中距离容差：GroundCast.cs:166、PlayerControls.cs:50）

── 缓存与失效 ────────────────────────────────────────────────────────
    单格探测 ≈ 2 次物理查询，微秒级 → 不必也**不应该**缓存整张地图
    只缓存"当前格 + 相邻 4 格"，并在以下任一条件成立时把缓存整体标脏：
      · GroundCast 的 HasGroundContact() 发生翻转
      · 收到任意 DestroyEntity / 摄像机附近 activeInHierarchy 状态变化
      · 每 N 帧（N≈10）无条件重测"脚下格"（防止 Rigidbody 休眠导致 GroundCast 不更新）
```

**为什么"必须校验命中高度"是这套方案的灵魂**：荷叶下沉的物理真相是 collider 跟着动画走低（§0），"向下打射线有命中"在整个过程中**始终为真**。只判 `hits.Length > 0` 的脚本会在荷叶沉下去的**最后一刻**才掉进水里 —— 而那时离死亡只剩 0.2 秒。

### 5.4 具体到荷叶关卡的应对策略（三选一，按稳定性排序）

**方案 A（推荐）：逐格实时探测 + 短程缓存**

- 走一步测一步（上方算法），只缓存当前格与 4 邻格，每 ~10 帧强制重测。
- 关键帧：**在朝目标格迈出第一步之前**探测；一旦发现"目标格没了"，立刻改为原地等待或换路。
- 用 `PlayerControls.GroundCollider == null` 作为**兜底告警**：只要它变 null，立刻停止一切移动输入，做"回退到上一格"或"随机微调方向"（把厨师推回有地面的地方）。
- 反应窗口参考：`m_timeBeforeFalling = 0.2s`（`PlayerControls.cs:270`）。厨师在荷叶中心离及格边约 0.6u（半格），以 4 u/s 计 ≈ 0.15s 就能跑出去 —— **勉强够，所以一旦告警必须当帧就动**。

**方案 B（降级 / 保守）：识别并绕开荷叶区**

```csharp
// 关卡加载后一次性建"黑名单"：可踩物体 + 水面
var pads  = Resources.FindObjectsOfTypeAll<Steppable>();      // 荷叶候选（含 inactive）
var water = Resources.FindObjectsOfTypeAll<RespawnCollider>(); // 水/致命区
// → 这些格永不进入寻路；只用确定的陆地行走
```
- 代价：可能无路可走（荷叶可能是**唯一通道**，**未验证**）。
- 好处：与荷叶的内部实现细节**完全解耦**（不需要知道它沉不沉、什么时候沉）。

**方案 C（不推荐）：只在必要时刷新整张地图**

- 41×3×41 = 5043 格；哪怕只测 z=0 层也是 1681 格 × 2 次物理查询 —— 单次刷新就是几千次物理查询，**在 60fps 下不可接受**。
- 而且"什么时候算必要时"本身就要靠探测来判断，等于把 A 的探测成本乘上整图规模。
- **正确做法是 A 的局部刷新，而不是 C 的整图刷新。**

**另外三条与本题相关的操作纪律**：

1. **不要用 `GridNavSpace` / A\* 规划**（只服务老鼠 NPC，且是开局快照）——见 §1.3。
2. **识别"厨师正在重生"并静默**：`PlayerControls.m_bRespawning`（`PlayerControls.cs:304`）+ 主 Collider `enabled == false`（`ClientPlayerRespawnBehaviour.cs:103`）。重生期间（约 5s，`PlayerRespawnBehaviour.cs:42`）发按键会被 `Suppress` 门控吞掉（`PlayerControls.cs:483-497`、`ClientPlayerRespawnBehaviour.cs:421-427`）。
3. **`SetActive(false)` 的物体要当作不存在**：遍历场景找目标（台面、荷叶、餐盘）时，除了 `ReferenceEquals(null)` 还要判 `activeInHierarchy`，否则会把"已被联机销毁（=失活）"的东西当成活的（`NetworkUtils.cs:112`）。
4. **不要靠 `TriggerDisableScript` 的开关状态做逻辑**：服务端不本地应用（`ServerTriggerDisableScript.cs:21-37`），非联机时消息可能根本不发（`ServerSynchroniserBase.cs:55-61`）→ 该开关在单机下可能与实际行为不一致（**反编译存疑，需探针**）。

### 5.5 一句话给写代码的人

> **把"这一格能不能站"当成一个"每帧都可能变"的物理量去实时问 PhysX，不要在开局建一张静态地图；`GetGridOccupant` 只用来查"台面/障碍/物品"，永远不要用来查"地面"。**

## 7. 未解疑问

1. **荷叶 prefab 的确切组件表**：挂了 `TriggerZone` 还是 `CollisionTrigger`？trigger 字符串是什么？是 `TriggerTimer`、`TriggerQueue` 还是 `TriggerWithCooldown`？→ **必须用运行时探针 dump 荷叶物体上的所有组件与 `[SerializeField]` 值**（BepInEx 侧可做）。
2. **荷叶"消失"到底是哪一种**：A（真销毁）/ B（`SetActive(false)`）/ D（动画把 collider 挪走）？三种对脚本的影响完全不同（§3.2）。→ 探针：记一次荷叶的 `GetInstanceID()` 与 `activeInHierarchy`，踩过去后再取一次，对比 ID 是否还能找到。
3. **荷叶下沉/浮起的时长与冷却数值**（`TriggerTimer.m_time`、`TriggerWithCooldown.m_Cooldown` 都是 prefab 序列化值）。→ 探针：踩上去后每帧记录脚下 `hit.point.y`，画曲线即可反推。
4. **荷叶是否注册占用格**（决定 `GetGridOccupant` 返回 `null` 还是陈旧对象）。→ 探针：踩之前/之后各调一次 `GetGridOccupant(gridIndexOfPad)`。
5. **荷叶的碰撞体在哪个层**（决定我们向下射线该用什么掩码）。`Ground` / `SlopedGround` 是 `ClientChefSynchroniser.cs:490` 用的两个层，但荷叶（可踩平台）是否在其中 **未验证**。→ 探针：`padCollider.gameObject.layer` + `LayerMask.LayerToName()`。
6. **`RenderKillSwitch` 的消费者**：全工程无代码引用（grep 结果），但它在 prefab 上存在（用户已确认类型存在）。→ 说明它由某个我们没看到的系统（渲染剔除 / 编辑器工具 / 原生插件）消费，**未验证**。
7. **`KillPlane` 的两种身份**：`LevelBounds.cs:8` 的 `"KillPlane"` 是**子物体名**（一个 `RespawnCollider`），`CapsuleCollisionHelper.cs:44` 的 `"KillPlane"` 是**层名**。两者是否同一个东西 **未验证**；`CheckCapsuleKillPlane()` 本身是死代码。
8. **服务端/客户端 synchroniser 的启用规则**：`SynchroniserBase.OnEnable` 只把 `ActiveAndEnabled` 置 true（`SynchroniserBase.cs:31-39`），但**看不到谁在客户端把 `ServerTriggerZone` 等关掉**。这决定"荷叶下沉在纯客户端视角何时可见"，以及非联机时 `TriggerDisableScript` 是否生效（§2.6）。→ **反编译存疑，建议运行时验证**。
9. **`TriggerZone` 无层过滤的实际后果**：往荷叶上扔一个番茄会不会触发"下沉"？按 `ServerTriggerZone.cs:51-58` 的字面逻辑**会**（任何 collider 都算占用）→ 推断会，**未验证**。
10. **`PlayerbasedActivation` 与占用网格的顺序**：被 `SetActive(false)` 的物体，如果它的 `StaticGridLocation` 已在 `Awake` 注册过，会留下**永久陈旧占用**；如果它在 `Awake` 前就失活，则压根没注册。同一批 `Awake` 的执行顺序在 `.cs` 里看不出 → **未验证**。
11. **厨师 `GroundCast.m_landscapeMask` 的确切掩码**（prefab 序列化值）。它决定"荷叶算不算地面"。
12. **Rigidbody 休眠导致的 `GroundCast` 停更**（`GroundCast.cs:111-124`）在实战中的影响幅度：厨师站着不动时，荷叶在脚下沉下去，`HasGroundContact()` 会不会一直报 true？→ **这是本专题最该优先验证的一条**，因为它直接决定"方案 A 的兜底告警"是否可靠。
