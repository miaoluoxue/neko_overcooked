# 09 · 分屏双键盘键位权威表

> 这份文档存在的理由：**键盘键位已经让我们踩过一次坑**（"厨师 id 和玩家编号不是一回事"，
> 导致所有按键都发给了错的人）。而更隐蔽的坑是：**游戏有两套完全不同的键盘绑定表**，
> 很容易照着单键盘那套去查，然后得出错误结论。
>
> 本文所有结论都直接来自反编译源码，带 `文件名.cs:行号`。

---

## 1. 两套绑定表，不要搞混

| 绑定表 | 入口 | 用途 |
|---|---|---|
| **合并键盘**（Combined） | `PCPadInputProvider.GetDefaultCombinedKeyboardBindings()` `PCPadInputProvider.cs:87-...` | **一个键盘当一只手柄用**（单人/手柄模式） |
| **分屏键盘**（Split） | `PCPadInputProvider.GetDefaultSplitKeyboardBindings()` `PCPadInputProvider.cs:55-85` | **一个键盘拆成两个虚拟手柄**，左右分屏双人 —— **本项目用的就是这套** |

**踩坑记录**：按合并表查会得到"交互键 = LeftCtrl"（`Button.X = Key.LeftControl`，`PCPadInputProvider.cs:92`）。
但在分屏模式下，左右两侧各拿到**不同的**键，`Button.X` 只属于右侧那个虚拟手柄。
**用合并表的结论去驱动分屏模式，会有一半的键发错。**

## 2. 分屏权威表（`PCPadInputProvider.cs:55-85` 原文）

|---|---|---|
| `RStickX` 正向 | **RightArrow** | `:76` |
| `RStickX` 负向 | **LeftArrow** | `:77` |

| `RStickY` 正向 | **DownArrow** | `:79` |

注意：**分屏表里没有 `D` 以外的 WASD 之外的移动键**，也没给 `Button.Start` 之外的系统键。
另外 `DpadY`（`:80-81`）也被绑到 P2 的上下箭头 —— 所以 P2 的上下箭头**同时是右摇杆和十字键**。

## 3. 逻辑动作 → 环境按钮 → 物理键（完整推导）

### 第一跳：逻辑动作 → 环境按钮（`PlayerInputLookup.cs:358-363`）

```csharp
LogicalButtonID.PickupAndDrop       => AmbiPadButton.One,     // 捡起/放下
LogicalButtonID.WorkstationInteract => AmbiPadButton.Two,     // 与工位交互(切菜/按按钮/开锅)
LogicalButtonID.Dash                => AmbiPadButton.Three,   // 冲刺
LogicalButtonID.Curse               => AmbiPadButton.Four,
LogicalButtonID.PlayerSwitch        => AmbiPadButton.Five,    // 换人
```

### 第二跳：环境按钮 → 环境手柄按键（`AmbiControlsMappingData.cs:35-59`）

| AmbiPadButton | 对应的 ControlPadInput.Button |
|---|---|
| `One` | `A`, `RB`, `LB` |
| `Two` | `X`, `RTrigger`, `LTrigger` |
| `Three` | `B`, `DPadLeft`, `DPadRight` |
| `Five` | `B`, `Y`, `DPadUp`, … |

`GetSidedLogicalCombo(...)`（`PlayerInputLookup.cs:391-396`）再按玩家在分屏里的**左右侧**，
挑出属于该侧虚拟手柄的那一个按键。

### 第三跳：落到物理键

| 动作 | P1（左半） | P2（右半） |
|---|---|---|
| **捡起/放下** `PickupAndDrop` | `LB` → **LeftShift** | `A`/`RB` → **RightShift** |
| **工位交互** `WorkstationInteract` | `LTrigger` → **LeftControl** | `X`/`RTrigger` → **RightControl** |
| **冲刺** `Dash` | `DPadRight` → **LeftAlt**（也接受 `DPadLeft`=LeftControl） | `B` → **RightAlt** |
| **换人** `PlayerSwitch` | `DPadUp` → **E** | `Y` → **I** |

### 与代码现状核对

`neko/bridge/keyboard_input.py` 的实际映射：

```python
PLAYER1 = {"pickup": "LSHIFT", "chop": "LCTRL", "dash": "LALT", ...}   # ✓ 与推导一致
PLAYER2 = {"pickup": "RSHIFT", "chop": "RCTRL", "dash": "RALT", ...}   # ✓ 与推导一致
```

**结论：当前映射是正确的**（2026-xx 校对）。不要再"顺手改"成合并表的键。

## 4. 但有一个前提必须成立

`PCPadInputProvider` 静态构造里（`PCPadInputProvider.cs:42-46`）：

```csharp
GameDebugConfig debugConfig = GameUtils.GetDebugConfig();
if (debugConfig.m_keyboardType == GameDebugConfig.KeyboardType.Actual) {
    m_allDevices.Add(StandardActionSet.CreateForKeyboard(m_UserKeyboardBindings));
}
```

也就是说 —— **游戏实际用的是"用户键盘绑定" `m_UserKeyboardBindings`，不是上面这张默认表**。
上表只是**默认值**；玩家（或云存档）改过键位，脚本就会失效。

**所以脚本必须保留 `probe_bindings()` 实测兜底**：按一下某个候选键，看厨师有没有动，
以此反推这套键位现在到底是什么。这也解释了为什么"实测探针"是有价值的，而不是多余的健壮性。

## 5. 与切菜/交互有关的两条硬约束（来自 06 号文档，一并记在这里）

1. **必须空手**才能交互：手上有物品时 `m_interactable` 会被手持物顶掉或置 null
   （`PlayerControls.cs:746-758`）。
2. **站距 ≤ 1.0，且在朝向前 180° 半圆内**（`PlayerControls.cs:745`、`:455-458`）。
   ⇒ **本文档特别提醒**：`neko/engine.py` 里的 `self.arrive = 1.8` 是"导航粗到半径"，
   **不等于交互半径**。交互前必须再收紧到 1.0 以内，否则按了也没用。
   这一点需要在实机上验一次（见 `tools/probe_move.py` 的用法）。

---

## 6. 按键的触发方式

交互是 **JustPressed 边沿触发**（`PlayerControls.cs:107-110`、`ClientPlayerControlsImpl_Default.cs:279-282`），
所以必须"**按下 → 松开**"才算一次。`neko/bridge/keyboard_input.py` 的 `tap()` 已经满足
（`key_down` → sleep → `key_up`）。**长按不会连续触发**。
