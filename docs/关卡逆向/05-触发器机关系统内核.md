## 1. 机制概览

### 1.1 一句话

Overcooked! 2 的机关系统**不是事件系统，是一根字符串总线**：

```
某个 MonoBehaviour（触发源）          →  GameObject.SendTrigger("字符串")
  → 同一 GameObject 上所有 ITriggerReceiver.OnTrigger("字符串")
    → 某个 Trigger* 组件判断字符串是否匹配
      → 执行动作（销毁/生成/禁用/点火/改动画/改材质/加载场景…）
      → 也可能再 SendTrigger("另一个字符串") 级联到别的物体
```

全系统只有一条核心 API：

```csharp
public static void SendTrigger(this GameObject _target, string _trigger)
{
    if (_trigger != string.Empty)
    {
        ITriggerReceiver[] array = _target.RequestInterfaces<ITriggerReceiver>();
        for (int i = 0; i < array.Length; i++) array[i].OnTrigger(_trigger);
    }
}
```
`GameObjectUtils.cs:423-433`

三个关键性质，决定了后面所有结论：

1. **只发给同一个 GameObject**。`RequestInterfaces<T>()` 的实现就是 `_obj.GetComponents<T>()`（`GameObjectUtils.cs:69-72`），**非递归**。想爬到父物体必须显式放 `ForwardTriggersToParent`（`ForwardTriggersToParent.cs:6-12`）。
2. **接口调用，不是反射**。所以**没实现 `ITriggerReceiver` 的组件收不到 `SendTrigger`**，哪怕它有一个同名 `OnTrigger(string)` 方法。
3. **只有"恰好等于 `string.Empty`"才会被丢弃**（`GameObjectUtils.cs:425` 用的是 `_trigger != string.Empty`，**不是 `IsNullOrEmpty`**）。所以一个**未序列化的 `string` 字段（值为 `null`）传进 `SendTrigger` 时不会被拦住**，会原样把 `null` 派发给所有 `ITriggerReceiver`。接收端普遍写成 `if (_trigger == m_xxx)` 形式（如 `ServerTriggerAdapter.cs:16`），null 与任何非 null 字符串比较都是 false，所以通常无害；但 `TriggerAnimationOnConveyor.OnTrigger` 是无条件转发（`TriggerAnimationOnConveyor.cs:56-59`），`TriggerDestroy.cs:11` 这类比较在 `m_trigger` 也为 null 时**会意外匹配**。写插件观测器时要能处理 `trigger == null`。

### 1.2 双总线：`SendTrigger` 与 `SendMessage`

系统里其实有**两条互不相通**的字符串总线，这是逆向时最容易踩的坑：

| 总线 | 入口 | 谁能收到 | 证据 |
|---|---|---|---|
| **A. 接口总线** | `GameObject.SendTrigger(str)` | 同 GameObject 上所有 `ITriggerReceiver`（**必须是 public 实现**） | `GameObjectUtils.cs:423-433` |
| **B. 消息总线** | `GameObject.SendMessage("OnTrigger", str)` | 同 GameObject 上**任意名字叫 `OnTrigger` 的方法**（public 或 private，1 个 string 参数） | `ForwardTriggerToTarget.cs:14-20`、`SendTriggerToObject.cs:58-64` |

**只看接口总线会漏掉一整个家族**。下面这批类的 `OnTrigger` 是 **private** 且**没有**声明 `ITriggerReceiver`，因此**只能被消息总线（B）驱动**：

|---|---|---|
| `TriggerCreateObject` | `TriggerCreateObject.cs:18` | 否（private） |
| `TriggerCreateHazard` | `TriggerCreateHazard.cs:31` | 否（private） |
| `TriggerIgniteArea` | `TriggerIgniteArea.cs:12` | 否（private） |
| `TriggerLoadScene` | `TriggerLoadScene.cs:11` | 否（private） |
| `TriggerAudio` | `TriggerAudio.cs:38` | 否（private） |

### 1.3 与其它系统的唯一硬连接：`StaticGridLocation`

机关要影响"能不能走"，唯一通道是**销毁/生成占格物体**。而占格注册/注销只在 `StaticGridLocation` / `DynamicGridLocation` 里：

- 注册：`Awake` → `m_gridManager.OccupyGrid(gameObject, m_gridIndex)`（`StaticGridLocation.cs:15-25`）
- 注销：**只在 `OnDestroy`**（`StaticGridLocation.cs:43-53`）；`OnDisable` 是**空实现**（`StaticGridLocation.cs:39-41`）
- 动态版额外提供 `OnDisable` 注销 + 每帧跟随位置重注册（`DynamicGridLocation.cs:5-44`）

⚠️ 这条差异直接决定了 §3.4 的"格子什么时候才真的空"。

#### 2.1.2 `TriggerZone` —— 玩家/物品进入区域（**无任何过滤**）

数据类（只有字段）：

```csharp

    public string m_onOccupationTrigger;
    public string m_onDeoccupationTrigger;
    public bool   m_fallPad;
}
```
`TriggerZone.cs:3-14`

服务端逻辑（**真正的触发条件**）：

```csharp
private void OnTriggerEnter(Collider other) {
    if (m_collidersOccupying.Count == 0)
        base.gameObject.SendTrigger(m_triggerZone.m_onOccupationTrigger);
    m_collidersOccupying.Add(other);
}
private void OnTriggerExit(Collider other) {
    m_collidersOccupying.RemoveAll(other.Equals);
    if (m_collidersOccupying.Count == 0)
        base.gameObject.SendTrigger(m_triggerZone.m_onDeoccupationTrigger);
}
```
`ServerTriggerZone.cs:51-58`、`ServerTriggerZone.cs:60-67`

**这是本专题最重要的一个结论**：

- **没有玩家过滤**。判据是"`OnTriggerEnter` 收到任何 `Collider`"（`ServerTriggerZone.cs:51`），不检查 layer、不检查 tag、不检查是否 `PlayerIDProvider`，也不检查 `DynamicGridLocation`。
- **没有重量条件**。`m_collidersOccupying` 只是 `List<Collider>` 计数（`ServerTriggerZone.cs:11`、`:46-49`），数量 ≥1 即占用，不看质量、不看数量。
- **是边沿触发，不是电平触发**。列表从 0 变 1 才发 `m_onOccupationTrigger`；1→2（第二个玩家也踩上来）**不重发**（`ServerTriggerZone.cs:53`）。同理，2→1 **不发** `m_onDeoccupationTrigger`（`ServerTriggerZone.cs:63`）。
- **`m_fallPad`**（翻板/落穴）：为 `true` 时每帧清理"已禁用的 collider"，让物体消失后能重新空闲下来（`ServerTriggerZone.cs:24-38`）。
  ⚠️ 该循环在遍历中 `Remove`（`ServerTriggerZone.cs:35`），会跳过下一个元素——「反编译存疑」，但逻辑上是个已知的 list-remove-while-iterating bug。

**跨网络的坑（重要）**：

- `ServerTriggerZone.SyncOccupied()` 被定义（`ServerTriggerZone.cs:40-44`）但**全工程无任何调用者**（grep `SyncOccupied` 只命中定义处）。
- `ClientTriggerZone` 只有一个从未被赋值的 `m_occupied` 字段，**没有 override `ApplyServerEvent`**（`ClientTriggerZone.cs:8`、`:21-24`）。

⇒ **`ClientTriggerZone.IsOccupied()` 永远返回 `false`**。唯一消费者 `ClientPressureSwitchCosmeticDecisions.Update()`（`ClientPressureSwitchCosmeticDecisions.cs:16-35`，用它切材质和按钮下沉位移）因此**永远显示"未占用"外观**。这是一个可观测的、可写探针验证的结论。压力开关的**功能**（发 trigger）在服务端仍然正常，只是**视觉反馈**不动。

`EntityType.TriggerZone` 与 `TriggerZoneMessage` 依然注册在案（`EntityType.cs:27`、`MultiplayerController.cs:114`、`MultiplayerController.cs:460`），属于"协议还在、链路断了"。

### 2.3 连线方式总览

```
                    ┌──────────────────────────────────────────┐
   触发源 ──────────►│ GameObject.SendTrigger(str)  [接口总线]  │
 (Zone/Collision/   └───────────────┬──────────────────────────┘

                    ┌──────────────────────────────────────────┐
                    │  ITriggerReceiver 们                     │
                    └───┬──────────┬──────────┬────────────┬───┘
                        │          │          │            │
        ┌───────────────┘          │          │            └──────────────┐

  TriggerAdapter            TriggerCounter  TriggerWithCooldown    TriggerOnObject
```

**`TriggerCounter` 的一个硬坑**（`ServerTriggerCounter.cs:22-30`）：

```csharp
m_iCounter++;
if (m_iCounter == m_counter.m_count) {        // ← 精确相等，不是 >=
    base.gameObject.SendTrigger(m_counter.m_outputTrigger);
    if (m_counter.m_ResetOnCountReached) m_iCounter = 0;

```

若 `m_ResetOnCountReached == false`，第 N 次之后 `m_iCounter` 变成 N+1、N+2…，**永远不再等于 `m_count`** → **该机关只会放行一次，之后彻底静默**。这是"机关只能用一次"的一个隐藏来源。

**`TriggerWithCooldown` 的初始化细节**（`ServerTriggerWithCooldown.cs:10-15`）：`StartSynchronising` 里把 `m_timeSinceLastTrigger` 初始化为 `m_Cooldown`，所以**开局即可立刻触发一次**，不需要先等一个冷却周期。

## 3. 运行时流程（时序）

### 3.1 加载期：机关是怎么被"接上电"的

机关组件本身是场景里的普通 MonoBehaviour。**Server\* / Client\* 两半是运行时被动态添加的**：

1. 关卡加载完成 → 客户端收到 `GameState.ScanNetworkEntities` → `MultiplayerController.ScanEntities()`（`ClientKitchenLoader.cs:132-141`）
2. `AsyncScanEntities` 先把所有机关类型注册进 `EntitySerialisationRegistry`（`MultiplayerController.cs:460-478`、`:540`、`:553-556`）
3. `SetupSynchronisation` → `LinkAllEntitiesToSynchronisationScripts()`：遍历所有根物体，对每个 `AddSynchronisedType` 的**标记类型**（如 `TriggerZone`）`GetComponentsInChildren(type, includeInactive: true)`，给命中的 GameObject **AddComponent 对应的 Server\* 与 Client\* 组件**（`EntitySerialisationRegistry.cs:163-236`）
4. `StartSynchronisingEntry` 对每个新组件调 `StartSynchronising(标记组件)`（`EntitySerialisationRegistry.cs:238-254`）——**所有 Register 回调、m_xxx 缓存在这一步完成**
5. `GameState.StartSynchronising` → `MultiplayerController.StartSynchronisation()` → `m_bSyncActive = true`（`ClientKitchenLoader.cs:142-146`、`MultiplayerController.cs:579-599`）

⚠️ **在 `m_bSyncActive` 变 true 之前，`SendServerEvent` 全部是空操作**：

```csharp
public virtual void SendServerEvent(Serialisable message) {
    if (MultiplayerController.IsSynchronisationActive()) ServerMessenger.EntityEvent(this, message);
}
```
`ServerSynchroniserBase.cs:55-61`

### 3.2 触发一次机关的完整时序（单机本地双人）

```
[Update 阶段]
  ① 物理引擎回调：ServerTriggerZone.OnTriggerEnter / ServerCollisionTrigger.OnTriggerEnter …
       └─ gameObject.SendTrigger("SomeString")
            └─ 同 GameObject 上所有 ITriggerReceiver.OnTrigger("SomeString")   ← 接口总线，同帧同步
                 └─ ServerTriggerDestroy.OnTrigger 等：执行动作
                      ├─ 纯逻辑（SendTrigger 级联）→ 继续同步递归，同帧完成
                      └─ SendServerEvent(msg) → ServerMessenger.EntityEvent
                           └─ Server.BroadcastMessageToAll
                                └─ LocalLoopbackConnection.SendMessage → **写入批量缓冲，不立即送达**
  …（同一 Update 里，MultiplayerController.Update 还会驱动所有 UpdateSynchronising()，
     见 MultiplayerController.cs:642-708）
[LateUpdate 阶段]
  ② MultiplayerController.LateUpdate()：m_LocalServer.Dispatch() → 批量缓冲发出
       └─ TransmitMessage → 对端 HandleReceivedBytes → 解码 → Mailbox.OnMessageReceived（**同步回调**）
            └─ ClientSynchronisationReceiver.OnEntityEventMessageReceived → ClientXxx.ApplyServerEvent(...)
                 └─ 客户端侧后果生效（Object.Destroy / SetTrigger / 材质切换 / 移动玩家…）
     MultiplayerController.cs:710-717、LocalLoopbackConnection.cs:33-37/49-57、
     BaseConnection.cs:64-77、Mailbox.cs:176-206
```

**关键推论**：服务端动作与客户端可见后果之间**隔着一次 LateUpdate**。

- 在同一帧的 Update 里，`ServerTriggerDestroy` 已经执行完，但物体**还没被 `Object.Destroy`**（`NetworkUtils.DestroyObject` 只做 `SetActive(false)` + 广播，`NetworkUtils.cs:110-114`）
- `StaticGridLocation.OnDisable` 是空的（`StaticGridLocation.cs:39-41`），所以**即使 `SetActive(false)` 了，`GridManager.GetGridOccupant(格)` 仍然返回那个物体**
- 只有等到客户端 `Object.Destroy(entity)`（`ClientSynchronisationReceiver.cs:244`）触发 `StaticGridLocation.OnDestroy`（`StaticGridLocation.cs:43-53`），`DeoccupyGrid` 才执行

⇒ **"触发 → 格子变空"至少跨 1 个 LateUpdate**。自动化脚本绝不能在同一逻辑帧里"触发后立即认为路通了"。

### 3.3 消息频率与批量

- **事件（EntityEvent）**：即时广播，但走连接的批量缓冲，在 `LateUpdate` 的 `Dispatch()` 送出（`ServerMessenger.cs:310-322`、`Server.cs:304-315`）。
- **状态同步（EntitySynchronisation）**：由 `ServerSynchronisationScheduler` 按 **10 Hz**（`kFrameDelay = 0.1f`）驱动，`FastNetworkChefs` 调试选项下 30 Hz（`ServerSynchronisationScheduler.cs:9-16`、`:106-124`）。
- 所有 `ServerTriggerXxx` **都没有 override `GetServerUpdate()`**（默认返回 `null`，`ServerSynchroniserBase.cs:30-33`）→ **机关不产生周期性状态同步，只产生事件**。对自动化是好消息：观测点集中在事件上。

## 6. 对自动化的含义（重点）

### 6.1 运行时如何发现"某个机关刚刚被触发了"

按可靠性 / 覆盖面排序，**推荐 1 + 3 组合**：

#### ✅ 手段 1（首选）：Harmony patch `GameObjectUtils.SendTrigger(GameObject, string)`

```csharp
public static void SendTrigger(this GameObject _target, string _trigger)   // GameObjectUtils.cs:423
```

**这是整个接口总线的唯一咽喉**。一次 patch 能拿到：

- `_target`：**机关本体 GameObject**（`GameObjectUtils.cs:427` 用的是 `_target.GetComponents<ITriggerReceiver>()`，非递归 → 收到的就是行为发生的那个物体）
- `_trigger`：触发字符串

从 `_target` 可以**立刻反查格坐标**：

```csharp
var sgl = _target.GetComponent<StaticGridLocation>();   // GridIndex / AccessGridManager 都是 public
if (sgl != null) { GridIndex idx = sgl.GridIndex; GridManager gm = sgl.AccessGridManager; }
```
`StaticGridLocation.cs:11-13`（`GridIndex` 与 `AccessGridManager` 属性）

**覆盖率**：所有 `Server*` / `Client*` 机关同步器 + 所有实现 `ITriggerReceiver` 的纯 MonoBehaviour（§2.1.1 的 35 处）都经过这里。

**⚠️ 漏网之鱼（必须知道的 3 类）**：

1. **消息总线路径**（§1.2 表 B 的 6 个发送点）—— 尤其 `ForwardTriggerToTarget.cs:18` 和 `SendTriggerToObject.cs:62`。想覆盖必须额外 patch `GameObject.SendMessage(string, object, SendMessageOptions)`。
2. **纯 Animator 路径** —— `TriggerOnAnimator` / `TriggerToggleOnAnimator` / `TriggerAnimatorSetVariable` 的客户端半只调 `Animator.SetTrigger/SetBool/SetFloat`（`ClientTriggerOnAnimator.cs:28` 等），不经过任何 `SendTrigger`。**但它们的入口（Server 半的 OnTrigger）仍然经过总线**，所以只要 patch 了总线，仍能看到"玩家触发了这个机关"这件事，只是看不到它最终改了什么动画参数。
3. **`TriggerTimer` / `TriggerWithCooldown` / `TimedQueue` 的延时放行** —— 它们到点后调 `SendTrigger`（`ServerTriggerTimer.cs:90`、`ServerTriggerWithCooldown.cs:27`、`ServerTimedQueue.cs:117`），**会**被 patch 捕获，但**时间上晚于玩家动作**。这对"等待机关生效"是好事（能拿到准确的生效时刻）。

#### ✅ 手段 2：patch `NetworkUtils.DestroyObject` / `ClientSynchronisationReceiver.DestroyObject`

- `NetworkUtils.cs:110-114` —— 服务端"销毁"入口（`SetActive(false)` + 广播）
- `ClientSynchronisationReceiver.cs:235-245` —— 客户端真正 `Object.Destroy`（**格子真正变空的时刻**）

**这两个是不同时刻**，间隔一个 `LateUpdate`（§3.2）。要在"格子空出来了"这个时刻行动，应该 patch 后者。

#### ✅ 手段 3（兜底，最可靠）：轮询 `GridManager.GetGridOccupant`

```csharp
GameObject GetGridOccupant(GridIndex _index);   // GridManager.cs:82-87
```

**为什么必须轮询**：

- `m_gridOccupancy` 是一个纯 `Dictionary<GridIndex, GameObject>`（`GridManager.cs:9`），**没有事件、没有版本号、没有脏标记**（全文件 139 行，见 `GridManager.cs:64-138` 的写入口）
- **没有任何"格子变化"事件存在**。所有变化都要靠 diff 发现
- 成本极低：41×41 = **1681 次字典查找**（`GridManager.cs:6-7`），5~10 Hz diff 完全可接受

**建议实现**：

```csharp
// 每 100~200ms 一次
var cur = new Dictionary<(int x,int z), GameObject>();
for (int x = -half.X; x <= half.X; x++)
  for (int z = -half.Z; z <= half.Z; z++) {
     var gi = new GridIndex(x, 0, z);
     var occ = gm.GetGridOccupant(gi);
     if (occ != null) cur[(x,z)] = occ;
  }
// diff 出 "newly blocked" / "newly free"
```

⚠️ **不要用 `GridIndex` 当 `Dictionary` 键**——它的 `GetHashCode()` 是 `(m_x<<16) ^ (m_y<<8) ^ m_z`（`GridIndex.cs:49-52`），且有多个有缺陷的 `Equals`/`IEqualityComparer` 实现（`GridIndex.cs:39-62`，与专题 01 §2.1.1 的结论一致）。用自建 `(int,int)` 元组或 int 编码。

#### ❌ 不可用的手段

- **不要用 `GridNavSpace.m_nodeMap` 判断"能不能走"**。它在 `Start()` 里**只构建一次，此后永不更新**：
  ```csharp
  private void Start() {
      m_nodeMap = new bool[2*half.X+1, 2*half.Z+1];
      for (...) m_nodeMap[i,j] = m_gridManager.GetGridOccupant(...) == null;
  }
  ```
  `GridNavSpace.cs:44-56`（`m_nodeMap` 在全工程仅此一处被写，grep 确认）
  ⇒ 它反映的是**关卡开局瞬间**的占用状态。所有机关造成的变化它都不知道。**必须是自动化自己维护动态占用表**。
- **不要监听 `TriggerZone` 的占用状态** —— `ClientTriggerZone.IsOccupied()` 永远返回 `false`（§2.1.2）。要读服务端状态得直接反射 `ServerTriggerZone.m_collidersOccupying`（private，`ServerTriggerZone.cs:11`）。

### 6.2 如何判断"某格刚刚变得不能走 / 刚刚能走了"

三条铁律：

**铁律 1：唯一权威数据源是 `GridManager.GetGridOccupant`**（`GridManager.cs:82-87`）。不是 `m_nodeMap`，不是 `TriggerZone.IsOccupied()`，不是任何 trigger 事件。

**铁律 2："变不能走"可能没有事件，"变能走"几乎总有一帧延迟。**

| 变化方向 | 有事件吗 | 何时真正生效 |
|---|---|---|
| 机关销毁占格物 → 格空 | 有（`DestroyEntity` / `SendTrigger`） | **LateUpdate 之后**（`ClientSynchronisationReceiver.cs:244` → `StaticGridLocation.cs:43-53`） |
| 机关生成占格物 → 格被占 | **可能没有**（`TriggerCreateObject` 走消息总线；`ServerSpawnPrefab` 走 SpawnEntity 通道） | 新物体 `Awake` → `OccupyGrid`（`StaticGridLocation.cs:15-25`） |
| 传送带搬运物品 | **完全没有** | 搬运协程执行中（`ServerConveyorStation.cs:198-203`） |
| 玩家自己走过去（`DynamicGridLocation`） | **完全没有** | 每帧 `Update`（`DynamicGridLocation.cs:5-26`） |

⇒ **结论：不要依赖事件来更新地图，永远靠轮询 diff 兜底。** 事件只用来"提前知道要重新采样了"。

**铁律 3：识别"机关型占格物"要排除玩家自己。**

`GridManager.GetGridOccupant` 会返回**玩家的 GameObject**（玩家挂 `DynamicGridLocation`，「推断」——`DynamicGridLocation.cs` 是通用组件，具体谁挂了它「未验证」）。别忘了加 `GetComponent<PlayerIDProvider>() != null` 的排除（`PlayerIDProvider.cs:5`、`PlayerControls.cs:8` 都标注了 `[RequireComponent(typeof(PlayerIDProvider))]`）。

### 6.3 应该在动作序列的哪些地方插入"重新取地图"

按优先级列出**必须重新采样**的时机：

| # | 时机 | 为什么 | 实现方式 |
|---|---|---|---|
| 1 | **开机后，等 `MultiplayerController.IsSynchronisationActive()` 变 true 再采第一张图** | 之前 `StartSynchronising` 还没跑，`Server*` 组件的回调没注册、`GridNavSpace.Start` 可能还没执行 | 轮询 `IsSynchronisationActive()`（`MultiplayerController.cs:596-599`） |
| 2 | **每次 patch 到 `SendTrigger` 之后的一个 LateUpdate** | 服务器动作已执行，客户端后果已落地 | patch 里打脏标记，在 `LateUpdate` 之后（或下一个 `Update`）采样 |
| 3 | **每次 patch 到 DestroyObject 之后** | 格真正变空的唯一时刻 | `ClientSynchronisationReceiver.DestroyObject` postfix |
| 4 | **每次玩家完成一次交互（拾取/放置/交互开始/结束）之后** | `ServerInteractable.cs:84-111` 与 `ServerAttachStation` 会带动物品占格变化 | 订阅 `Interactable` 的三个 trigger 字段（也可由手段 1 顺带捕获） |
| 5 | **每 N 帧无条件 diff 一次（N=5~10）** | 兜住传送带、移动平台、玩家自身移动、火灾等**无事件**来源 | 定时任务 |
| 6 | **场景名变化时全量重置** | `TriggerLoadScene` 会把整个场景换掉（`TriggerLoadScene.cs:11-17`） | 监听 `SceneManager.sceneLoaded`，或每帧比较 `SceneManager.GetActiveScene().name` |
| 7 | **检测到 `SkipToEnd()`** | `TriggerLevelExit.cs:16-20` 会直接结束关卡 | 轮询对局状态 |

**额外必须插入"等待玩家控制权恢复"的时机**（否则发出去的按键会丢）：

### 6.5 一句话总结（给插件作者）

> **机关的"触发"是一条字符串事件，能用一个 Harmony patch 全量捕获；但机关的"效果"绝大多数是改 GameObject 的存活性/显隐，而"能不能走"的唯一真相在 `GridManager.GetGridOccupant` 这个字典里，且它没有任何变更通知。所以：事件用来"知道发生了什么"，轮询 diff 用来"知道现在能不能走"，两者缺一不可。**
