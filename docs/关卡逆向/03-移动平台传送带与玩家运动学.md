## 1. 机制概览

### 1.1 三条完全不同的"带动"通道，绝不要混为一谈

游戏里"玩家/物品被地面带着走"有 **三套互不相通的实现**，触发条件、物理语义、脚本后果都不一样：

| 通道 | 谁实现 | 作用对象 | 传播方式 | 典型关卡物件 |
|---|---|---|---|---|
| **A. 动态父子挂接** | `IParentable` + `DynamicLandscapeParenting` | 玩家（厨师） | `transform.SetParent(平台的挂接点)`，靠层级关系跟着走 | 移动平台、`PushableObject`、`Teleportal` 挂接点 |
| **B. 移动表面速度** | `IMovingSurface`（**全工程只有 `Travelator` 一个实现**） | 玩家（厨师） | 每帧读取地面碰撞体上的 `IMovingSurface`，把表面速度当作额外位移叠加 | 只有传送带 |
| **C. 推力 / 风 / 冲击** | `IWindSource` → `WindAccumulator`、`ApplyImpact`、`AddForce` | 玩家 + 物品 | 每 1/60 秒直接 `MovePosition` 或改写速度 | 风区、风箱、水枪、火焰、投掷物命中、Dash 对撞 |

**关键结论：移动平台不走 B 通道。** `IMovingSurface` 在全部 2365 个 .cs 里只有两个引用点：接口定义本身（`IMovingSurface.cs:3-8`）、唯一实现 `Travelator`（`Travelator.cs:3`）、唯一消费者 `SurfaceMovable`（`SurfaceMovable.cs:13-15, 56`）。搜遍全工程 **没有任何** `Waypoint` / `Patrol` / `PingPong` / `Oscillat` / `Mover` 脚本 —— 也就是说**引擎里不存在"自动巡航的移动平台"**，平台的位移全部来自"有人驾驶"（见 §2.2）。

#### 2.1.4 `ClientPlayerControlsImpl_Default` —— 运动的核心循环

这是全网唯一真正写速度的地方（`ClientPlayerControlsImpl_Default.cs:393-466`）：

**四个必须记住的性质：**

1. **帧率无关**：外层按 `TimeManager.GetDeltaTime` 累加、内层固定 1/60 消化（`:395, 405-407`）。30fps 时一帧跑 2 个子步，10fps 时一帧跑 6 个子步，位移速度不变。
2. **无加速度**：速度是**每子步直接赋值**（`:434`），不是插值逼近。下一节会给出行之有效的证明。
3. **位移方向 = 输入方向**，不是朝向（`:414` 用的是 `vector`）。所以"按 D 立刻向右走"，转身动画/朝向跟不上但位置已经动了。
4. **Dash 是"速度曲线"而不是"一次性冲刺"**：`m_dashTimer` 从 `DashTime`(=1) 递减，混合系数 `n = 0.5(1-cos(π·m_dashTimer/DashTime))`（`MathUtils.cs:77-81`）从 1 平滑降到 0。也就是**Dash 开始时速度为 8，之后 1 秒内平滑回落到 4**。

摩擦/表面处理函数（`:852-870`）：

```csharp
private Vector3 ProgressVelocityWrtFriction(Vector3 _gameplayVelocity /*=m_lastVelocity*/,
        Vector3 _physicalVelocity /*=刚体速度*/, Vector3 _targetVelocity, PlayerPhysicsSurfaceProperties _surface) {
    Vector3 n  = m_controls.GroundNormal;                          // :854 地面法线
    Vector3 t1 = Vector3.Cross(n, Vector3.forward).normalized;     // :855
    Vector3 t2 = Vector3.Cross(t1, n).normalized;                  // :856
    Vector3 a  = new Vector3(Dot(t1, _gameplayVelocity),
                             Dot(n,  _physicalVelocity),
                             Dot(t2, _gameplayVelocity));          // :857
    float sm   = (_surface == null) ? 1f : _surface.SpeedMultiplier;   // :858
    float slip = (_surface == null) ? 0f : _surface.Slippiness;        // :859
    float slid = (_surface == null) ? 0f : _surface.Slidiness;         // :860
    float k = MathUtils.Remap(slip, 0f, 1f, 1f, TimeManager.GetDeltaTime(...)); // :861
    Vector3 w  = new Vector3(k, 0f, k);                            // :862
    Vector3 v2 = sm * _targetVelocity.MultipliedBy(w) + a.MultipliedBy(Vector3.one - w); // :863
    Vector3 v3 = t1 * v2.x + n * v2.y + t2 * v2.z;                 // :864
    float  m4  = (1f - n.y) * Mathf.Clamp01(slid);                 // :868
    Vector3 v5 = slid * (n.WithY(0f).SafeNormalised(Vector3.zero).x * t1
                       + n.WithY(0f).SafeNormalised(Vector3.zero).z * t2);     // :867
    return (1f - m4) * v3 + m4 * v5;                               // :869
}
```

**平地 + 无 `PlayerPhysicsSurface`（最常见的关卡情况）**：
`sm=1, slip=0 → k=1 → w=(1,0,1)`；`a` 的权重 `(1-w)=(0,1,0)` 只剩 Y 分量；`slid=0 → m4=0`。
代入得 `v = t1·tx + n·(n·v_phys) + t2·tz`。对 `n = Vector3.up`：`t1 = (1,0,0)`、`t2 = (0,0,1)`，于是

> **最终速度 = (目标速度.x, 原竖直速度, 目标速度.z)** —— 水平分量被**完全替换**，竖直分量保留（保存下落/跳跃的竖直动量）。
> **⇒ 平地无惯性、无加速、无减速：按下即 4 u/s，松开即 0 u/s。位移 = 4 × 按住秒数。**

> **「推断」斜坡**：`n` 倾斜时 `t1 = Cross(n, forward).normalized` 退化为"沿坡面切向"，`t2` 恒等于 `forward`。沿坡走时速度模长守恒（4 不变），横切坡面时结果近似纯世界 Z 方向、被碰撞解算顶出。**需要在斜坡关卡做运行时验证。**
>
> **「反编译存疑」`MovePosition` 与 `velocity` 的叠加**：`SetVelocity`（`:434`）与 `ApplyGroundMovement→MovePosition`（`:436, 926-930`）在同一子步内先后调用，两者在 Unity 内部的合成顺序属于引擎行为，`.cs` 无法判定。**传送带上"4 + 带速"这个结论方向可信，精确合成建议实测标定。**

其它相关函数：
- 压制移动：`Update_MovementSuppression`（`:340-371`）—— 投掷瞄准（`m_aimingThrow`）或处于会话交互（`m_sessionInteraction != null`）时把 `m_movementInputSuppressed = true`，**位移归零**；解除条件要么是摇杆回中（`sqrMagnitude < 0.25²`），要么是方向相对"上次记录的方向"偏转 ≥ `m_analogEnableAngleThreshold`(=15°，`PlayerControls.cs:291`)。

> **「推断」/「反编译存疑」**：`AddForce(ForceMode.Acceleration)` 是往"下一物理步的力累加器"里加，而调用频率（60Hz）与物理步频（默认 `Time.fixedDeltaTime = 0.02` → 50Hz）不同，因此**实际下压加速度会按 60/50 的比例被放大**；同时 `SetVelocity`（`:434`）每个子步都会重写速度（竖直分量从物理速度里取回，所以重力仍能积累）。最终表现是"贴地 + 斜坡上缓慢下滑"。**精确数值必须实测**，本文不给出"净重力加速度 = 12 u/s²"这种断言。

**权威位移逻辑**（`ServerPilotMovement.cs:54-89, 105-143`）：

```csharp
public override void UpdateSynchronising() {
    float deltaTime = TimeManager.GetDeltaTime(base.gameObject);      // :56
    m_pilotMovement.RigidbodyMotion.SetKinematic(false);              // :61
    if (m_controlScheme != null && Update_Movement(deltaTime)) {      // :62  ★ 有驾驶员 → 驾驶员说了算
        m_gridTarget = null; return;                                  // :64-65
    }
    if (!m_gridTarget.HasValue) m_gridTarget = GetNearestGridPosition();   // :67-70  ★ 无驾驶员 → 吸附最近格心
    float num = Mathf.Log(2f) / m_pilotMovement.SnapHalfLife;         // :72  半衰期 0.1s → 速率 6.93 /s
    Vector3 velocity = (m_gridTarget.Value - base.transform.position) * num;   // :73
    m_pilotMovement.RigidbodyMotion.SetVelocity(velocity);            // :74
    if (velocity.sqrMagnitude > 0.3f) { /* 反注册旧格区 + 注册新格区 */ }        // :75-88
}

private bool Update_Movement(float _deltaTime) {                      // :105-143
    float value = m_controlScheme.m_moveX.GetValue();                 // :107
    float z = 0f - m_controlScheme.m_moveY.GetValue();                // :108
    Vector3 vector = new Vector3(value, 0f, z).SafeNormalised(Vector3.zero);   // :109  ★ 世界轴，与平台朝向无关
    if (vector.sqrMagnitude > 0.040000003f) {                         // :110  ★ 死区 |v| > 0.2
        m_gridManager.DeoccupyGridRegion(m_min, m_max);               // :115
        if (GridBoxCast(..., vector, 0.3f, ...)) {                    // :116  前方 0.3u 探测
            SetVelocity(MoveSpeed * vector); return true;             // :118  ★ 4 u/s
        }
        if (|vector.x| > 0.3f && GridBoxCast(..., Sign(x), 0.3f, ...)) {  // :121-125  轴向滑行回退
            SetVelocity((MoveSpeed*Sign(x), 0, 0)); return true; }
        if (|vector.z| > 0.3f && GridBoxCast(..., Sign(z), 0.3f, ...)) {  // :126-130
            SetVelocity((0, 0, MoveSpeed*Sign(z))); return true; }
        /* 都失败 */ m_pilotMovement.RigidbodyMotion.SetVelocity(Vector3.zero);   // :134  ★ 完全卡死
        return true;                                                  // :140
    }
    return false;                                                     // :142  输入回中 → 交给吸附逻辑
}
```

**要点：**
1. **平台速度 = `PilotMovement.MoveSpeed` = 4 u/s**，与厨师同速。方向是**世界轴**（`new Vector3(moveX,0,-moveY)`），与平台自身朝向、摄像机朝向都无关（`:109`）。
2. **驾驶不是自由移动，而是"必须前方 0.3u 内的网格区域全部空闲"**（`:91-103` 的 `GridBoxCast` 用 `TryOccupyGridRegion` 同时做"检测 + 占位"）。占据物包括其它平台、台面、传送带、地上的物品。
3. **被挡住时的回退**：斜向输入被挡 → 尝试单轴滑行；单轴也被挡 → 速度置 0（平台"顶住"不动），不会挤开东西。
4. **无人驾驶会自己"归位"**：`m_gridTarget` 只在"第一次进入无驾驶状态"时取一次最近格心（`:67-70`，注意 `m_gridTarget` 命中后不再更新），随后以半衰期 0.1s 的指数衰减速度滑向该格心。**约 0.3~0.5 秒内平台会回到"驾驶员下车那一刻所在格"的格心**——这带来一个非常重要的脚本性质：**松手后平台会自己停在格心附近，位置基本可预测**。
5. 平台移动时实时改占用网格：`DeoccupyGridRegion(m_min,m_max)` + `TryOccupyGridRegion(新区域)`，失败则回滚占旧区域（`:75-88`）；区域范围由碰撞体包围盒缩进 0.15 后换算成格坐标（`:30-40`）。

**B. 物理摩擦（A 通道关闭时的兜底）**
平台是一个 `isKinematic=false`、带速度的动态刚体（`ServerPilotMovement.cs:61, 74`），厨师站在它的碰撞体上 → 由 PhysX 的接触摩擦把厨师"拖着走"。
> **「反编译存疑」**：Unity 2017.4 / PhysX 对"动态刚体在移动平台上被摩擦拖动"的实际效果很差（会被缓慢甩下、边缘滑落），而且完全没有代码显式处理。**是否真的靠摩擦带走玩家，必须实测。**

**C. 完全没有第三条路**
平台不写 `SurfaceMovable`，所以 `ClientPlayerControlsImpl_Default.ApplyGroundMovement`（`:926-930`）在读 `m_controls.SurfaceMovable.GetVelocity()` 时，站在平台上得到的是 **`Vector3.zero`**（`SurfaceMovable.cs:42-52`：`m_surface == null` → 速度为 0；`m_surface` 只在 `OnGroundChanged` 里通过 `RequestInterface<IMovingSurface>()` 赋值，`:54-70`）。

**物品**：靠 `IParentable` 的 `GetAttachPoint`（`ObjectContainer` 是最朴素的一种，`GetAttachPoint` 直接返回自身 transform，`ObjectContainer.cs:3-13`），以及 `GridAutoParenting`（`Awake` 时把自己挂到所站格子的占用物下，`GridAutoParenting.cs:11-20`）。平台上的台面若挂了 `IParentable`，其上的物品会跟着平台走。

> **平台"路径可读吗"？** 平台没有自己的路径数据：位置完全由驾驶员输入决定（或无人时向"最近格心"指数衰减）。**没有任何 `.cs` 里存着平台的巡航点。** 所以脚本要么自己规定驾驶路线，要么用格心吸附把它当"格子间传送"。这是**结论**，不是猜：全工程不存在 waypoint/patrol 脚本（见 §1.1）。
>
> ⚠️ **「未验证」的例外**：平台物体上如果挂了 Unity `Animator` + 动画剪辑（纯资产层），位移可以完全不经过任何 `.cs`。`.cs` 侧无法排除，需在场景里确认。

#### 2.3.1 `IMovingSurface`：全工程唯一实现


然后每个 1/60 子步把表面速度当位移叠加（`ClientPlayerControlsImpl_Default.cs:436, 926-930`）：

```csharp

```

> **⇒ 传送带的作用方式是"每子步额外平移 `带速 × 1/60` 个单位"**，与玩家自己的 4 u/s 速度**相加**（不是取最大、不是覆盖）。每秒额外前进 `带速` 个世界单位 = `带速/1.2` 格。
> **注意：`Movement(velocity, _deltaTime)` 用的是 `Rigidbody.MovePosition`，而玩家自身的速度走 `velocity` 积分 ——「反编译存疑」两者的精确合成由 Unity 决定，`4 + 带速` 的方向性结论可信，绝对值建议实测。**

#### 2.3.2 `Travelator` 的方向判定（最容易写错的地方）

```csharp
public enum XZDirection { Leftwards, Rightwards }                        // Travelator.cs:5-9
[SerializeField] public  float m_speed = 1f;                             // :12
[SerializeField] private XZDirection m_directionXZ = XZDirection.Rightwards;  // :15
[SerializeField] private float m_border;                                 // :18
[SerializeField] public  float m_materialScrollMultiplier = 0.3f;        // :21  （只影响贴图滚动）

private Vector3 GetSurfaceVelocity() {                                   // :134-137
    return (!base.enabled) ? Vector3.zero : (m_speed * GetTravelDirection());   // :136  ★ 组件禁用 → 带速为 0
}
private Vector3 GetTravelDirection() {                                   // :167-175
    return m_directionXZ switch {
        XZDirection.Leftwards  =>  base.transform.right,                 // :171
        XZDirection.Rightwards => -base.transform.right,                 // :172  ★ 默认值是「-right」！
        _ => Vector3.zero,
    };
}
```

> ⚠️ **默认值 `Rightwards` 对应的是 `-transform.right`（局部 -X 方向）**，名字与实现是反的。判断某条传送带往哪跑**必须读 prefab 上的 `m_directionXZ` 和物体的 `transform.right`**，不能靠名字猜。
> **「未验证」**：具体关卡里每条传送带的 `m_speed`（默认 1）、`m_directionXZ`、`m_border`、以及 `transform.right` 的实际朝向。

#### 2.3.3 相邻传送带连接与"提前交接"

```csharp
public Vector3 CalculateVelocityAtPoint(Vector3 _point, IMovingSurface _prevSurface) {   // :50-62
    Vector3 v = Vector3.zero;
    if (CalculateForPrevSurface(_prevSurface, _point, ref v)) return v;   // :53  ★ 1. 上一帧站的带子优先
    if (CalculateForBorders(_point, ref v))                   return v;   // :57  ★ 2. 越界"边界带"次之
    return GetSurfaceVelocity();                                          // :61  ★ 3. 否则用自己的速度
}
```

1. `CalculateForPrevSurface`（`:69-95`）：如果**上一帧踩的那条带子**的"下一条"就是自己，且两条方向点积 `< 0.5`（即夹角 > 60°，典型是反向对撞的带子），并且 `_point` 在两条带子的连线之间（`VectorUtils.ProgressUnclamped` ∈ [0,1]，`:86-87`），就用**上一条带子的速度**。→ 视觉/物理上是"被上一条甩过来接力"。
2. `CalculateForBorders`（`:97-110`）：用 `_point` 相对自身中心在 X/Z 上超过 `m_border` 判断"越过了哪条边界"（`GetBorderDirection`，`:112-132`），若那条边上的邻居带子的"下一条"是自己，就用**邻居的速度**。
3. `GetNextTravelator()`（`:139-147`）= 沿自己的行进方向取邻格（`GetAdjacentGridIndex` 用 `Mathf.Round(direction)`，`:160-165`）→ `GetGridOccupant` → `RequestComponent<Travelator>()`（`:149-158`）。**⇒ 传送带的拓扑是"网格邻接 + 朝向"，而不是显式连线。** 网格来自 `StaticGridLocation`（`Travelator.Start`，`:31-33`）。

#### 2.3.4 `TravelatorCosmeticDecisions`

`TravelatorCosmeticDecisions.cs:1-13` 只有 13 行，`[RequireComponent(typeof(Travelator))]`，`Start` 里取一次组件——**没有任何逻辑**。贴图滚动是由 `Travelator.SetSpeedOnMaterial()` 直接写 shader 的 `_speed`（`Travelator.cs:37-48`，值 = `m_speed * m_materialScrollMultiplier`，默认 0.3），**纯视觉、与物理无关**。

### 4.3 由上面推导出的实用换算（格 = 1.2 世界单位）

| 场景 | 换算 |
|---|---|
| 直走一格 | 1.2 / 4 = **0.300 s** 按住方向键 |
| 斜走一格（两轴各 1 格） | √(1.2²+1.2²)/4 = **0.424 s** |
| 每 1/60 子步位移 | 4/60 = **0.0667 u** ≈ 0.0556 格 |
| 180° 掉头（仅转向） | ≈ 0.157 s（≈10 子步 × 19.1°） |
| 全程 Dash 位移 | 4 + 4×∫₀¹S(u)du = 4 + 2 = **≈6.0 u ≈ 5 格 / 1 s** |
| Dash 起始瞬时速度 | 8 u/s（2 倍速），1 秒内平滑回落到 4 |
| 撞火击退（以 4 u/s 撞入） | 8 u/s × 0.2 s = **1.6 u ≈ 1.33 格** |
| 风箱推人 | 10 u/s × 0.2 s = **2.0 u ≈ 1.67 格** |
| 传送带（默认 m_speed=1） | 顺向 5 u/s → **0.24 s/格**；逆向 3 u/s → **0.40 s/格**；不按键也漂 **0.83 格/s** |
| 风区（风速 w） | 每秒额外漂 `w` u = `w/1.2` 格 |

> **Dash 位移的推导**：混合系数 `n = 0.5(1-cos(π·m_dashTimer/DashTime))`（`MathUtils.cs:77-81`），`m_dashTimer` 从 1 线性降到 0。速度 `v(t) = (1-n(t))·4 + n(t)·8 = 4 + 4n(t)`。距离 = ∫₀¹[4+4·S(1-t)]dt = 4 + 4·0.5 = 6 u。**前提是 Dash 期间朝向不变且方向键一直按着**；若松键，基础项归零，Dash 速度也会跟着变小（`:423` 的两项混合）。

## 5. 对自动化的含义

### 5.1 按键 → 位移的标定规则

1. **`位移 ≈ 4 u/s × 按住秒数`（无加速度、无惯性）**，依据：平地无 `PlayerPhysicsSurface` 时速度被直接赋值（§2.1.4 的推导）。
   **但请务必在运行时读 `PlayerControls.Movement.RunSpeed` 再标定**，不要硬编码 4（prefab 可能改写）。
2. **按住时间 = 距离 / 4**，1 格 ≈ 0.30 s。因为**没有任何加速度或刹车**，多按 0.1 s 就多走 0.4 u（≈1/3 格），会明显偏离目标格心。建议：**走一格按 0.28~0.30 s，然后立刻松开读实际坐标做闭环修正**，而不是一次性开环连按多格。
3. **方向与朝向无关**：按 D 就向世界 +X 走（`ClientPlayerControlsImpl_Default.cs:414`）。但**交互目标与朝向强相关**：
   - `LevelConfigBase.m_gridSelection` 默认 true（`LevelConfigBase.cs:13`）→ 走 `InteractWithItemHelper.GetFacingGridOccupant` 分支（`PlayerControls.cs:745` → `InteractWithItemHelper.cs:186-210`），**目标是"朝向前方那一格"的占用物**，有效夹角到 ±135°（`:89`），取朝向点积最大者。
   - 所以**掉头后必须等 ≈0.16 s 让朝向转过来再按交互键**，否则会去交互身后的台面。
4. **键盘是八向的**：同时按 D+S = 归一化斜向（±0.707/±0.707），目标速度仍是 4，但位移是斜向的。要么只用单轴，要么按 `0.424 s` 算斜向一格。
5. **保持游戏窗口前台**：`Application.isFocused == false` ⇒ 所有输入读 0（`PlayerControls.cs:455` + `GateLogicalValue.cs:13-20`）。
6. **避免一切会被 Suppress 的状态**：过场、表情轮盘、对话框、重生期间（§2.1.8）。可在脚本里轮询 `PlayerControls.IsSuppressed()`（`PlayerControls.cs:494-497`）作为"别发按键"的信号。
7. **准星/瞄准会冻结移动**：手持可投掷物且按住使用键 → `m_movementInputSuppressed = true` → 速度归零（`ClientPlayerControlsImpl_Default.cs:340-371, 415-418`）。**投掷后必须先松开使用键，厨师才会动。**
8. **喷射会冻结移动**：`MovementScale = 0`（`ClientSprayingUtensil.cs:104`）。
9. **Dash 是"1 秒加速曲线"而非瞬移**：全程 ≈6 u、耗时 1 s。若只想跑 1 格（1.2 u），Dash 起手（8 u/s）按 ~0.15 s 就够，然后松开 Dash 与方向键；靠"整段 Dash"来做 1 格微调是错的。
10. **判定"开始/结束可控"**：轮询 `PlayerControls.enabled`（驾驶/推箱期间为 false）与 `PlayerControls.m_bRespawning`（`PlayerControls.cs:303-304`）。

### 5.2 【核心问题】移动平台格子在寻路里到底该怎么处理

**结论：不能把占用网格当作厨师的可行走图；移动平台格对厨师毫无阻挡意义。**

理由链（每一步都有源码）：

1. **`GridNavSpace.m_nodeMap` 只在 `Start` 采样一次，之后永不刷新**（`GridNavSpace.cs:44-56`）。其判据是 `m_gridManager.GetGridOccupant(index) == null`（`:53`）。
2. **它只被"老鼠 NPC"消费**：全工程 `GridNavSpace` 的消费者只有 `GridNavigator`（`GridNavigator.cs:18, 48`），而 `GridNavigator` 只出现在 `RatBehaviour`（`RatBehaviour.cs:3`）与调试用的 `DebugPathSelector`（`DebugPathSelector.cs:3`）。**厨师根本不用它寻路。**
3. **平台确实是"占用物"**，而且是**动态的**：出生格由 `StaticGridLocation` 占（`StaticGridLocation.cs:20-25`），移动中由 `ServerPilotMovement` 反注册/注册格区（`ServerPilotMovement.cs:75-88, 115-135`）。
4. 于是产生**时间错位**：
   - 平台**出生格** → 在 `Start` 快照里被**永久标记为墙**，即使平台早就开走了；
   - 平台**后来驶入的格** → 快照里仍是"可走"，但物理上正被平台占着。
   两个方向都错。**这个快照只能用于"老鼠该往哪跑"，不能用于厨师。**
5. **游戏自己也承认这两类占用物不是实心障碍**：`InteractWithItemHelper.cs:46` 把 `Hazard` / `Travelator` / `MovingPlatform` 三个 tag 从"阻挡视线"里排除掉。

**⇒ 自动化侧的正确做法（建议）：**

```
厨师可行走图 = 自建，不要用 GridManager 占用表，也不要用 GridNavSpace

单格判据（三层，全部在插件里自己算）：
  ① 静止障碍层：把"已知的台面/墙体"标为 blocked
     （可用 GameObject.layer / 组件类型判定，或直接抄一份静态关卡地图）
  ② 地面层：该格中心向下 Raycast(landscapeMask, ~2u)，有命中的才叫"有地板"
     —— 这与 GroundCast.cs:126-155 用的是同一套判据
  ③ 动态覆盖层（每帧重算，别缓存）：
     - 该格若有 tag == "MovingPlatform" 的占用物 → **可站上去，不是墙**
       （但要标记成"会动"，参与时间窗规划）
     - 该格若有 tag == "Travelator" 的占用物 → **可站上去**，且带速度矢量
       （速度 = m_speed * 行进方向，行进方向要读 prefab，默认是 -transform.right）
     - 该格若有 tag == "Hazard" → 可站上去但会吃击退（§2.4.2）
     - 其它占用物（灶台/案板/墙） → blocked
```

**逐条回答"该绕开还是该走"：**

| 格子类型 | 寻路里怎么处理 | 原因 |
|---|---|---|
| 移动平台**当前**所在格 | **不是墙，可走/可站**；标记为"会动"，规划时要留出平台移走后的空格 | 平台是动态刚体地面，玩家站得上去（`ServerPilotMovement.cs:61` 非运动学；`InteractWithItemHelper.cs:46` 不视作阻挡） |
| 移动平台**出生格**（已开走） | **必须当成可走**，绝不能因为占用表里有它就绕开 | `GridNavSpace` 快照把它永久记成墙（`GridNavSpace.cs:53` 一次性采样），是过时数据 |
| 移动平台**将要**驶入的格 | 占用表说"空闲"，但物理上会被平台挤占；**派厨师过去要选平台不在的时窗** | `ServerPilotMovement.cs:115-135` 只在移动时更新占用，且被挡时速度归零 |
| 传送带格 | **可走但必须补偿**：顺向 `4+speed`、逆向 `max(0, 4-speed)`、静止也会漂 | `Travelator.cs:134-137` + `ClientPlayerControlsImpl_Default.cs:929` |
| `Hazard`（火）格 | 可走但**必须绕**（击退 1.33 格的位移会破坏时序），并且火的碰撞体随点火状态开关 | `ClientPlayerControlsImpl_Default.cs:835-850`；`ClientFireHazard.cs:25-36` |

**还有一个更省事的等价做法**：不要查任何占用表，**直接问物理**。对目标格中心做向下 Raycast 判断"有没有地板"、做一次小 `OverlapBox` 判断"有没有实心阻挡物"，用碰撞体自身的 tag/组件来分类。占用表只能回答"这一格上注册了谁"，回答不了"这格能不能站"。

### 5.3 传送带上的按键补偿表

设带速 `s`（沿带方向的矢量，默认 `m_speed=1`，方向 = `-transform.right` 当 `m_directionXZ == Rightwards`）：

| 目标 | 需要按住的时间（走 1 格 = 1.2 u） | 备注 |
|---|---|---|
| 顺带方向走 1 格 | `1.2 / (4 + s)` | `s=1` → 0.24 s |
| 逆带方向走 1 格 | `1.2 / (4 - s)`，**若 `s >= 4` 则永远走不动** | `s=1` → 0.40 s |
| 垂直于带方向横穿 1 格 | `1.2 / 4` 但**会被侧向漂移**：横穿期间沿带方向漂移 `s × t` | 横穿 1 格用 0.3 s，漂移 0.3 u = 0.25 格 → 终点要后撤 0.25 格来补偿 |
| 站着不动 1 s | 沿带方向漂 `s` u = `s/1.2` 格 | **"原地等待"在传送带上不成立** |

> **应对策略**：优先把传送带当成"确定性传送带"来规划——**人上去、松开键，让它自己送**比"一边走一边补偿"更可预测（因为"带速 vs 4 u/s"的合成关系存在 §2.1.4 提到的 `MovePosition` + `velocity` 合成歧义）。送 1 格需要 `1.2/s` 秒（`s=1` → 1.2 s）。

### 5.4 移动平台上的按键补偿与脚本模板

**A. 平台是谁在动？**
- **必须有一个厨师在 `Terminal` 上驾驶**（§2.2.2）。⇒ 双人关卡的脚本必须**分工**：A 厨师去摇杆台驾驶，B 厨师站平台上被运走。
- **驾驶中的厨师完全不能做别的**（`PlayerControls.enabled = false`，`ServerSessionInteractable.cs:33`），而且**任何按钮按下都会把会话踢掉**（`:85`）。⇒ 驾驶阶段只能发方向键。
- 驾驶时方向键是**世界轴**（`ServerPilotMovement.cs:109`），与镜头无关。→ 脚本可以直接用世界方向表映射按键。

**B. 平台速度 = 4 u/s，所以：**
- 平台走一格同样 ≈ 0.30 s。移动到目标格心后，**松开方向键**，平台会用 ~0.3–0.5 s 自动吸附到最近格心（`ServerPilotMovement.cs:67-74`）。**这是脚本极大的便利：不用精确定位，松手就归位。**
- 但请注意吸附目标是在"**松手瞬间平台所在的格**"（`:67-70` 只取一次 `m_gridTarget`），如果松手时平台刚好跨格中点，可能会吸到"后面那一格"。**建议在目标格中心附近才松手。**

**C. 站在平台上的厨师（乘客）**

| 关卡配置 | 乘客行为 | 脚本应对 |
|---|---|---|
| `m_disableDynamicParenting == false`（动态挂接开启） | 厨师被 `SetParent(平台挂接点)`（`DynamicLandscapeParenting.cs:42`），随平台刚性移动；自己按键走的是**相对平台的 4 u/s**（世界速度 4 u/s 叠加平台运动） | 按"平台已停稳"再走；不要在平台运动时反向走（净速可能为 0） |
| `m_disableDynamicParenting == true`（代码默认！） | 无挂接，只能靠 PhysX 摩擦（**未验证是否可靠**）；玩家很可能被平台"从脚下抽走" | **必须有主动补偿**：平台朝 +X 跑时，乘客要周期性点按 A（−X）来"跟住"；或者干脆不让厨师站在会动的平台上 |

> **运行时探针（强烈建议加）**：关卡加载后检查
> `GameUtils.GetLevelConfig().m_disableDynamicParenting`，
> 并在厨师站上平台时检查 `player.DynamicLandscapeParenting != null && player.transform.parent != null`。
> 两者一起就能确定当前关卡走的是 A 通道还是摩擦通道，从而切换脚本策略。

**D. 传送带式的"确定性"更强**：如果关卡里有传送带，**优先用传送带完成运送，把平台驾驶限制在开关式（开到位→停）**，因为传送带的位移是代码显式写入的（`ClientPlayerControlsImpl_Default.cs:929`），比平台+摩擦可预测得多。

### 5.5 需要"额外补偿时间"的清单

| 情形 | 额外时间 / 补偿 |
|---|---|
| 掉头 180° 后立刻交互 | +0.16 s（等朝向） |
| 投掷/瞄准后恢复移动 | 必须**松开使用键**（松开瞬间即解压制，或方向偏转 ≥15° 时提前解，`ClientPlayerControlsImpl_Default.cs:340-371`） |
| Dash 结束 | 位移曲线本身持续 1 s；之后可立即再 Dash（`DashTime - m_dashTimer >= 1` 在计时器归零后即满足，`:437`） |
| 撞火被击退 | +0.2 s 不可控 + 1.33 格位移 |
| 被风箱/水枪喷到 | +0.2 s + 1.67 格位移（风箱） |
| 传送带逆向 | 位移时间 ×`4/(4-s)`，`s=1` 时 ×1.33 |
| 上传送带/下传送带 | 有 `m_border` 邻带交接窗口（`Travelator.cs:97-110`），速度会**提前变成邻带的**，交接瞬间速度有跳变 → 靠近边界时不要用精确按键时长 |
| 上/下平台 | 地面碰撞体变化 → 触发父级切换（`GroundCast.cs:197-200`），有 1 帧左右的层级切换抖动；`PlayerControls.FixedUpdate` 会重投影上一帧位置（`PlayerControls.cs:670-684`），**切换帧测量的速度会有一帧异常，脚本不要用单帧速度做判断** |
| 驾驶平台后下车 | 平台再漂 0.3–0.5 s 归位 |
| 炮台飞行 | ≈`m_CurveTime`(1 s) 不可控 + 落地 0.2 s（0.4 u 前冲） |
| 剧情瞬移 | 完全不可预知，必须闭环读坐标 |

## 6. 未解疑问（需要在运行期验证，不要在文档里猜）

1. **`Player` 预制体上 `MovementData` 的实际数值**。本文所有数值都是 C# 字段初始值（`PlayerControls.cs:24-50`），prefab 可覆盖。**建议**：插件启动时 dump `PlayerControls.Movement` 的全部字段。
2. **各关卡 `LevelConfigBase.m_disableDynamicParenting` 的实际取值**。代码默认 `true`（`LevelConfigBase.cs:11`），这决定了厨师到底会不会被平台 `SetParent` 带（§2.2.4）。**这是本节最重要的未知量。**
3. **`DynamicLandscapeParenting` 在父子关系成立时，玩家自己的 `Rigidbody` 速度（世界系）与父级位移是如何叠加的**。`ClientPlayerControlsImpl_Default` 只写世界系速度（`:434`），而层级位移由 Unity 施加——「反编译存疑」，需实测"平台速度 4 + 玩家按键 4 到底得到多少"。
4. **`MovePosition`（表面速度/风）与 `velocity`（自身移动）的精确合成**。`ClientPlayerControlsImpl_Default.cs:434` 与 `:929` 在同一子步里先后生效，「反编译存疑」。**传送带上"4 + 带速"的方向性结论可信，绝对速度需实测标定。**
5. **"New Gravity" 下的净重力加速度**。`AddForce(Acceleration)` 每个 1/60 子步调用一次（`:916`），而物理步是 `Time.fixedDeltaTime`（默认 0.02 → 50Hz），两者的频率比会放大累积，「反编译存疑」。表现为贴地 + 斜坡缓滑，具体数值需实测。
6. **`RatBehaviour.m_knockbackDistance = 3f`（`RatBehaviour.cs:13`）没有任何读取点**，`m_lives`（`:10`）同样。老鼠是否真的会击退玩家？**未验证**——可能在未反编译的程序集里，或已废弃。
7. **`tag = "MovingPlatform"` 由谁设置**：全工程无赋值点（搜遍 `CompareTag|.tag ==|tag = "`），必然来自 prefab/场景 → **未验证具体哪些 prefab 打了这个 tag，以及平台物体上是否挂了 `IParentable`（`ObjectContainer` 等）**。后者决定 A 通道能否工作。
8. **关卡里每条 `Travelator` 的 `m_speed` / `m_directionXZ` / `m_border` / `transform.right`** 全在 prefab，「未验证」。注意 `Rightwards` 的实现是 `-transform.right`（`Travelator.cs:172`），别按名字猜。
9. **平台物体上是否有 `Animator` 驱动的位移**（纯资产层，绕过全部 `.cs`）。`.cs` 无法排除，需在场景里确认——这关系到 §1.1"不存在自动巡航平台"这个结论是否绝对成立。
10. **传送门动画时长**（`ManualAnimation` + 剪辑）与 `Teleportal.m_receiveDelay / m_cooldownTime` 的关卡取值（`Teleportal.cs:17-20` 默认 0），「未验证」。建议用状态轮询而非定时。
11. **`PilotRotation` 在炮台上的 `MoveSpeed` 到底是度/秒还是别的**。`ServerPilotRotation.cs:46` 是 `m_angle += MoveSpeed * ±1 * deltaTime`，而 `m_angle` 被直接赋给 `eulerAngles.y`（`:48`），所以单位是**度/秒**；但 `PilotMovement.MoveSpeed` 的默认值是 4（`PilotMovement.cs:9`），即 4°/s——**对炮口转动来说太慢**，怀疑炮台 prefab 覆盖成了更大的值。「推断 + 未验证」。
