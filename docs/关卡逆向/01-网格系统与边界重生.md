## 1. 机制概览

游戏里有 **两套互不相同的"格子"概念**，混用是自动化脚本最大的坑：

1. **占用网格（GridManager）** —— 一张 `Dictionary<GridIndex, GameObject>`，键是整数格坐标，值是"这一格上站着谁"。它由关卡里实现 `IGridLocation` 的对象在 `Awake` 里主动注册（`StaticGridLocation.cs:20-25`），移动物体则每帧重注册（`DynamicGridLocation.cs:5-26`）。
   **只有"占位物"才进这张表** —— 灶台、案板、墙、地上放着的物品、火灾。水面 / 岩浆 / 车道这类 `RespawnCollider` 触发器**不进表**（`GridNavSpace.cs:53` 的判据就是 `GetGridOccupant(index) == null`）。

2. **导航网格（GridNavSpace）** —— 在 `Start` 时把占用网格采样成一张 `bool[,] m_nodeMap`，再交给 `AStar.PathFinder`（`GridNavSpace.cs:44-56`）。它**只在 Start 建一次，之后永不刷新**（见 §2.1.7）。

所以：**"能不能走" ≠ "会不会死"**。原生 `FindPath` 只会绕开占用物，一定会横穿水面把厨师淹死（`GridNavSpace.cs:53` + `ServerRespawnCollider.cs:46-49`）。要拿到真正安全的路径，必须自己做一层"占用格 ∪ 危险触发器"的并集。

死亡与重生分两半：
- **服务端**（`ServerRespawnCollider` → `ServerPlayerRespawnManager.KillOrRespawn` → `IRespawnBehaviour.RespawnCoroutine`）只负责"发一条 Begin 消息 + 处理手里物品"。
- **客户端**（`ClientPlayerRespawnBehaviour`）持有**完整时间线**：关碰撞、播动画、渐隐/缩放、搬回出生点、放特效，全程由 `UpdateSynchronising()` 驱动（`ClientPlayerRespawnBehaviour.cs:71-84`）。

`ServerPlayerRespawnBehaviour.RespawnCoroutine` 在发完 Begin 后 `yield break`（`ServerPlayerRespawnBehaviour.cs:27`），**服务端根本不知道重生什么时候结束**——重生时长实际上由客户端本地计时决定。

> ⚠️ **反编译存疑（重要，影响字典正确性）**
> - `Equals(object)` 反编译为 `X == gridIndex.X && Y == Y && Z == Z`（`GridIndex.cs:44`）。若字面属实，则结构体判等**只比较 X**——而 `GridManager.m_gridOccupancy` 就是一个 `Dictionary<GridIndex, GameObject>`（`GridManager.cs:9`），会用默认比较器走 `Equals(object)` / `GetHashCode()`。**更可能是 ilspycmd 把 `gridIndex.Y` 折叠成了 `Y`**，但无法从 `.cs` 确认。
> - 哈希函数 `(m_x << 16) ^ (m_y << 8) ^ m_z`（`GridIndex.cs:51`）在 x/y/z 超出 8/16 位时会互相污染。
> - `IEqualityComparer<GridIndex>` 的两个实现方法一个只比哈希（`GridIndex.cs:54-57`），一个用 `this.m_z` 而非 `obj.Z`（`GridIndex.cs:59-62`）——都有 bug。**不过** `GridIndex` 没实现 `IEquatable<GridIndex>`，`Dictionary` 的默认比较器不会走这两个方法；`new Dictionary<...(default(GridIndex))`（`GridManager.cs:9`）参数是接口类型，`default(GridIndex)` 装箱后是 `null`，所以仍是默认比较器。
> - **建议**：插件侧自己建索引时不要复用 `GridIndex` 作为 `Dictionary` 键，用自己的 `(int x, int z)` 元组或 int 编码；并在运行时用探针验证 `gm.GetGridOccupant(new GridIndex(x,0,z))` 对不同 x 相同 z 的格是否返回不同值。

#### 2.1.3 `QuadGridManager` / `HexGridManager`（原点与偏移怎么算）

**`QuadGridManager`（方形网格，关卡主用）**

```csharp
// QuadGridManager.cs:5-9
[SerializeField] private Vector3 m_origin;               // 默认 (0,0,0)
[SerializeField] private Vector3 m_size = Vector3.one;   // 每格尺寸，默认 (1,1,1)

// QuadGridManager.cs:28-31
GetPosFromGridLocation(i) = transform.TransformPoint(m_origin + (i.X*m_size.x, i.Y*m_size.y, i.Z*m_size.z))

// QuadGridManager.cs:33-38
GetUnclampedGridLocationFromPos(p) :
     local = transform.InverseTransformPoint(p) - m_origin
     return GridIndex( round(local.x/m_size.x), round(local.y/m_size.y), round(local.z/m_size.z) )
```

要点：
- **格坐标是世界坐标经 `GridManager.transform` 的逆变换再减 `m_origin` 后除以 `m_size` 得到的**。也就是说 `GridManager` 的 Transform 如果带旋转/缩放，格坐标轴会跟着转/缩放。
- 「每格 1.2 世界单位」= `m_size.x = 1.2`，这个值来自 prefab 序列化数据（`.cs` 里只看到默认 `Vector3.one`）→ **未验证具体关卡里 `m_size` 与 `m_origin` 的实际取值**。
- 反查用 `Mathf.Round`，即**最近格**（不是 floor）。
- `Origin()` 方法额外暴露 `m_origin`（`QuadGridManager.cs:23-26`），`AccessOrigin` 属性可读可写（`QuadGridManager.cs:11-21`）。

**`HexGridManager`（六边形网格，个别关卡/世界地图用）**
- `m_hexRadius`（默认 1）、`m_gridSizeY`（默认 1）（`HexGridManager.cs:8-12`）。
- `GetPosFromGridLocation`：`x*3/2*R`、`y*gridSizeY`、`R*(x*√3/2 + √3*z)`，`c_root3 = 1.7320508f`（`HexGridManager.cs:14`、`HexGridManager.cs:23-26`）。
- `GetUnclampedGridLocationFromPos`：先算浮点 fx/fz，再对 floor/ceil 四种组合取**欧氏距离最近**的格（`HexGridManager.cs:33-54`）。
- 提供 `static int ComputeDistanceHexGrid(GridIndex A, GridIndex B)`（`HexGridManager.cs:56-75`）。

#### 2.1.4 占用物是怎么注册的（谁调用、什么时机）

|---|---|---|---|

**`StaticGridLocation` 的执行顺序**由 `[ExecutionDependency(typeof(CampaignKitchenLoaderManager))]` / `[ExecutionDependency(typeof(CompetitiveKitchenLoaderManager))]` 标注（`StaticGridLocation.cs:3-4`），即**等关卡加载管理器就绪后才允许 `Awake` 注册占用**。`GridAutoParenting` 同样声明了对 `IGridLocation` 的依赖（`GridAutoParenting.cs:3`）。

#### 2.1.5 `IGridLocation` / `IHandleGridTransfer` 与"挤占"时机

```csharp
// IGridLocation.cs:1-6
public interface IGridLocation { GridIndex GridIndex { get; } GridManager AccessGridManager { get; } }

// IHandleGridTransfer.cs:3-8
public interface IHandleGridTransfer {
    bool CanHandleTransfer(GridIndex _index, GameObject _object);
    void HandleTransfer(GridIndex _index, GameObject _object);
}
```

**`GridManager.OccupyGrid` 的完整语义**（`GridManager.cs:64-80`）：

```
if 该格已有占用物 old:
    t = old.RequestInterface<IHandleGridTransfer>()
    if t != null && t.CanHandleTransfer(index, new):
         t.HandleTransfer(index, new)     // 通知旧物"你被顶掉了"
         m_gridOccupancy[index] = new     // 换人
    else:
        什么都不做（新物占用失败，但方法返回 void，调用方无从得知）
else:
    m_gridOccupancy.Add(index, new)
```

- **这是 `void` 方法**：挤占失败（新物没占上）时调用方拿不到任何返回值。`DynamicGridLocation` 因此必须自己回读 `GetGridOccupant` 才知道成没成功（`DynamicGridLocation.cs:20-25`）。
- 游戏里唯一的 `IHandleGridTransfer` 实现是 `ServerHazardBase`（`ServerHazardBase.cs:4`），它的 `CanHandleTransfer` 恒 `true`（`ServerHazardBase.cs:22-25`）。具体子类 `ServerFireHazard.HandleTransfer` 的行为是：**若闯入者不是火，就把自己扑灭**（`ServerFireHazard.cs:50-56`）。也就是说火灾占格，厨师/物品踩上去会把火浇灭。
- `ServerHazardBase.Start()` 通过 `RequireInterface<IGridLocation>()` 拿到自己的格与 `GridManager`（`ServerHazardBase.cs:14-18`）——所以危险物本身也是 `IGridLocation`（通常配 `StaticGridLocation`）。

#### 2.1.6 `GameUtils.GetGridManager` —— 多网格时怎么选

```csharp
// GameUtils.cs:98-109
public static GridManager GetGridManager(Transform _areaReference) {
    if (_areaReference != null) {
        var gm = _areaReference.gameObject.RequestComponentUpwardsRecursive<GridManager>();  // ① 沿父级链向上找
        if (gm != null) return gm;
    }
    return RequireManagerInterface<GridManager>();                                            // ② 退回 ManagerDirectory
}
```

- **① 向上找**：从当前对象沿 `transform.parent` 链找 `GridManager`。关卡物件一般挂在关卡根下，而 `QuadGridManager` 挂在 `GameController` 层级下（因为 `ManagerDirectory` 用 `GetComponentsInChildren<Manager>()` 收集，`ManagerDirectory.cs:29-36`），所以**向上找经常失败**。
- **② ManagerDirectory 兜底**：
  ```csharp
  // GameUtils.cs:190-193 → GameUtils.cs:165-188 → ManagerDirectory.cs:60-76
  foreach (var kv in m_allManagers) {                 // Dictionary<Type, Manager>，遍历顺序未规定
      T v = kv.Value.gameObject.RequestInterface<T>();
      if (v != null) return v;                        // 第一个命中就返回
  }
  ```
  `m_allManagers` 的键是"每个 Manager 的完整继承链上的每个 Type"（`ManagerDirectory.cs:32-35`）。对 `T = GridManager`，**所有 `QuadGridManager` / `HexGridManager` 都会命中**。
  → **多个网格同时活跃时，选哪一个取决于 `Dictionary` 的遍历顺序，属于未定义行为**。

- **`GridManager.s_activeGrids`（`GetActiveCount`/`GetActive`）与 `GameUtils.GetGridManager` 是两条不同的路径**，前者是全局列表、顺序 = `OnEnable` 顺序，后者依赖层级/字典。游戏自身在需要"遍历全部网格"时统一用前者：
  - `InteractWithItemHelper.GetFacingGridOccupant`：`for (i < GridManager.GetActiveCount())` → `GetActive(i)` → `GetUnclampedGridLocationFromPos(scanner.position)` → `GetGridOccupant(...)`，并且**用未夹紧坐标**（`InteractWithItemHelper.cs:37-49`）。
  - `TriggerIgniteArea.GridObjectsInRadius`：同样遍历全部活跃网格，再用 `GetPosFromGridLocation` 做半径判定（`TriggerIgniteArea.cs:32-64`）。

#### 2.1.7 `GridNavSpace` / `GridNavigator`（原生 A*，以及"不会刷新"）

```csharp
// GridNavSpace.cs:6
public class GridNavSpace : Manager

private bool[,] m_nodeMap;      // GridNavSpace.cs:10
private Point2  m_mapOffset;    // GridNavSpace.cs:12
```

构建（**只在 `Start` 执行一次**）：

```csharp
// GridNavSpace.cs:44-56
Point3 h = m_gridManager.GetGridHalfSize();
m_nodeMap   = new bool[2*h.X + 1, 2*h.Z + 1];          // 默认 (20,1,20) → 41 × 41
m_mapOffset = new Point2(h.X, h.Z);
for i in 0..X-1, j in 0..Z-1:
    m_nodeMap[i, j] = (m_gridManager.GetGridOccupant(GetIndexFromPoint(new Point2(i, j))) == null);
```

坐标映射：
- `GetIndexFromPoint(Point2 p) = GridIndex(p.X - offset.X, 0, p.Y - offset.Y)`（`GridNavSpace.cs:25-28`）→ **导航层永远取 `Y = 0`**。
- `GetPointFromIndex(GridIndex i) = Point2(i.X + offset.X, i.Z + offset.Z)`（`GridNavSpace.cs:20-23`）→ **第一维是 X，第二维是 Z**。

公开 API：
- `Point2 GetNavPoint(Vector3 worldPos)`（`GridNavSpace.cs:14-18`）
- `List<Vector3> FindPath(Point2 start, Point2 end)`（`GridNavSpace.cs:30-37`）—— 直接 `new SearchParameters(start, end, m_nodeMap)` 交给 `AStar.PathFinder`，再把结果逐点 `GetPosFromGridLocation` 转世界坐标。

**关键缺陷**：
1. `m_nodeMap` / `m_mapOffset` 都是 `private`，**没有任何 public 读取接口**。插件拿不到原始布尔图，只能靠 `FindPath` 结果反推。
2. **没有刷新逻辑**。`Start` 之后即使灶台被搬走、火灾生成、动态关卡换布局，`m_nodeMap` 也不变 → 动态关卡里原生 A* 会给出过时路径。
3. 水面不是占用物 → A* 一定会穿水。

`GridNavigator`（`GridNavigator.cs:5-75`）是消费方：`Awake` 里 `GameUtils.GetGridNavSpace()`（`GridNavigator.cs:16-19`），`MoveToTarget(Vector3)` 逐帧沿 `FindPath` 结果推进，速度 `m_speed = 4.5f`（`GridNavigator.cs:7-8`、`GridNavigator.cs:44-75`）。

> `GridNavSpace` 是 `Manager`，`GameUtils.GetGridNavSpace()` 走 `RequireManager<GridNavSpace>()`（`GameUtils.cs:111-114`），即也是从 `ManagerDirectory` 解析——**多个关卡/多网格时同样可能选错**。

#### 2.1.8 动态关卡里网格会不会重建

- `GridManager` 是挂在关卡环境（`GameController` 层级，带 `ManagerDirectory`）下的 `Manager`（`ManagerDirectory.cs:29-36`）。**换关卡 = 换场景 = 该 `GridManager` 随 `OnDisable`/`OnDestroy` 从 `s_activeGrids` 移除**（`GridManager.cs:30-33`），新关卡重新 `OnEnable` 注册。→ 网格会重建。
- **同一个关卡内**布局变化的处理方式不同：
  - 可移动物（飞艇/木筏平台）走 `DynamicGridLocation` 每帧重注册（`DynamicGridLocation.cs:5-26`）或 `ServerPilotMovement.TryOccupyGridRegion`（`ServerPilotMovement.cs:30-40`）。
  - 关卡切换动画（木筏离开/墓地柜台换位）**不复用网格，而是直接用 `IRespawnBehaviour` 把物体"重生"掉**：`CampsiteAnimatedDynamicTransition.DestroyAndRespawnObjects` 遍历场景所有 `IRespawnBehaviour`，落在离开区域的逐个 `ServerPlayerRespawnManager.KillOrRespawn`（`CampsiteAnimatedDynamicTransition.cs:53-99`，调用点 `:77`、`:95`）；`GraveyardCountersDynamicTransition.RespawnAllUtensils` 同构（`GraveyardCountersDynamicTransition.cs:139-154`，调用点 `:151`）。
  - **但 `GridNavSpace.m_nodeMap` 不跟着刷新**（§2.1.7）→ 这是自动化里最容易踩的坑。

#### 2.1.9 `ComponentCache<T>` / `ComponentCacheRegistry`

## 5. 对自动化的含义

### 5.1 ★ 怎么用公开 API 读出整张可走网格（确切答案）

**推荐路径：直接自己枚举 `GridManager` 的占用表**——它虽然是 private 字段，但 `GetGridOccupant` 是 public（`GridManager.cs:82-87`），足以重建整张图。

```csharp
using UnityEngine;
using System.Collections.Generic;

public struct Cell { public int X; public int Z; }

public static Dictionary<Cell, GameObject> BuildGridMap(out GridManager gm)
{
    var map = new Dictionary<Cell, GameObject>();

    // ① 拿到"当前关卡的那个"网格管理器。两条路都要试：
    //    (a) 全局活跃列表 —— 游戏自己遍历多网格时的写法（InteractWithItemHelper.cs:40-43 / TriggerIgniteArea.cs:34-37）
    //    (b) 从某个已知关卡对象向上找 —— GameUtils.cs:98-109
    //    若 GetActiveCount() == 1 直接用；>1 时必须逐个判断哪个属于自己的关卡（见 §5.2 的坑）
    int n = GridManager.GetActiveCount();
    gm = (n == 1) ? GridManager.GetActive(0)
                  : GridManager.GetActive(0);   // 多网格时按 bounds/occupant 分布挑（见 §6 未解疑问）

    // ② 半尺寸决定坐标范围
    Point3 half = gm.GetGridHalfSize();                       // GridManager.cs:59-62
    for (int x = -half.X; x <= half.X; x++)
    for (int z = -half.Z; z <= half.Z; z++)
    {
        // ③ 导航层固定 Y = 0（GridNavSpace.cs:25-28 的 GetIndexFromPoint 恒用 y=0）
        var idx = new GridIndex(x, 0, z);
        var occ = gm.GetGridOccupant(idx);                    // GridManager.cs:82-87
        if (occ == null) map[new Cell { X = x, Z = z }] = null;   // 空格 = 可走
        else             map[new Cell { X = x, Z = z }] = occ;    // 有东西 = 障碍
    }
    return map;
}

// 格 → 世界坐标（导航时用来发移动目标）
public static Vector3 CellToWorld(GridManager gm, int x, int z)
    => gm.GetPosFromGridLocation(new GridIndex(x, 0, z));     // QuadGridManager.cs:28-31

// 世界坐标 → 格（★ 用 Unclamped 版本，否则越界会被吸到边界格）
public static GridIndex WorldToCell(GridManager gm, Vector3 p)
    => gm.GetUnclampedGridLocationFromPos(p);                 // GridManager.cs:47 / QuadGridManager.cs:33-38
```

要点与坑：

1. **不要用 `GetGridLocationFromPos` 反查"我在第几格"之外的用途**：它会把越界点 `Mathf.Clamp` 到边界（`GridManager.cs:49-57`），得到"贴着墙的假格"。判断"是否出界"必须用 `GetUnclampedGridLocationFromPos`。
2. **`Y` 层**：`halfSize.Y` 默认 1 → 有 `-1 / 0 / 1` 三层。导航只看 `Y = 0`（`GridNavSpace.cs:27`）。想知道"某格上方是否被台面挡住"，还要查 `Y = 1`。
3. **必须轮询，没有事件**：`GridManager` 不提供任何占用变化通知。若要在每帧做寻路，缓存 `Dictionary<Cell, GameObject>` 并按需（例如每 0.2s 或每步）重建。
4. **多网格**：`GridManager.GetActiveCount()/GetActive(i)` 是**唯一的全局枚举入口**（游戏自己也是这么用的：`InteractWithItemHelper.cs:37-49`、`TriggerIgniteArea.cs:32-64`）。`GameUtils.GetGridManager(transform)` 在多网格时是**未定义行为**（§2.1.6）。
5. **【重要】不要依赖 `GridNavSpace.FindPath`**：`m_nodeMap` 只在 `Start` 建一次、永不刷新（`GridNavSpace.cs:44-56`），且它把水面当可走格（`GridNavSpace.cs:53`）。可以调用它的 `FindPath` 做参考，但**必须自己叠加危险区过滤**，或干脆自己在 `Dictionary<Cell,...>` 上跑 A*。
6. **`GridNavSpace.FindPath` 的输入是 `Point2`，不是世界坐标**：先 `GetNavPoint(worldPos)`（`GridNavSpace.cs:14-18`），并且**第一维是 X、第二维是 Z**（`GridNavSpace.cs:20-23`）。返回值已是世界坐标 `List<Vector3>`。
7. **自己生成的对象要刷缓存**：如果插件创建了带 `IGridLocation` 的对象，必须调 `ComponentCacheRegistry.UpdateObject(go)`（`ComponentCacheRegistry.cs:85-105`），否则 `ComponentCache<IGridLocation>` 里是 `null`。

### 5.2 ★ 怎么识别水面格（确切答案）

水面**不是**占用物（`GridNavSpace.cs:53` 只看 `GetGridOccupant`），所以必须单独拿 `RespawnCollider`。

```csharp
using UnityEngine;
using System.Collections.Generic;

// 收集所有危险触发器（水/岩浆/车道/深渊），并给出它们的碰撞体
public static List<(RespawnCollider rc, Collider col)> CollectHazards()
{
    var list = new List<(RespawnCollider, Collider)>();
    foreach (var rc in Object.FindObjectsOfType<RespawnCollider>())   // RespawnCollider.cs:3（public MonoBehaviour）
    {
        var col = rc.GetComponent<Collider>();                        // 碰撞体是同级组件，见 LevelBounds.cs:32
        if (col != null) list.Add((rc, col));
    }
    return list;
}

// 判断某一格是否踩了危险区
public static RespawnCollider.RespawnType? HazardAt(GridManager gm, int x, int z,
                                                   List<(RespawnCollider rc, Collider col)> hazards)
{
    Vector3 p = gm.GetPosFromGridLocation(new GridIndex(x, 0, z)) + Vector3.up * 0.1f;  // 略微抬高避免贴地误判
    foreach (var (rc, col) in hazards)
    {
        if (col.bounds.Contains(p)) return rc.m_respawnType;          // RespawnCollider.cs:13-14 公开字段
        // 非盒体可用： if (col.ClosestPoint(p) == p) ...
    }
    return null;
}
```

判定与结论：
- **水 = `RespawnCollider.m_respawnType == RespawnType.Drowning`**（`RespawnCollider.cs:8`、`:13-14`）。`m_respawnType` 是 **public 字段**，直接读。
- **最终可走格 = `GetGridOccupant(idx) == null` 且 `HazardAt(idx) == null`**。
- 车/滑倒区是 `RespawnType.Car`（`RespawnCollider.cs:10`），深渊/掉出地图是 `FallDeath`（`:9`）。**是否要把 `Car` 也当禁行取决于关卡**，建议把三者都标出来再按关卡策略过滤。
- 注意 `RespawnCollider` 自身无 Collider、需同级取；`LevelBounds` 的 4 面墙 + KillPlane + Ceiling 也是 `RespawnCollider`/`Collider`，会被同一个 `FindObjectsOfType` 抓到 → **务必按 `m_respawnType` 过滤**，否则整张图都会被判成不可走。
- `Object.FindObjectsOfType<RespawnCollider>()` **不返回未激活对象**。若某些水域平时 `SetActive(false)`（例如水位动画），需要 `Resources.FindObjectsOfTypeAll<RespawnCollider>()` 再过滤 `gameObject.scene.IsValid()`。
- **敌人/坠落也包含在内**：KillPlane 覆盖整个关卡底部，其 `bounds.Contains` 对任何地面平面都成立吗？——KillPlane 通常是**低于地板**的一块薄板，所以地面格一般不在其 bounds 内。**这一点必须实测确认**（未验证）；如果发现 KillPlane 覆盖了正常地面，就用「离地高度」或只取 `Drowning` 来过滤。

### 5.3 重生期间该等多久 / 怎么等

- **推荐等待条件**：轮询 `player.m_playerControls.m_bRespawning == false`。
  - 依据：`m_bRespawning` 是 `PlayerControls` 的 **public 字段**（`PlayerControls.cs:303-304`），在 `BeginRespawn` 开头置 `true`（`ClientPlayerRespawnBehaviour.cs:112`），在 `RunSpawnAtSpawnPoint()` **完整跑完**（含 `m_particleTime` 等待和 `ResumeMovement()`，`:389-404`）之后才置 `false`（`:165`）。
  - 也就是说 **`m_bRespawning == false` ⟺ 控制权已归还**，不需要再额外等 `m_particleTime`。
- **等价条件**：`player.GetComponent<ClientPlayerRespawnBehaviour>().IsRespawning == false`（public 属性，`ClientPlayerRespawnBehaviour.cs:40`）。两者同时翻转，取哪个都行；`m_bRespawning` 更省一次 `GetComponent`。
- **预期时长**：`m_respawnTime + m_particleTime` ≈ **6.0s**（代码默认值）。保险起见给 8~10s 超时保护，并检查超时原因（见下）。
- **超时的常见原因（要写进日志）**：
  1. `MultiplayerController.IsSynchronisationActive()` 为假 → `m_currentRespawn` 被直接丢弃（`ClientPlayerRespawnBehaviour.cs:75-78`），**重生流程永久卡死**，玩家会一直隐身+无输入。
  2. `m_clientChefSynchroniser.IsReadyToResume()` 长时间为 false → 卡在 `RunSpawnAtSpawnPoint`（`:372-379`），此时 `m_bRespawning` 仍是 `true`。
  3. 玩家所在层被 `TimeManager` 暂停 → `TimerRoutine` 不走（`CoroutineUtils.cs:25-31`、`TimeManager.cs:315-322`）。
- **不要用固定 `Sleep(5)`**：prefab 可以覆盖 `m_respawnTime`（**具体关卡的实测值未验证**），而且上面三种卡死会让固定睡眠变成误判。
- **重生期间不要发输入**：本地受控玩家被 `Suppress`（`ClientPlayerRespawnBehaviour.cs:421-427` → `PlayerControls.cs:483-486`、`SuppressionController.cs:18-27`），移动指令不会生效（`PlayerControls.cs:470-473`）。

### 5.4 死亡后 0.5s 的控制权切换

`RunSwitchToNextDelayed(m_switchDelay = 0.5f)`（`ClientPlayerRespawnBehaviour.cs:139`、`:177-190`）会在死亡 0.5s 后调用 `PlayerSwitchingManager.ForceSwitchToNext(player)`（`PlayerSwitchingManager.cs:118-125`），前提是"当前选中的 avatar 就是死的这个"。
- **若一个输入槽只挂一个厨师**（标准双人双控），这个调用基本是空操作。
- **若一个输入槽挂了多个厨师**（本项目的自动化方案若用单输入驱动两名厨师、或开了连续角色切换），**死亡 0.5s 后当前受控对象会变**。插件必须每帧重读当前受控的 `PlayerControls`（`PlayerSwitchingManager.SelectedAvatar(playerId)`，`PlayerSwitchingManager.cs:111-116`），**不要在死亡前缓存 chef 引用**。

### 5.5 越界判断怎么用

- 想复用游戏的边界盒：`Object.FindObjectOfType<LevelBounds>()`（`s_bounds` 是 private static，拿不到列表）→ `.Contains(worldPos)`（**public 实例方法**，`LevelBounds.cs:92-95`）。
- **不要指望 `ActiveBoundsContain` 判断"玩家是否越界"**：它只被物品回位台与盘子回收台使用（§2.2.4），并且在没有任何 `LevelBounds` 时**恒返回 true**（`LevelBounds.cs:89`）。
- 若 `m_bounds` 因为"侧面 RespawnCollider 数 ≠ 4"而没算出来（`LevelBounds.cs:27`），`Contains` 几乎恒为 false → 插件启动时应该做一次自检：拿玩家出生点的世界坐标去 `Contains`，为 false 就说明边界盒没建好。

### 5.6 物品丢失的时间预算

- 物品掉进危险区后 **5s（`UtensilRespawnBehaviour.m_respawnTime`）+ 不定长的"等空台面"**（`ServerUtensilRespawnBehaviour.cs:49-59`）。
- 若全图没有任何合法的空 `ServerAttachStation`，**物品永远不回来**（`while (freeStation == null) yield return null;` 无超时）。自动化脚本在"缺盘子/缺锅"时要考虑这个情况：**该重开而不是干等**。
- 台面候选列表 `m_allRespawnStations` 首次调用后缓存（`ServerUtensilRespawnBehaviour.cs:135-138`）→ 动态关卡新增的台面不会被计入。
- 基础黑名单（灶台/盘子回收/盘子站/垃圾桶/传送带/洗碗站）见 `ServerUtensilRespawnBehaviour.cs:121-128`；`CookingUtensilRespawnBehaviour` 还有 `+1000` 惩罚（`ServerCookingUtensilRespawnBehaviour.cs:3`、`:15-18`）。
- **手里拿着东西淹死 = 东西也一起死**（`ServerPlayerRespawnBehaviour.cs:37-41`），Hit/Car 则只是丢地上（`:44`）。想保物品就别让它下水。

### 5.7 危险物占格 / 挤占语义

- 想模拟"某格是否会被危险物占据"：`gm.GetGridOccupant(idx)` 上有 `IHandleGridTransfer`（`ServerHazardBase.cs:4`）就说明这格是火灾类危险物；`ServerFireHazard.HandleTransfer` 在被非火物体挤占时会**把自己扑灭**（`ServerFireHazard.cs:50-56`）。
- `GridManager.OccupyGrid` 是 `void`，**挤占失败不报错**（`GridManager.cs:64-80`）。插件若要"放置"东西，放完之后必须回读 `GetGridOccupant` 确认。
- 想批量判断一片区域能否放置：`TryOccupyGridRegion(min, max, go)` 返回 `bool`（`GridManager.cs:94-123`）。**注意它会真的占用**，只用于探测的话探测完要 `DeoccupyGridRegion`。
