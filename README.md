> ⚠️ **免责声明**
> 非官方个人研究项目，与 Team17 / Ghost Town Games 无关；使用需要你**自行拥有正版游戏**。
> 仓库**不包含**任何游戏本体资源、模型、音频，也**不包含**反编译得到的游戏源码
> （原因：反编译源码是 Team17 的专有代码，随仓库分发会构成侵权；
> 你可以从**自己拥有的正版游戏**用 ilspycmd 自行生成，放在根目录 `overcooked_decomp/` 即可）。

## 构建与部署

1. BepInEx 解压到游戏根目录，先运行一次游戏让它生成 `BepInEx/plugins/`。
2. 改 `build.bat` 顶部的 `GAME=` / `BEP=` 两个路径。
3. `build.bat`
   > ⚠ 引用的是 **`v2.0.50727`**（.NET 2.0），**不是** `v4.0.30319`。游戏的 CLR 是 2.0，
   > 用 .NET 4 的引用会**编译通过、加载时**报
   > `Method not found: 'System.Threading.Monitor.Enter'`。
4. `build/Overcooked2AI.dll` → `<游戏目录>\BepInEx\plugins\`
   > ⚠ **游戏必须完全退出**：BepInEx 只在启动时读 dll，而且文件会被占用。
5. 启动游戏。插件在 **127.0.0.1:48778** 起一个 TCP 桥（行 JSON 协议）。

## 跑起来

```bat
:: 推荐：看护 —— 大厅缺 P2 就补、进对局自动拉起、对局结束收掉（一局一连）
python -u run_watch.py

:: 双人（两个引擎线程，共用一个订单黑板避免抢活）
python -u run_team.py
```

看护替你做四件事，**顺序不能变**：

1. 轮询游戏状态（默认 2.5 秒一次）；
2. **大厅里缺 P2 就补** —— 按 A 加入这个动作**只能在大厅做**；
3. **进对局就拉起子脚本**，且**确知这局有 `Player.Two`** 才拉（子脚本没有 P2 会直接退出）；
4. **对局结束把子脚本收掉** —— 走 `CTRL_BREAK_EVENT`（等价 Ctrl+C），**绝不 `kill`**：
   子脚本的 `finally` 里要跑 `pad.uninstall()`，不跑的话那只厨师的输入**持续被虚拟手柄
   接管**，直到游戏完全重启。

### 看护怎么配

**别每次 `set`。** 参数写进 `runtime/watch.local`（`runtime/` 是 gitignore 的，不进仓库）：

```ini
# 每行 KEY=VALUE；# 开头是注释；值里的 = 和空格都原样保留
NEKO_WATCH_CHILD=run_team.py --input keys,virtual   # 两个脚本自己打
NEKO_WATCH_KEEP_FOCUS=1                             # 一个键盘一个手柄 ⇒ 必须保持前台
NEKO_PLAN=on                                        # 递归规划器
```

配好之后，**开终端只要一句** `python -u run_watch.py`。

| | |
|---|---|
| 格式 | `KEY=VALUE`。`#` 开头和空行忽略；没有 `=` 的行也忽略（**配置写歪了不该让看护起不来**） |
| 优先级 | ☠ **显式设的环境变量优先于这个文件** ⇒ 临时改一格 `set NEKO_PLAN=shadow` 仍然管用，不用动文件 |
| 换 / 关 | `set NEKO_WATCH_LOCAL=<别的路径>`；`set NEKO_WATCH_LOCAL=0` 完全不用这个文件 |

**☠ 这个文件能放什么：不只是看护那 11 个，是全部 49 个 `NEKO_*`。**

看护起子进程时 `Popen` **不带 `env=`** ⇒ **整个环境变量原样传给子脚本**，
所以文件里的 `NEKO_PLAN` / `NEKO_STEP_COOLDOWN` / … 子脚本一样收得到。
**⇒ 一个文件配完所有东西，不用分两处。** 实测（不是推的）：

```
文件里写 NEKO_PLAN=shadow        → 看护自己收到 shadow, 子进程也收到 shadow
文件里写 NEKO_STEP_COOLDOWN=99   → 同上
```

⚠ 一个副作用值得知道：**`NEKO_INPUT` 也在其中** ⇒ 下面这两种写法**等价**，

```ini
NEKO_WATCH_CHILD=run_team.py --input keys,virtual   # 写在子脚本那一行
```
```ini
NEKO_WATCH_CHILD=run_team.py
NEKO_INPUT=keys,virtual                             # 单独一行(那是 --input 的默认值来源)
```

两种都行。**推荐第一种** —— 输入层跟哪个脚本是绑在一起的，写在一处不容易看混。

**怎么确认生效了** —— 看护启动时会自己报出来：

```
[看护] 已读本机配置 …\runtime\watch.local(显式设的环境变量优先于它)
[看护] 子脚本: run_team.py --input keys,virtual
[看护] 🔒 持续保持前台: 开着(每 2.0s 检查一次失焦) …
```

### 看护的全部参数

| 变量 | 默认 | 什么时候要改 |
|---|---|---|
| `NEKO_WATCH_CHILD` | `run_engine.py` | **要跑双人就改**：`run_team.py --input virtual`。空格分隔，第一段是脚本、其余是它的参数 |
| `NEKO_WATCH_KEEP_FOCUS` | `0` | **只要有一只厨师走键盘就该开**（`=1`）。见下面"焦点"那节 |
| `NEKO_WATCH_KEEP_FOCUS_EVERY` | `2.0` | 上面那个的检查间隔（秒）。太小吃鼠标，太大键盘厨师白等一会儿 |
| `NEKO_WATCH_FOCUS` | `1` | 启动时 / **每次按 A 之前**切前台。**和 `KEEP_FOCUS` 是两条不同的机制** |
| `NEKO_WATCH_INTERVAL` | `2.5` | 轮询间隔（秒）。游戏卡顿时可以调大 |
| `NEKO_WATCH_MISSES` | `3` | "离开对局"要**连续**几次读不到 `inRound` 才算（防抖）。读状态偶发失败时别调小 |
| `NEKO_WATCH_HEARTBEAT` | `30` | 无变化时的心跳日志间隔（秒），`0` = 不打。刷屏就调大 |
| `NEKO_WATCH_READ_FAILS` | `5` | 连续读状态失败几次才收工。⚠ **不是重连次数** —— 中间不重连 |
| `NEKO_WATCH_STOP_TIMEOUT` | `30` | 收子进程时等它自己退多久（秒）。**超时不 kill**，只是重新计时再等 |
| `NEKO_WATCH_PY` | `sys.executable` | 子进程用哪个解释器（要用宿主 `.venv` 时设它） |
| `NEKO_WATCH_LOCAL` | `runtime/watch.local` | 本机配置文件路径；`0` = 不用 |

### 全自动进关（`NEKO_WATCH_AUTO`，默认 **关**）

开着时：**主界面加入 → 切 Party 模式 → 大厅选主题 → 进可进入的关卡**。
逻辑在 `neko/auto_level.py`（纯模块 + I/O 注入，可离线验；探针 `_autolevel_probe`）。

| 变量 | 默认 | 干什么 |
|---|---|---|
| `NEKO_WATCH_AUTO` | `0` | **总开关**。`1` = 开。关着时**逐字退回老行为**（只补 P2，一个菜单键都不按） |
| `NEKO_WATCH_AUTO_SEQ` | 见下 | **换序列**（不用改代码）：`screen=join,RB,A;lobby=A,A` |
| `NEKO_WATCH_AUTO_GAP` | `1.5` | 每个动作之间等多久（秒） |
| `NEKO_WATCH_AUTO_TRIES` | `3` | 同一阶段最多重来几遍；跑完还不变就**停手打警告** |
| `NEKO_WATCH_AUTO_PAD` | `1` | 用哪个虚拟手柄（`0`/`1`） |

**动作面**：`join`（补 P2，复用既有的 `join_lobby`）/ `wait` / `pad:<键>`（虚拟手柄，默认）/
`kbd:<键>`（键盘，会当场把前台拽回游戏）。裸键名自动当 `pad:`。

☠☠ **这是"盲发按键 + 看落到哪一屏"** —— 插件报不出"主菜单当前选中哪个标签页"
（`app.menu` 读的是**游戏内**暂停菜单，主界面里恒为空串），也报不出"大厅里选了哪个主题"。
能用的只有 `scene` / `inRound` / `users`：

| `scene` | 阶段 | 动作 |
|---|---|---|
| `StartScreen` | 主界面 | 补 P2 → 切 Party/Coop → 确认 |
| `Lobbies` | Coop 大厅 | 选主题（`PickLevel` **随机挑图**）→ 厨师选择那一屏再确认 |
| 其它 | 加载/过场 | **一个键都不按**（乱按只会帮倒忙） |

⇒ 卡住就看 `[进关] ▶ <阶段>: <动作>` 那几行，对着改 `NEKO_WATCH_AUTO_SEQ`。
**默认序列是按逆向文档推的，实机第一次跑很可能要微调。**

> [`docs/参数配置.md`](docs/参数配置.md) —— 那张表是从代码里扫出来的全量 49 个。

### 切换：改哪一行

☠ **单/双脚本、输入层，全在 `NEKO_WATCH_CHILD` 这一行里**——
**前半段决定单脚本还是双脚本，后半段是传给那个脚本的参数**（输入层就在后半段）。
持续焦点是**独立的另一行**。

**① 单脚本 ↔ 双脚本**（改前半段）

| 想切到 | `NEKO_WATCH_CHILD=` |
|---|---|
| **单脚本**（一只引擎 + 你当 P2） | `run_engine.py` |
| **双脚本**（两个引擎自己打） | `run_team.py …` |

**② 输入层**（双脚本时，改后半段的 `--input`）

| 想切到 | 完整那一行 | 前台要求 |
|---|---|---|
| **两只都用手柄**（**默认**，不写就是它） | `NEKO_WATCH_CHILD=run_team.py` | **后台也能跑** |
| P1 键盘 / P2 手柄 | `NEKO_WATCH_CHILD=run_team.py --input keys,virtual` | ☠ **必须一直盯着前台** |
| 都键盘 | `NEKO_WATCH_CHILD=run_team.py --input keys` | ☠ **必须一直盯着前台** |

☠ **为什么默认是"两只都用手柄"**（实机打回来的）：试过"一个键盘一个手柄"，结果**键盘那只整局瘫痪** ——
`SendInput` 只发给**当前前台窗口**，"看一眼终端"就把前台抢走了，看护每 2 秒拽一次、
人一抢回去它又暂停 ⇒ 那一只**一步没动**（那一单全靠走手柄的另一只跑完）。
⇒ 两只都用手柄：**不看焦点、后台也能跑**，跑的时候电脑照样能用。

**③ 持续焦点**（独立一行，默认关）

| 想 | 那一行 |
|---|---|
| 开 | `NEKO_WATCH_KEEP_FOCUS=1` |
| 关 | `NEKO_WATCH_KEEP_FOCUS=0` |

⚠ **只要配置里有键盘（②里的后两种），持续焦点就该开** —— 理由见下一节。
⚠ 不写 `--input` 时用各自的默认值：**两个都是 `virtual`**（不看焦点、后台可跑）。
⚠ 参数是**启动时**读的 ⇒ 改完要**重开 `run_watch.py`**（游戏不用重启）。

三个常见组合，抄一行就行：

```ini
# 单脚本 + 你当 P2（调试用；键盘注入 ⇒ 要前台）
NEKO_WATCH_CHILD=run_engine.py
NEKO_WATCH_KEEP_FOCUS=1

# 双脚本 · 双手柄（后台也能跑，不用 KEEP_FOCUS）
NEKO_WATCH_CHILD=run_team.py --input virtual

# 双脚本 · 一个键盘一个手柄（要保持前台）
NEKO_WATCH_CHILD=run_team.py --input keys,virtual
NEKO_WATCH_KEEP_FOCUS=1
```

### ☠ 焦点：为什么默认两只都用手柄

上面写着"等引擎起来之后就不用管焦点了：那时 `runInBackground` 已经被打开，放后台照样跑"。
**那条只在两只都用手柄时成立。**

`runInBackground` 被打开的是**游戏**；而**键盘注入走 `SendInput`，它只发给当前前台窗口**。
所以只要配置里有一只走键盘，**进对局之后仍然必须保持前台**。

**实测后果比"效果差一点"严重得多**（2026-09-16）：配成"一个键盘一个手柄"跑一局，
那一只**整局一步没动** —— 因为你总要看终端，而"看一眼终端"就把前台抢走了；
看护的 `KEEP_FOCUS` 每 2 秒拽一次，人一抢回去它又暂停 ⇒ 一直卡在"暂停/恢复"之间抖。
那一单全靠走手柄的另一只一个人跑完（**它交掉了**）。

⇒ 所以默认改成**两只都用手柄**：不看焦点、后台可跑，跑的时候电脑照样能用。
`NEKO_WATCH_KEEP_FOCUS=1` 仍然留着（真要一键盘一手柄时才需要）——
☠ 但要知道它会**真的抢走你的焦点**，那是它的意义不是副作用。

### 两个"不是参数"的注意事项

**① `python -u` 不是可选的。** 看护起子进程走的是**管道**，Python 对管道默认 8KB 块缓冲
⇒ 日志**攒着分批吐**，看不到实时次序；更糟的是收尾走 `CTRL_BREAK_EVENT`，缓冲区里没吐出来
的那部分**直接丢** —— 而一局 150 秒跑完，最想看的恰恰是结尾那几行。
看护拼子进程命令时**固定带 `-u`**，手动跑入口脚本时也一律写 `python -u`。

**② 别给桥写"断了自己重连"的包装器。** 桥的 `AcceptLoop`（`BridgeServer.cs:50-69`）
一出异常就 `break`，之后整个会话不再接新连接。看护用的是**一条长连接**，读状态偶发失败
就在**同一条连接上再读**，不重连。

### 看护的日志怎么读

```
[看护] 启动 —— 轮询游戏状态, 缺 P2 就补, 进对局拉起 run_team.py
[看护] 已读本机配置 …(显式设的环境变量优先于它)      ← 配置生效了没有, 看这两行
[看护] 子脚本: run_team.py --input keys,virtual
[看护] ✓ 桥已连上(游戏没开时这里会一直等)
[看护] ✓ 已把游戏切到前台(启动)
[看护] 大厅玩家: 2 人:One,Two —— 检查是否需要补 P2
[加入] 大厅里**已经有 2 个人** … —— 已经是双人, **跳过加入**
[看护] ▶ 进入对局
[看护] ✓ 这局有 Player.Two
[看护] ▶ 起双人 pid=…: run_team.py --input keys,virtual —— 下面开始是它的日志
[看护] · 心跳: 对局中, 场景='…', 玩家=2 人:One,Two
[看护] ◀ 离开对局(连续 3 次读不到 inRound)
[看护] ⏹ 收掉双人(对局结束) —— 发 CTRL_BREAK(等价 Ctrl+C), 等它自己 uninstall 完
```

三个关键判断点：

- `[加入]` 那行说**跳过** —— 对，大厅里已经两个人，**再按 A 会引进第三个人**；
- `[看护] ⚠ 这局没有 Player.Two` —— 那局子脚本不会被拉起（补 P2 只能在大厅做，等下一局）；
- `[看护] ⚠ 等了 30s 双人还没退` —— **不是**让你去 `kill`。等它自己缓过来，或者手动关掉它。

> **跑脚本时电脑照样能用。** 默认策略下脚本**绝不抢焦点**：你切出去干别的，它会自动暂停
> 并松开所有按键，切回游戏自动继续（`NEKO_FOCUS=always` 可改成旧行为）。
> 急停键默认 **F12**（只读按键状态，不影响你在游戏里的操作）。
> 原因：`SendInput` 是系统级注入，键会发给**当前前台窗口** —— 只能在游戏就是前台时发键。

### 按步协作的日志指纹（2026-09-17）

两个厨师**不再一人一单**：各自从**跨单的候选池**里挑"最高收益的那一步"（见
`docs\参数配置.md` 的「按步协作」一节）。这套机制**离线探针只盖到方法级**，
**整块的接线要靠下面这几行实机日志认** —— 看到才说明它真的在跑：

```
[订单] 池里 3 张单 / 21 步(跨单组 3)              ← 跨单拼池生效了
[分工] fetch SushiFish(#524212 步3) 队友在做 → 我改选下一个   ← 步级去重生效了
[盘子] counter7 那盘 → 本单(#524212:Sushi_Fish)   ← 盘子绑给订单了
[盘子] counter9 那盘 → **我接手**(原主 P1 已 25 秒没碰, 超过 NEKO_PLATE_TTL=20s)
[盘子] 这一步属于 Sushi_Fish(#524213) —— 摆盘位切到 counter9      ← 跨单时摆盘位跟着换
[评分] …(表里新增了「订单」一列)
```

**正面验收**：同一关同难度，一局得分要高过改前的 0 分。

**反面断言**（看到就是坏了，每条都对应一个能关的开关）：

| 看到什么 | 说明什么 | 先关哪个 |
|---|---|---|
| `判定=重复(全被占)` 成片刷 | 步级占位没起作用 | `NEKO_COOP_STEPS=0` 对照 |
| `错开(队友在做 X)` 成片，而队友日志里**没有** `▶ … X` | **占位泄漏**（队友被锁住） | `NEKO_STEP_TTL` 调小 |
| `⚠ 全池的步位都被占` 反复出现 | 看它**下面那行 `谁占着`**：占位**全在同一个 cid** 名下、而它此刻在做别的事 ⇒ **占位泄漏**（`NEKO_STEP_TTL` 调小 / 查释放路径）；两边各占自己那几步 ⇒ 不是泄漏，是**池子小**（`NEKO_COOP_ORDERS` 调小） | 按上面那行分 |
| `⚠ 那盘是别的单的` 刷屏 | 盘子绑定判错 | `NEKO_COOP_PLATE=0` 对照 |
| `③ 有单…但一步都做不了` 里写着 **`N/M 步的占位在队友名下`** | 池被队友占满（**是 bug**） | `NEKO_COOP_STEPS=0` 对照 |
| 同上，但写着 **`一步都不在队友名下`** | 真的做不了（**是世界的现状**） | 去看地图/可行性，别动协作开关 |
| 两人**同一时刻**同一条动作，且**没有** `[分工]` 前缀 | 黑板竞态 | `NEKO_COOP=0` 做对照 |

行为不对时的二分顺序（**从最外层往里关**）：
`NEKO_COOP` → `NEKO_COOP_ORDERS` → `NEKO_COOP_CLOCK` → `NEKO_COOP_STEPS` → `NEKO_COOP_PLATE`
→ 最后才是 **`NEKO_PLAN`**（规划器在更内一层，见下）。

### 递归规划器的日志指纹（2026-09-17 起**默认开**）

`NEKO_PLAN` 默认 `on`：规划器**接管"选哪个"**（软闸门 + 奖励分），
不是另写调度器 —— 计划排给我的那一步优先，**这一步这一轮做不到就退回整池**。

```
[引擎] 递归规划器: **已接管【选哪个】**(默认开; `set NEKO_PLAN=0` 一键回退)…
[规划] Sushi_Fish: 推出 6 步(每步的依赖见括号)
[规划]   0. P1 fetch SushiFish   ←依赖 0,1
[规划]   ★ 我(P1)下一步应为: fetch SushiFish
[规划]   ⚠ 依赖: sushirice 正在 stove0 上煮(约 8s 后熟, 到点回去取)
[规划] ⤵ 只做计划排给我的那一步: fetch SushiFish     ← 收窄生效
```

**反面断言**：

| 看到什么 | 说明什么 | 先关哪个 |
|---|---|---|
| `★ 我(Pn)下一步应为: (没有分给我的步)` | 分工**全排给一个人**（真出现过的 bug：`_plan_ctx.check` 的格距取错，`min()` 平局） | `NEKO_PLAN=0` 对照 |
| `⚠ 未验证` 的步成片 | 那些步**从没被探测过**，计划只给了它们一个分工 | 同上 |
| `⤵ 只做计划排给我的那一步` 每轮都出现 | 收窄过头（杂活/别的单都被挤出去了？） | `NEKO_PLAN=shadow` 看计划对不对 |
| `[规划] ⚠ 算崩了(不影响主流程)` | 规划器抛异常（**旁路，不影响跑**，但计划没了） | 把那一行贴出来 |

### 跨单合并计划（2026-09-17）

☠☠ 规划器**覆盖整个订单池**（池里最多 `NEKO_COOP_ORDERS` 张单），不再只覆盖最紧急那一张。

为什么必须扩：执行层的候选池本来是**跨订单**的，而计划只覆盖一张 ⇒ `_rank_candidates`
的收窄闸门（`_pf` 是**一张单**）每轮把池**压回一张单** —— **`NEKO_COOP_ORDERS` 静默失效**
（不报错，只是那几张单只剩一张在跑）。

形状（用户 2026-09-17 选的）：**只覆盖到池，不在规划期排人** ——
"谁做哪一步"仍旧交给**执行层的评分 + 步级占位**去错开两个人。
合并计划 = **无交并**：每张单各走一遍它的链，拼起来、`deps` 整体偏移、
每步盖上槽位键（`Step.slot`）。跨单**不建**依赖边。

```
[规划] 池里 3 张单(Sushi_Fish + Salad + Soup): 推出 14 步(每步的依赖见括号)
[规划]   0. P1 fetch Rice [Sushi_Fish]    ←依赖 0
[规划]   2. P2 fetch Fish [Salad]
[规划]   ★ 我(P1)下一步应为: fetch Rice[Sushi_Fish], fetch Fish[Salad]
[规划] ⤵ 只做计划排给我的那一步: fetch Rice, fetch Fish  → 收窄到 2 条候选(覆盖 3 张单)
```

☠ **`[规划]` 那一整块逐步骤日志是 `NEKO_PLAN=shadow` 专有的** —— `on` 模式只算不打印。
上面那几条指纹（含 `★ 我(Pn)下一步应为`）要看得见就得跑 shadow；
而 `⤵ 只做计划排给我的那一步` 是**评分层打的，两种模式都有**。

**反面断言（跨单这一刀专有）**：

| 看到什么 | 说明什么 |
|---|---|
| `[规划] 池里 N 张单(...)` 的 N 与 `[订单] 池里 N 张单` 对不上 | `_plan_tick` 建池与 `execute()` 建池的门不一致（两边必须同一份判据） |
| `★ 我(Pn)下一步应为:` 只列出**一张单**的步 | 合并没生效（或池里确实只有一张单） |
| `→ 收窄到 1 条候选(覆盖 3 张单)` 且**每轮都这样** | 另外两张单那几步此刻够不着（逐条可达性会剔除它们），看 `⚠ 另有 N 条此刻够不着` |
| 同名两张单的 `fetch X` 互相顶掉 | `Step.slot` 没盖上（归属会退回按 `(action, target)` 猜 —— 本仓那条老账） |

外部控制（**不用重启脚本**）：`tools\ctl.py mode|do|pause|resume|stop`。

|---|---|

## 行为层策略

**一句话：不是"按菜谱往下走"，而是"每一步把候选动作都模拟一遍能否做成，能做的里面挑分最高的"。**

### 0. 先模拟可行性，再动手 —— 这层是承重墙

每个候选都要过**两道**：

```
可达  —— 解得了解目标吗（计划坐标 → 实时台面 → 可达箱子 → 地上的料），
        以及目标旁边有没有"站得到"的格子（`_stand_cell_of`，ortho_only，和游戏一致）
可做  —— 到了那儿**干得了**吗（`_op_actionable`）
```

原话：*"可达性说的是'我到得了'，这里说的是'到了以后干得了' —— **两件事**。"*

三条纪律：

- **探测阶段永远不执行任何动作** —— 评分层拿到的每一格，都是纯查询的结果。
- **判据一律问游戏，不自己算几何**。交互半径量的是**到碰撞体表面**的距离，
  拿"格子中心距离"去比没有可比性 ⇒ `_aim_ok` 直接比对**游戏报的** `pick`/`use` 名字。
- **闸门宁可严**：`assemble` 的阶段闸门、`deliver` 的前提、`cook` 的取菜，
  都**不受 `strict` 影响** —— 因为它们不是"名字猜不准"的兜底项，是**正确性前提**。

**为什么它是承重墙**（本项目最贵的一条教训）：

> **假"能"的代价是执行一个错的物理动作，不是排序。**
> 排序错了只是慢一步；把"其实做不了"判成"能做"，就会按下去**做错事**。
> 实测两个方向都栽过 —— 拿着生肉去 `assemble`（60 分压过一切）**真会把生肉放上盘子**；
> 反过来板是空的时候空按十几下却报 `✓`，而 `pending` 是**做成了才销号、销了号就回不去**
> ⇒ 那一步再也做不了 ⇒ **整单报废**。
> ⇒ 所以判据一律收紧，宁可"现在做不了"（去干别的），也不要"以为能做"。

### 1. 候选从哪来

**菜谱步骤**（`derive()` 从订单推出来的链）+ **五个生成器**，都进同一张表：

| 生成器 | 什么时候提议 |
|---|---|
| `_chore_candidates` | 杂活：按钮可按 / 有脏盘子 / 台面上有没加工完的料 / 台面上有拼好的一盘 |
| `_pass_candidates` | 链条上有一环**我够不着**、或者**走过去太远**（`NEKO_PASS_FAR_CELLS`），而料我拿得到 ⇒ 丢给队友 |
| `_rescues` | 有锅进了报警窗口 ⇒ 去端下来（**分随紧迫度上涨**，能压过一切） |
| `_redos` | **回溯**：下游那一步要的料没了 ⇒ 把产出它的**上游**那一步重新提出来 |
| `_preps` | **提前备料**（延迟收益）：订单栏要 N 份、现在 M 份 ⇒ 把缺的那份提出来。**份数由订单算**（`lookahead.demand`），不是常数 |

### 2. 怎么排

```
分数 = 步骤价 − 2.0 × 格距 − 1.5 × 顺路 + 紧迫度 + 推进
                                    ↑         ↑        ↑
                        和别的候选目标的距离差   锅快糊了   手上这份的下一步
到不了（dist is None）⇒ -inf，直接出局
```

**步骤价**是固定的优先级表：`deliver 100` > `assemble 60` > `cook 45` = `serve_any 45`
> `pass 38` > `mix 35` > `chop 30` > `fetch 20` > `plate 15` > `rescue 15` > `work 11`
> `wash 10` > `press 8`。
一次决策只跑 **2 次 BFS**（我一份、队友一份），然后每个候选查距离表 —— 不是每个候选跑一次。

### 3. 让位（人类优先）

我分数低于 `YIELD_MIN_SCORE`(12) **且**队友原始分更高 **且**队友没在挂机（静止 < 8 秒）
⇒ 让给他。全被让位就收回自己上。**只对人类队友开**（双脚本局面比不了）。

### 4. 失败分三类 —— 处置互相冲突

| 类 | 什么时候 | 怎么办 |
|---|---|---|
| `branch` | **这一支不行**（板是空的 / 走不到 / 对不齐 / 游戏回 `placeCanHandle=false`） | **换支**重选，不原地重试，也不算整单失败（上限 `BRANCH_RETRY_MAX`） |
| `death` | 摔死到上限，路本身走不通 | 不原路重试，坐冷板凳 + 换目标 |
| `""` 空 | 执行抖动（差 1 格 / 被推开 / 被抢） | 值得**原地重试** |

⚠ 冷板凳的 key **必须带台面** —— 否则"一块板走不到"会封掉**所有**板。
⚠ 分支失败要把 op **放回 `pending`** —— 选中那一刻已经销了号，不放回去重选时它根本不在池子里。

### 5. 做不成的时候 —— 绝不停机

- **冷板凳**：同一步连续失败就把 `"动作 目标"` 移出候选 `NEKO_STEP_COOLDOWN`(20 秒)，
  这段时间去做别的（别的步骤 / 别的菜 / 杂活）。**`run()` 里没有任何 `return` 退出** ——
  一局只有 150 秒，停机 = 整局报废，而"某一步现在做不成"通常是**暂时的**。
- **横向换支**：台面被划掉就重选（`mark_branch_dead` 按**台面**记账，不是按动作）。
- **对不齐就换边**（2026-09-17，用户点名的"锅的定位不是很好"）：`_align_for_place`
  原地挪不出来时，**围着这台子转一圈**再问游戏（`NEKO_ALIGN_TRY_CELLS=0` 一键回退）。
  老行为只会朝**台面中心**再挪一步 —— 而台面是障碍格、那一步要么被挡要么把人往中心推
  ⇒ **它没有任何机制能换到台子的另一侧**，"对不齐"于是白白把一整支划死 25 秒。
  指纹见 `docs\参数配置.md` 的「放置对不齐时换边」。
- **向上回溯**：菜谱是链，下游缺料就把上游那一步重新提出来（`_redos`），一次退一级。
- **空手是回退态** —— 卡住时先把手腾空，因为**空手是可选动作最多的状态**。
  已接三处：腾手（`op_fetch`）、进不了盘时丢脚下、一个候选都没有时 `direct("take")` 丢脚下。
- **链子断了就立刻作废**：手空 + 剩下的步骤里**没有 `fetch`**（填不满手）+ 剩下的全是
  终结步（`deliver`/`pass`/`assemble`）⇒ 这条链再也走不通，立刻作废订单让外层重规划，
  不白等那 20 秒。

## 地图解析是怎么做的

### C# 侧：`Overcooked2AI/Game/LevelInfo.cs` —— 从游戏自己的网格读出来

- **来源**：游戏的 `GridManager`（`GetGridOccupant` / `GetPosFromGridLocation` / `GetGridHalfSize`）。
  ⚠ **不用** `GridNavSpace` 那张图 —— 它全工程只被**老鼠 NPC** 消费，而且只在 `Start()`
  建一次、永不刷新（平台出生格被永久记成墙，后来驶入的格却仍是"可走"，两个方向都错）。
- **每格除了可走性还要判六类**（判定有固定顺序）：

  | 判成 | 依据 |
  |---|---|
  | `F` 火 / `P` 移动平台 / `T` 传送带 / `#` 普通占用 / `C` 台面传送带 | 占用物的 **tag** |
  | `H` 危险区 | `RespawnCollider` 的 XZ 投影（按类型滤掉 `LevelBounds`/`KillPlane`，并有"单个 FallDeath 覆盖过半就忽略"的保险丝）；另有**逐格向下射线**，打中的物体挂 `RespawnCollider` 且类型是 `Drowning` ⇒ 水 |
  | `V` 空洞 | 空格子**向下打射线打不到地面** |
  | `v` 地板过低 / 正在下沉 | 射线命中了，但**落点高度不够**（低于 `StepHeightMax`）—— 荷叶那种"踩下去会沉"就靠这条 |
  | `x` **物理阻挡** | 有地面但**站不下**：`Physics.OverlapSphere` 探针球（球心在脚上方，半径取身体半径的 0.88 倍），忽略 Ground/Players/Water 等层，跳过 trigger 和 RespawnCollider；身体半径从厨师的 `CapsuleCollider` 读 |

- **刷新**：默认缓存 **5 秒**（`max_age` / `force` 可改）。`foot`（交互足迹）**不参与缓存**且最贵。

### Python 侧：`neko/terrain.py` —— 字符模型 + A\*

- **字符表**：`. # F P T H V v - @ ~ x`，`DANGER_CHARS = "FHVv"`。
  ⚠ **"太低"和"太高"都记成 `V`**（和空洞同符号）—— 用户定的。代价是**图上分不出**
  "真空洞"和"别层的平台"，要区分得看 `cell_floor_y()` 的数值。
- **`find_path`**：**A\***，8 邻接 + octile 启发，`max_nodes=8000`；
  只搜起点的连通块（`use_reach`）；**对角不切角**；终点落在台面旁最近的可走格；
  支持 `extra_edges`（**传送门 + 地面传送带**：到这一格就也能到那一格）。
- **拉直**：`_smooth` 做视线裁剪，每一跳用和 A\* **完全相同的判据**重验，且**不跨传送门跳变**。
- **`distances_from`**：从世界坐标跑一次 BFS → `{格: 步数}`，**评分层的"格距"就是查这张表**
  （一次决策两份：我一份、队友一份）。
- **`bridge_cells`**：逐格试"只把这一格变可走，目标是不是就可达了" —— 给**移动平台当桥**用。
- **`is_danger`**：字符 ∈ `DANGER_CHARS`。危险判据只在"**当前格安全、而前方是危险格**"时拦，
  不然整片被判成危险的关卡会一步都走不了。
